大家好，我是小林。
在今年云栖大会上，我看到了阿里的产品 Qoder Cloud Agents 发布了 1.0 版本，简称 QCA。
可能不少同学还是第一次听到 Cloud Agent 这个名字，你可以简单理解为，跑在「云」上的 Agent。
平时我们用桌面 Agent，打开工具，交代任务，帮自己写代码、处理文件。
但如果你做了一个 AI 应用，用户随时都可能来用呢？比如凌晨两点，有人想查订单、办售后，总不能等你第二天开电脑吧。
这时候，就需要把 Agent 放到云端，作为一项可以随时调用的服务。你希望自己的 AI 应用 7×24 小时都能接待用户，Agent 的执行就不用依赖你手边的电脑，任务来了，由云端处理，再把进展和结果传回应用。
Qoder Cloud Agents 做的就是把这部分工作托管起来。
你在 Qoder Cloud Agents 里创建一个 Agent，写好系统提示词，告诉这位 Agent 负责什么，再配上需要调用的工具，云端的 Agent 就有了。
接着，通过 API 把这个 Agent 接进自己的应用。用户在页面上发消息，云端 Agent 就能接任务去干活，省去了自己从头写一套 Agent 的功夫。
我这次做的「小林茶铺」智能客服平台，就是这么搭起来的，从0开始搭建到跑通，用了不到半天，就快速落地了一个AI应用。
这个AI应用里面共有三个专员，每个专员你可以理解为是一个Agent，每个Agent 只负责一个事情。
比如，如果顾客不知道想喝什么奶茶，饮品顾问专员就会去回复用户。
如果有顾客想看订单和进度，就会分配给订单专员去与顾客对接。
顾客想退款的话，也会分配售后专员去处理。
这个项目背后的架构是这样的。网页把任务交给 Qoder Cloud Agents，Agent 调用业务工具处理，再把结果返回网页。网页应用和数据由我提供，Qoder Cloud Agents 负责 Agent 的运行与协作。
你可能也会问，自己接大模型 API，再写点代码，不也能做吗？
当然能。但写出来之后，任务进度怎么保存，等待时资源怎么安排，出了问题又去哪查？
Qoder Cloud Agents 会保存对话、工具调用和中间结果，后续处理可以接着已有的状态继续。你也能查看执行过程，出了问题，知道该从哪里排查。
任务等模型、等工具时，可以先挂起，等结果回来再继续执行。等待期间不用一直占着执行资源，保存进度、挂起和恢复任务的这套机制，也不用自己从头搭。
至于后续Agent运行框架的升级和维护， 也不用你自己操心，你的应用直接通过接口使用Agent云服务就行，完全就省去自己跟进底层改动的精力，就可以把精力放回自己的业务上。
当然，Qoder Cloud Agents 能做的可不止智能客服。你可以按自己的需求，定义各种用途的 Agent。
比如接上经营数据，做一个分析门店生意的助手；接上代码仓库，做一个检查代码提交的评审助手；接上搜索工具，做一个持续追踪行业动态的研究助手。想让 Agent 干什么，就围绕这个任务配置提示词、数据和工具就行。
接下来看看，我是怎么一步一步把「小林茶铺智能客服平台」搭建起来的。
────奶茶智能服务台，具体怎么搭的？────
01｜先跑通一个 Hello World Agent
第一次用 Qoder Cloud Agents，可以先跟着「快速开始」建一个 Hello World Agent。
先用四步把云端 Agent 跑起来，再把这个 Agent 接进自己的网页，整个过程就清楚了。
第一步，选一个起点。
进入 Qoder Cloud Agents 控制台的「快速开始」，选择 Hello World Agent。模板已经配好了基础提示词和工具，点击「快速开始」就能往下走。
地址：https://qoder.com/cloud/
第二步，告诉 Agent 要做什么。
名称、描述、模型、系统提示词，都可以在这里改。模型先用默认的 Auto 就行，系统提示词则用来告诉 Agent 负责什么、按什么要求做事，比如「用中文简洁回答，需要查资料时先调用工具」。
第三步，给 Agent 配一个运行环境。
可以把环境理解成 Agent 在云端干活的地方。我这里新建了一个 hello-world-agent-env，后面创建会话时，选上这个环境就行。
第四步，发句话试试。
到了「第一个 API 调用」这一步，可以直接在右侧在线测试。比如，这里我发了一句「你好，用三句话介绍你能帮我做什么」，很快就收到了回复，第一个云端 Agent 就跑起来了。
左边这三个接口，后面接网页时就会用到。
第五步，把 Agent 接进自己的网页。
先准备好刚创建的 Agent ID、环境 ID。
再到控制台左侧的「个人访问令牌」创建并复制令牌，后面应用调用 Qoder Cloud Agents 时会用到。
具体怎么接入呢？接入代码可以交给 Qoder 来写。把 Qoder Cloud Agents 的 API 文档、Agent ID、环境 ID 和页面需求交给 Qoder，让它生成网页和配套后端，并创建好读取访问令牌的配置文件。
等项目建好，把刚才复制的令牌填进项目根目录的 .env.local。这次项目用的配置项是 QODER_PAT，由后端读取。
最后让 Qoder 启动项目，打开它给出的本地地址，就能在自己的页面里聊天了。页面上的消息，会由后端发给 Qoder Cloud Agents 中创建好的 Agent，回复再传回页面。
如果你想继续扩展，就去配置工具和 Skill。
回到「智能体」，点开刚建好的 Agent。
往下就能看到「技能」和「工具」。
内置工具能搜索、读写文件、运行命令；要接自己的业务系统，可以添加 MCP 服务器或自定义工具。Skill 则用来复用一套做事方法，比如固定的分析步骤、报告格式，需要时再让 Agent 加载。
熟悉了单个 Agent 怎么创建，接下来就来看奶茶店的服务台是怎么构建的。
02｜创建四个智能体
按刚才的方式，创建四个 Agent，分别写好各自的职责。一个负责接待和分配任务，另外三个负责饮品、订单和售后。
角色
负责什么
智能服务台
理解顾客需求，委派任务，汇总回复
饮品顾问
根据门店、口味和预算查询菜单与库存
订单专员
核实订单状态、金额、商品和顾客备注
售后专员
查询政策、登记申请、执行已批准的模拟退款
把三位专员建好，再到主服务台的「多智能体」里添加子智能体，团队就组起来了。
三位专员的提示词，写清楚各自负责什么。服务台的提示词，则要交代怎么分配任务。比如顾客要退款，先让订单专员核实订单，再把结果交给售后专员处理。工具没查到，就说没查到，别自己瞎猜。
03｜给Agent接上业务数据
奶茶店的菜单、库存、订单这些业务数据，都存放在 MySQL 里。为了让 Agent 能查到，我把查询 MySQL 数据的能力封装成了 MCP 工具。
MCP 服务这部分，我交给 Qoder 来写。把数据库的连接配置、表结构，以及需要提供哪些业务工具说明白，再让 Qoder 通过 SSH 登录服务器，完成开发和部署。
我在自己的服务器上搭了一个 MCP 服务，分成饮品、订单、售后三个入口，各自提供对应的业务工具。饮品顾问能查菜单和库存，退款工具则交给售后专员。
部署好之后，回到对应 Agent 的「工具」，点击「添加 MCP 服务器」，填入服务地址，再配置访问这个服务所需的凭证。
对了，这些 Agent 的系统提示词里也要交代一句，涉及价格、库存、订单这些业务信息，先调用工具查询，再根据结果回答。这样，顾客问「这杯还有没有货」，Agent 就会通过工具去查数据库。
如果你已经有订单、库存接口，也可以把这些现成接口封装成 MCP 工具，继续复用原来的业务逻辑。
04｜基本测试和评测集
配好之后，到 Qoder Cloud Agents 控制台创建会话，选择「智能服务台」，关联运行环境和前面配置好的 MCP 凭据，就可以开始测试了。
然后发一句话试试：「我在科技园店，想喝清爽一点、不含奶的饮品，20 元以内有什么推荐？」
这轮先看两件事，服务台有没有找对专员，推荐有没有用上店里的数据。在会话的执行记录里，可以查看服务台把任务交给了谁，以及专员调用了哪些工具、查到了什么数据。
对了，你还可以在 Qoder Cloud Agents 里建一个「评测集」，把常见问题和怎样才算答对一起存下来。以后改了提示词或工具配置，就拿这组问题再测一遍，看看哪些回答变好了，哪些反而出了问题。
我给小林茶铺准备了 5 个问题，覆盖饮品推荐、售罄查询、订单查询，还有订单不存在、退款信息没给全的情况。
每道题除了问题，还要写清楚怎样才算答对。比如问「科技园店现在还有茉莉柠檬茶吗？」，这轮模拟数据里库存是 0，检查点就是如实回答售罄，并且不能声称已经帮顾客下单。
发布测试集后，再创建一个实验，选好要测试的 Agent 和评估器，就可以发起评测了。
跑完后，可以查看每道题的得分和分析报告。这次我准备的 5 个问题全部通过，正确性评分都是 100 分。
这样就不用每次自己挨个提问、翻聊天记录了。你在实际使用中遇到答错的问题，也可以顺手加进评测集，下次更新时一起检查。
在 Qoder Cloud Agents 里完成这些测试后，就可以把服务台接到自己的网页了。
05｜把 Qoder Cloud Agents 接到自己的网页
网页接入和前面的 Hello World 一样，这次换成「智能服务台」的 Agent ID，并带上对应的运行环境和 MCP 凭据配置。
我把这些信息、Qoder Cloud Agents 的 API 文档和页面需求交给 Qoder，让 Qoder 完成聊天页面和后端。个人访问令牌仍然放在后端读取的 .env.local 里。
做出来就是下面这样。左边是咨询记录，中间聊天，右边可以看到哪位专员正在工作。
接入完成之后，就可以在网页应用中创建会话、发送消息、接收回复了。顾客开始一次新咨询，后端就在 Qoder Cloud Agents 创建一个会话，关联我们配好的服务台 Agent。后面继续追问，就沿用这个会话。
Qoder Cloud Agents 返回的回复和处理进展，会同步显示在页面上。
网页里的每次咨询，都能在 Qoder Cloud Agents 控制台找到对应会话。调用过哪些工具、消耗了多少 credits，也能一并查看。
06｜让服务台每天自己检查库存
当然，服务台也可以按时主动干活。比如每天开店前，检查一下哪些饮品卖完了，哪些库存快不够了。
在 Qoder Cloud Agents 的「部署」里创建一个定时任务，选择已经配好的智能服务台，设置每天上午 9 点执行，再写清楚任务要求，让 Agent 检查库存，整理一份缺货和低库存清单。
到点后，Qoder Cloud Agents 就会自动发起任务，服务台查询库存，再把结果整理出来。
这次运行中，库存为 0 的「茉莉柠檬茶」就被列进了缺货清单，店长打开结果，就知道哪些饮品需要安排补货。
这样以后就不用每天再发一句「帮我查库存」了，设好时间，Agent 会按时去做。 你也可以换成每天整理售后申请、每周汇总经营数据，把这些需要反复做的事情交给云端 Agent。
────Agent 搭好了，接下来谁来管？────
前面我们把应用搭起来了。但如果真把这个应用交给用户，新的问题就来了。
一个人用的时候，能跑就挺开心。客户多了，每个人的资料怎么分开？一批任务同时进来，谁来安排？后面想升级 Agent，难道还得挨个改？
这些事情，才是应用上线之后要长期面对的。
用 OpenClaw、DeepSeek Harness，或者基于 Codex 的运行框架自己搭，当然也是一条路。自由度高，想怎么改都可以。但采用自部署方案之后，服务器、运行配置、扩容和维护，也需要自己安排。
Qoder Cloud Agents 的好处，就是把 Agent 运行这一块交给平台托管。除了前面演示的搭建和调用，还有几项能力，在用户多起来之后会更有用。
先说身份管理。同一个 Agent，可以服务不同客户，但每个人的资料和配置得分清楚。
比如你做一个经营分析助手，A 商家上传了销售报表，B 商家接了自己的店铺系统。分析方法可以共用，资料和访问权限可不能混着来。
这次实操用的是 Qoder Cloud Agents 的 Managed 模式。如果进一步面向不同客户提供服务，可以用 Forward 里的 Identity，把自己应用中的用户关联到对应的身份，分别管理他们的文件、记忆和配置。访问外部系统需要的密钥，也可以通过 Vault 托管，运行时按需使用。
这样，同一套 Agent 能力就能复用给不同客户，不用来一个客户，就重新搭一整套。用户下次再来，也能按授权继续使用之前保存的资料。
再说并发。用户来得多，也不必跟着手动多开几套 Agent。
平时只有零星任务，活动期间突然忙起来，如果自己部署，就要考虑准备多少执行资源、任务怎么排队。一直按高峰准备，闲的时候又有点浪费。
Qoder Cloud Agents 提供弹性的执行资源调度，根据任务量安排 Agent 运行。你继续通过接口提交任务，平台承接背后的调度和扩缩容，减少自己盯着 Agent 实例加加减减的工作。
像批量分析报表、集中处理一批资料，还可以走 Batch，批量提交后再统一收取结果，不用守着一个个发。
还有一件上线后很实际的事，怎么更新，又怎么知道钱花在哪了。
比如你给 Agent 加了一套新的分析 Skill，可以先验证新版本，再让客户使用已经验证过的版本。不同客户需要的技能、模型和预算，也可以分别配置，不必为了这些差异，把业务代码改得到处都是分支。
再结合任务记录和用量统计，就能看看哪些任务经常出问题、哪些场景消耗比较多，后面该优化哪里，心里也有数。
