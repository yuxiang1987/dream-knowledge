零门槛：从一个想法，到一个高级审美的、能跑的产品。
你好，这是大刘的第 67 篇原创干货～
开源「齐码.SKILL」。
它是专用于 Vibe Coding 的 Skills。目标是接管"从一个想法，到一个高级审美的、能跑的产品"的整条链路。
不管你是什么水平，即使是小白，都可以用。
解决的问题包括：想法不确定是否有价值、需求不清晰、技术栈不固定、设计不专业、审美不高级、实现不规范、AI 味太重。它可以轻松帮你解决。
为什么叫「齐码」？看完你一定会有答案。
现在做 vibe coding，几乎都是同一个路子：把需求一股脑丢给 AI，它 vibe 一下，给你吐个能跑的产品。
听着挺爽。
如果你真的 Vibe Coding 过，那你绝对不会觉得这是简单的事情，“做计划 -> AI写代码 -> 返工 x 10086 -> 删文件夹重来”，这个闭环肯定都经历过。
很多人因此骂 AI 不行。完全没办法对齐你的想法。
但是实际上它生成代码的能力早就够用了，甚至好得有点过分。
生成早就不是瓶颈了，真正缺的，其实是我们自己都没写清楚的思路，是我做产品设计的审美，是一套足够优秀的技术架构，和一条能让每一环都对上的纪律。
所以这阵子，我干脆停下来，把我一年多做 Vibe Coding 和 AI 产品的经验，总结成这套 Skills（包含 6 个相互关联的 Skills）：
齐码.SKILL = vibe-idea → vibe-interaction → vibe-architecture → vibe-design → vibe-prototype → vibe-implement。
顾名思义，他们的任务分别是：
1. vibe-idea：把一个模糊的念头，挖掘成一份想清楚、还够狠的立项 idea.md。
2. vibe-interaction：把 idea.md 落成零歧义的交互文档 interaction.md，每次点击看到啥、触发啥， Ai都不可能有第二种解读。
3. vibe-architecture：照 interaction.md 的数据需求，在固定技术栈上派生出技术骨架 architecture.md。
4. vibe-design：把你给的视觉来源，固化成一份谁都改不歪的视觉准则 design.md，审美高级，完全没有 AI 味。
5. vibe-prototype：照着 design.md 和 interaction.md，半自动出一批对齐过的页面原型 prototypes。
6. vibe-implement：把前面这几份对齐好的文档，落成能跑的代码，做到实现=设计，一个不多、一个不少。
这里要讲一下最核心的顶层设计哲学：
每一个 skill 的入口一定是上一个 skill 的产物。
什么意思呢，就是为了确保每一环都对齐，遵循完全一致的规范，所以每个 skill 虽然是分开的，但是他们都一定有向下一步的交接。
听起来有点绕。我逐个 skill 介绍一下，你就懂了。我认为我对这套 Skill 的整体设计思路也比较有意思。
第一个 Skill，叫 vibe-idea，产出一份 idea.md。
这个 skill 里面融入了我对一个 Idea 的优劣的理解。你可以理解，它是一个优秀的帮你完善想法的产品经理。
简单说来，它把全世界的产品公认的那套"什么才算个好 idea"的标准，掰开揉碎地和我一起优化我的想法。
先问它站不站得住：这痛点是真疼，还是我自己臆想出来的？谁会用、什么场景、多久用一次？最小能跑的那版是啥、做出来拿什么算成功？这几样答不上来，那它多半还只是个一时冲动，算不上一个能做的产品。
更进一步，还需要考虑产品的流变重构、成本坍缩、人即环境、可验证黑盒这四个角度怼我，逼我别老在旧东西上修修补补，去想这事能不能用 AI 把那行的固化的解法整个进行颠覆性改造（这是我认为最有价值的地方）。
什么是我挖掘的产品的流变重构、成本坍缩、人即环境、可验证黑盒，这里我不细节展开（但是强烈推荐你打开 skill 文档研究一下），做个图大家理解一下。
业界有个共识就是，人的一瞬间想法95%是有价值的，但是真正产品化后 75% 都是辣鸡。
所以这个 skill，我希望做到的就是用足够标准的经验和角度，让你那个有价值的 idea，变成一个值得做的立得住的产品。
接下来第二个 skill，叫 vibe-interaction，产出 interaction.md。
它是整套东西里我花心思最多的，也是我觉得 vibe coding 整个流程中最核心的地方。
这个 skill 干的事，就是把"用户在每一个页面、每点一下，看到什么、触发什么"，写到非常非常非常细致的程度。
为什么重要？因为传统的 Vibe Coding 流程，基本只管核心页面，而忽略了很多细节，但是页面中是有非常多的按钮、链接、弹窗、抽屉等交互元素。实际上这些才是产品交互的核心。
所以这一段里，我搞了一套呈现方式的分类法，一共十一个词：navigate、modal、confirm、drawer、popover、bottomsheet、toast、inline-expand、inline-edit、newtab、download。
每一个能交互的元素，它点下去之后，到底是弹窗、是抽屉、是确认、还是跳转，必须、而且只能，标其中一个。
通过这种设计方法，把"点了之后到底是弹窗还是跳页"这种歧义，从源头掐死了。
至此，我们的产品中的每个可以点击的部分，从此只有一种确定的呈现方式了。
当然，光是十一个词还不够。每一个能点的东西，我都给它配一张规格表：什么时候能触发、点之前要满足什么条件、点下去走哪几步，还有它在 default、hover、pressed、disabled、loading、success、error 这七八种状态下，分别长啥样。每个页面，再强制写满四种状态：加载中、空、出错、没权限。这四个状态，恰恰是大家做产品最爱忘、也最容易翻车的地方。
再往深一层，才是我觉得"真正高级的 UI/UX"真正藏着的地方。它从来不在生成那一下界面多漂亮，而在你肯不肯把那些没人愿意操心的犄角旮旯，一样样抠清楚。
比如：一个页面在加载中、没数据、出错、没权限的时候，分别长啥样；点一下有没有个恰到好处、不晃眼的反馈；还有 AI 产品才有的那部分，模型吐内容的过程能不能让人看见、随时喊停。
这几样，恰恰是 AI 和新手最爱顺手跳过的。
这一段写完，产出的交互文档 interaction.md 厚得吓人。但你想，这些本就该有人想清楚，过去全被一句"你看着做"糊过去了。Ai 肯定理解不到。
所以这个 skill，它的最终目标，是让 AI 拿到的不再是一句"你看着做"，而是一份没有第二种解读的交互方案。
第三个skill，vibe-architecture，产出 architecture.md，搭技术骨架。
它干的活其实很直接：顺着上一份交互文档往下推，界面要显示啥、用户能改啥，它就反推出背后该存哪些数据、要几张表、前后端怎么接。采用什么样的技术栈。
我设置了默认的，但是你也可以改。
第四个skill，vibe-design，产出 design.md，定视觉。
这是非常重要的一部分，我想重点说。
我知道很多人第一反应是，定视觉不就是让 AI 出几版设计稿挑一个吗。
但是实际上，AI 完全无法准确遵循一整套设计风格！而且 AI 真的很喜欢输出蓝紫渐变，现在这种页面已经让我看着就有生理性厌恶了。
所以这个 skill，就是让你 vibe coding 出来的页面，真正是一套高级的视觉方案。
怎么做到的？我的思路其实是沿用 Claude Design 的方法。采用一个你认可的视觉风格。
那么首先，视觉风格哪里获取呢？有些网站具有大量的 DESIGN.md，比如 🔗：styles.refero.design。
选择自己喜欢的视觉风格。下载对应的 DESIGN.md。
比如说，我喜欢 Cursor 的视觉风格，我就下载它的 DESIGN.md。
然后再在 Agent 中告诉 AI，我选用的风格是@cursor-DESIGN.md。
这个 skill 就会为你产出一整套标准的包含色系、样式、组件、字体、布局的视觉方案，后面所有的页面都必须遵循。
第五个skill，vibe-prototype，产出一批原型，落在 prototypes/ 这个文件夹里。
到这一步，前面的交互和视觉都定死了，该把它们变成一张张能看的页面了。
AI 原型图，现在大多 Vibe Coder 的做法都是跳过这步，直接生成页面。
结局就是，AI 产出的内容丑、交互逻辑完全混乱。很难产出能用的页面。
所以这个 Skill 的目标，就是产出交互明确、样式高级、审美惊艳的前端设计页面雏形。
这时候，前面的 vibe-interaction 产出的那个很详细的交互文档和 vibe-design 产出的视觉规范文档，就需要放进来了。
这个 vibe-prototype 会根据前面的设计为每个页面（细化到弹窗、子页面等）构建明确的发给 AI 的提示词，存在 prompts 文件夹里面。
接下来，就是产出原型了。
打开 Google Stitch。传入我们之前下载的 Cursor 的 DESIGN.md。选择 Gemini 3 Pro 模型。
这一步其实就是把视觉规范确定好。
这时候画布里就会是这样。
接下来，就是把刚刚产出的每个页面的 prompt 传给 Stitch，让他生成各种页面的原型。
最后，把所有原型下载下来，放入 prototypes/ 文件夹。
告诉 Agent 你已经产出了一整套原型。这时候，它会把所有的页面和原型对齐！
把对齐的标准存放在 prototypes/manifest.json 这个文件里。
这样，所有的页面和原型，都对齐了。
后面咱们实现的时候，就严格按照这个原型进行实现。
所以这个 skill 做到的就一句：你眼睛看到的原型，跟最后跑出来的产品，长得一模一样。
高级、稳定、标准。
第六个skill，也是最后一个，vibe-implement。到这儿，才真正开始写代码。
这个步骤，就是把刚刚我们完成的，对齐的交互、对齐的设计、对齐的页面、对齐的技术栈，进行代码实现。
这里面我也引入了 Harness Engineering 的方法，这里不详述。
我觉得有必要说的是，这个严格的 skill 中有始终在上下文的检查流程，它的目标就是做两件事：
不许多，代码里不准冒出文档里没有的东西；
不许少，文档里写过的每一个交互，都得在代码里落地、一条条核销掉。
一个不多，一个不少。
说白了，目标就差一个字：把"实现≈设计"，收紧成"实现=设计"。
所以等这个 skill 跑完，我敢拍着胸脯说一句：跑出来的，就是我当初设计的那个，一处没走样。
等这六段全走完，恭喜你，可能你的那个idea，已经出现在了屏幕上。
这套 Vibe Coding Skills，想解决的，不是快速实现。而是审美不走样、不返工。
它觉得它的灵魂，就一个词。
对齐。
来回看一下，怎么做到的从 idea 到 code，具有高级审美、明确技术栈、严格对齐的产品实现的。
这几个 skill 的配合是：
idea 想清楚做什么，interaction 把每次点击定死；
architecture 反推技术骨架，design 钉死视觉；
prototype 合出对齐的原型，implement 照着落成代码，一个不多一个不少。
最后，说说打磨这套 skill 的心路历程。
这六个 skill 理解越深入之后，我越清楚地看见一件事：
AI 把活儿干得越严丝合缝，我们应该越是把"我到底为什么要干这件事"这一句，仔细想清楚。
它能把你文档里写过的每一个交互，一条条核销到不多、也不少。可"这东西到底为什么要做、做给谁、解决他哪一个具体的难处"，就这一句，它答不上来，也永远答不上来。
所以，为什么第一个 Skill 是 idea，以及，我为什么这么强调 “对齐”。
对齐这个词。就是核心思路。
软件工程的人几十年前就把它写进教科书了。叫契约式设计，Design by Contract。
名字唬人，讲的都是同一件朴素的事：动手之前，先把"要做什么、谁对谁负责"，说到不留一丝歧义。
这套 Skill 的核心就是把这两样老掉牙的东西，从那个还没有 AI 的年代，原原本本搬回 2026，又重新讲给 AI 听了一遍。
既然"实现"这道门槛，AI 已经能帮你一脚踏平，那这套 Skill 就是把它彻底拆掉，让每一个心里揣着个想法、却一直被"我不会写代码"这五个字挡在门外的人，都能自己动手，把那个东西真的做出来。
