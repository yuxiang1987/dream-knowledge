# 公众号流水线多Agent化改造评估

本页是对一个具体问题的评估：现有公众号工作流 Skill（见 [[topics/公众号Skill流水线设计]]）改造成多 Agent 协作，会不会更好、难度在哪、改完是否更方便。

结论先给：**不建议整体改造，建议只改两处。** S1 选题改成「多个只读子代理分头搜集来源、一个主代理汇总取舍」，S4 定稿检查改成「多个检查代理分头查不同层、主代理合并成一份报告」。S3 写稿、S2 实测、S5 排版、S6 入库保持现在的单代理顺序执行。人工关口一个都不动。

原因不是「多 Agent 不行」，而是这条流水线的瓶颈不在并行度上：它最慢的一环是作者亲自实测（S2 硬关口），这一环无论几个代理都并行不了；而最能从中获益的两处恰好是搜集与检查，它们天然可拆。

## 评估依据

- **知识库既有拆解**：[[sources/Buzz多Agent协作文章拆解]]、[[sources/苍何Hermes多Agent军团文章拆解]]、[[sources/EvoX蜂群与经验复用文章拆解]]、[[sources/小林GraphEngineering文章拆解]]、[[sources/豆包Seed-Evolving实测文章拆解]]。
- **本账号流水线现状**：`gzh-daily-pipeline` 七阶段 S0–S6、四个人工关口、S2 硬关口、文件契约交接、脚本验收，详见 [[topics/公众号Skill流水线设计]]；最近一次真实运行产物在 `E:\work\wechat-assistant\pipeline\2026-10-24-WorkBuddy设置`，其中 `01_选题卡.md` 与 `03_证据与实测.md` 是本评估的对照样本。
- **本次会话实测**：用 omp 的子代理能力做了三轮只读探针，见下节。探针不修改任何文件、Skill 或配置。
- **尚未量化的部分**：多 Agent 的协调成本在本账号链路上没有数字，见「未验证项」。

## omp 已具备的多 Agent 能力（本次核实）

| 能力 | 实证方式 | 结论 |
| --- | --- | --- |
| 批量派发子代理 | `task` 批量调用，一次派 2 个 | 两路同时运行，墙钟 8 分 8 秒与 12 分 30 秒 |
| 子代理可做外部检索 | 只读子代理调 `web_search` 3 次并开页面核对 | 可用，返回非空结果，无工具报错 |
| 子代理可读本项目 Skill | 读 `skill://gzh-topic-planning` | 可用，frontmatter 与正文结构完整 |
| 子代理可读工作区产物 | 读 `E:/work/wechat-assistant/pipeline` | 可用，8 个阶段文件全部可见 |
| 分角色、分模型 | 内置 `scout`／`task`／`reviewer`／`sonic`，可按角色配模型 | 可用；`scout` 跑更快更便宜的模型 |
| 结构化产出 | 任务可带输出 schema | 可用，候选可按固定字段回收 |
| 人工介入与观察 | Agent Hub（`Alt+A`）看运行中子代理、看转写、接管、杀掉 | 可用；子代理运行中主代理也能发消息纠偏 |
| 项目级自定义 Agent | 项目 `.omp/agents/*.md` | 可用；本项目当前没有该目录 |
| 隔离工作区、worktree、DAG 编排 | 文档存在 | 本流水线用不上：产物是文件不是代码分支 |

实测细节（2026-10-26，只读）：

1. **能力探针**：一个子代理确认 `web_search`、`skill://` 读取、工作区绝对路径读取三项全部可用，均无报错。
2. **S1 选题并行探针**：派两个子代理，一个只做「官方产品变化」类外部检索，一个只做「库内旧文延伸与作者实践」类内网梳理，各自按 `gzh-topic-planning` 的约束输出候选。结果：外部那路产出 6 条官方变化线索（每条带来源链接、发布日期、官方原文要点与待核项），内网那路产出 2 个可执行候选（带证据锚点、素材缺口、最小试跑与退路），并主动把一条方向降级为「暂缓」，理由是原项目路径在本机已不存在。
3. **边界表现**：两个子代理都没有凑满来源、没有编造读者评论、没有把官方宣称写成作者亲测成功；内网那路还主动区分了「对方读者的评论」与「本账号读者需求」。这与 [[topics/证据与边界库]] 的要求一致。

## 逐阶段可拆性

| 阶段 | 能否并行 | 判断 | 依据 |
| --- | --- | --- | --- |
| S0 定盘 | 否 | 单点基准，拆开只会产生多个互相冲突的基准 | [[topics/公众号Skill流水线设计]] 约定全流程唯一基准 |
| S1 选题 | **是** | 六类来源互相独立，每类可交给一个只读子代理；汇总与取舍由主代理做 | 探针 2 已验证两路并行产出可用候选 |
| S2 案例与实测 | 部分 | 素材与提示词准备可并行；**实测本身不可并行也不可代理** | 硬关口是作者亲测，助手不代填 |
| S3 写作 | **否** | 单一作者口吻与一条证据链需要同一个人格一次写完 | [[sources/Buzz多Agent协作文章拆解]]：创造类工作只定方向；多份草稿拼接会掉口吻 |
| S4 定稿检查 | **是** | 四层检查互不依赖（禁用词／标点／句式／活人感），加事实边界与媒体完整性，可各查一层 | [[sources/Buzz多Agent协作文章拆解]]：写代码的不能自己验收；当前单代理自写自查正是这个毛病 |
| S5 标题封面排版 | 不必 | 排版是确定性脚本，封面是一次生图，标题收益本就小（不强制多版） | [[topics/公众号Skill流水线设计]]：排版只翻译格式 |
| S6 发布与回流 | 否 | 要改同一批知识页并保持交叉引用一致，并行写会互相覆盖 | 同上：多处更新的归属判断需要单一决策者 |

## 难度分级

| 改造点 | 难度 | 具体要做什么 | 主要风险 |
| --- | --- | --- | --- |
| S1 分来源并行搜集 | 低 | 在 `gzh-topic-planning` 增加「派子代理分头搜集」环节；子代理只读，回产物落成文件；主代理汇总比较 | 子代理各说各话，主代理合并时要保留每条来源与日期，不能只留结论 |
| S4 分层并行检查 | 中 | 在 `gzh-final-check` 增加「按层派检查代理」；合并去重成一份报告；**改稿授权仍归作者** | 报告变长容易淹没必须修改项；合并逻辑写不好会漏项或重复计数 |
| 调度者角色 | 中 | 主代理固定当唯一调度者，不让子代理互相派活 | [[sources/Buzz多Agent协作文章拆解]]：协调 Agent 站在指挥链上，它就是瓶颈 |
| 项目级自定义 Agent | 低 | 建 `.omp/agents/` 写角色定义（选题搜集、检查分角色） | 角色定义与 Skill 职责重叠，日后容易两处都改、只改一处 |
| 阶段产物契约 | 中 | 并行产物要落成文件而不是留在对话里 | 留在对话里就退回协调者瓶颈，且断点续跑失效 |
| S3 写作多版本并行 | 高且不建议 | — | 拼接口吻不一、证据链断裂，且与「不强制多版」的现行决定冲突 |
| S2 实测代理化 | 不可做 | — | 越过「作者亲测」硬关口，破坏整套证据纪律 |

## 改完会更方便吗

分环节看，不是一个统一答案。

**会变方便的：**

- 找选题：候选来源更宽，热点与官方变化不必靠单次会话内的记忆。探针里两路并行 12 分半出候选，比单代理串行做同样两路更快。
- 查问题：S4 交给没写过这篇稿子的检查代理，四层检查各查各的，比现在自写自查更容易发现作者视而不见的问题。库内已有同向证据：验收方与执行方必须分离。
- 人工关口的确认对象变清楚：作者看到的是结构化候选表和分层问题清单，而不是一段散乱的讨论。

**不会变方便的：**

- 写稿：仍是一个代理一次写完，多代理只会破坏口吻。
- 实测：这是整条链路的耗时大头，多代理帮不上。
- 发布与入库：保持人工。
- 总体成本：多跑几个模型要多花钱，[[sources/DeepSeek原生Harness文章拆解]] 与多 Agent 类样本都提示协调、转发与重复读文件会抵消收益。

**人机协作的实质改善点**：不是自动化更多，而是把「作者要确认什么」变成结构化文件。前提是子代理产物必须落到流水线目录里的阶段文件，否则这套改造只剩协调负担。

## 建议方案

只做两处，保持其余不动：

1. **S1 加并行搜集**。`gzh-topic-planning` 在「收线索」一步按来源类别派只读子代理（可复用现有 `scout` 角色，走更便宜的模型），每个子代理只交一份线索卡，落到流水线目录的临时线索文件；主代理读全部线索卡后做取舍，写 `01_选题卡.md`。人工确认选题这一关保持不变。
2. **S4 加分层检查**。`gzh-final-check` 在检查阶段派若干检查代理分别查禁用词、标点、句式、活人感、事实边界与媒体完整性，各交一份发现，主代理合并去重为 `05_检查报告.md`，「必须修改」清零这一关保持不变。

配套三条约束：

- **主代理是唯一调度者，也是唯一写稿者**。子代理之间不互相派活，避免协调者瓶颈。
- **子代理只读不写流水线主产物**。并行产物一律落成独立文件，由主代理写正式阶段文件。
- **子代理结论必须带来源与时间**，主代理汇总时保留来源，不允许只留结论。

试点方式：从两个 Agent、一个小任务开始，跑通了再加角色——这是 [[sources/Buzz多Agent协作文章拆解]] 里作者自己给的建议。

## 风险与红线

- **不要动 S2 硬关口**。助手不代填实测、不把策划预期写成结论，是这套流水线的底线，多代理不构成放宽理由。
- **不要用多代理去凑候选数量**。S1 仍限至多 3 个候选、推荐 1 个。子代理交上来的是线索，不是票数。
- **不要让子代理改稿**。定向改稿与「其他不要动」的授权边界仍由作者给出。
- **并行度别开高**。[[sources/豆包Seed-Evolving实测文章拆解]] 记录过十个 Agent 并行造成堵塞、中断变多。
- **协调成本目前没有数字**。见下节。

## 未验证项

- **协调成本无法量化**。本账号链路上「多跑几个代理」相对「单代理串行」的 token 差、墙钟差与人工介入次数都没有实测记录。[[topics/选题问题库]] 里「协调成本能否量化」本来就是待验证选题，本页把它落到本工作流上。
- **探针规模小**。只验证了两路并行、只覆盖 S1 的两类来源；S4 分层并行没有实跑，合并去重规则尚未写出来也尚未被检查。
- **不构成对成本的预测**。本评估没有任何 token 与费用的实测数字，不据此推断发布节奏或收益。
- **S1 候选质量未经作者判断**。探针产出的候选是否真的值得写，只有作者能定。
