# 测评问题与实战技巧库

> 收录约定：路人甲TM 的条目不再重复标注作者；其他作者的条目以「作者名：」开头。跨作者的统计结论要等样本量足够后单独成页。

本页记录**问题 → 针对性任务 → 观察点 → 失败与调整 → 结论边界**。它补充 [[topics/AI写作案例库]]：案例库回答「可以做什么任务」，本页回答「为什么做这个任务、重点测什么、失败后如何再测」。当前只提取了 [[sources/Qwen-Image-3实测文章拆解]] 的内容，不能把作者一次测试后的感受当成稳定效果。

## 本篇提取的测评链条

| 具体问题 | 作者怎样测试 | 文中观察与调整 | 可借鉴的技巧 | 还不能推断什么 |
| --- | --- | --- | --- | --- |
| 生图中文字会乱码或模糊，中文复杂字尤其难 | 用三国、汉服、动物、行星、茶等高文字密度信息图；部分任务与 Image2 用同样提示词 | 汉服图小字模糊；作者在提示词末尾追加「避免：画面模糊，文字模糊或崩掉」后称文字改善 | 把字形准确度列为独立验收项；失败后针对性补约束，再保留前后结果 | 没有重复次数与错字统计，不能说这个短句必然提高成功率 |
| 图像精致却过度锐化，文字背景反而不清楚 | 用同题材三国信息图比较 Image2 与 Qwen-Image-3.0 | 作者认为 Image2 人物偏硬、细节过多，Qwen 图更清楚；也承认两者风格各有特色 | 把**画面审美、文字可读、整体信息层级**分开评价 | 图片未在本库核看，不能判定两模型普遍优劣；原文未给系统样本 |
| 长输入能否保持清楚的知识结构 | 把约 3500 字《人类简史》摘要交给生图模型做「一图读懂」 | 首轮几次革命混在一起；第二轮指出具体结构问题后称结果清晰 | 修改时既说「哪里错了」，也说「希望怎样组织」；核对关键层级和遗漏 | 单篇书摘与两轮尝试不足以证明长上下文能力上限 |
| 海报能否在短要求下自行补全设计 | 做城市宣传、虚构品牌电商和耳机爆炸海报 | 作者喜欢促销标签的别针细节与耳机自动命名，但城市海报更偏好 Image2 | 先给对象、用途、必备文字和感觉，再看模型自动补出的细节是否有用 | 惊喜细节不等于品牌准确、商品结构正确或适合正式投放 |
| UI 图是否能辅助产品构思 | 为同一知识库 App 生成首页、课程、我的三页 | 作者认为视觉一致、功能较完整 | 测多页风格和导航一致性，别只测单张漂亮首页 | 静态设计图不能证明页面可点击或产品已经实现 |
| 分镜里人物看着一致，动作却不连贯 | 用故事脚本生成宫格分镜，逐格看人物、时间和空间关系 | 首轮出现眼睛、人物变形，以及镜头 05 趴地、06 凭空腾起；作者追加避免瞬移／悬空的限制并细化关键动作 | 分开检查**角色一致性**与**动作连续性**；把出错的相邻两格当成修正目标 | 原文未给完整初始与修改提示词，也没有多次成功率统计 |

## 原文中可读到的提示词片段

| 片段 | 原文用途 | 如何保存和使用 |
| --- | --- | --- |
| 「避免：画面模糊，文字模糊或崩掉」 | 汉服拆解图小字模糊后追加的反向提示 | 这是**原文片段**，不是完整提示词。下次测试可把它作为一个变量，比较加与不加的结果，记录样本数和错字情况 |
| 「避免违反物理规律，比如猫在空中停滞、瞬移」 | 宫格分镜动作跳跃后的反向约束 | 这是**原文举例**，实际使用应改成当前角色、动作和镜头关系，并配合正向关键动作说明 |

原文的动物科普、汉服拆解、长文图谱等完整提示词主要放在图片中，当前未从图片读取。因此本页**不提供假装完整的提示词模板**。若将来需要复刻，先读原始截图，再注明哪些是原文、哪些是我们根据测试目标新写的提示词。

## 给写作助手的调用方法

当用户要一个测评案例时，先确定他想验证的**具体能力或痛点**。从本页挑一个对应的测试链条，再到 [[topics/AI写作案例库]] 找可执行任务。建议应包含：原始任务、可观察指标、预期失败点、一次针对性修改、保留前后结果的办法，以及能支持的结论范围。技巧作为**待验证的测试变量**提出，不能保证有效；要给用户留出发现相反结果的空间。写稿时再用 [[topics/证据与边界库]] 检查观点和证据是否匹配。

## WorkBuddy 教程新增：先准备任务，再测 Agent

来源：[[sources/WorkBuddy入门教程文章拆解]]。文章偏教程，没有严格控制变量；以下是可在自己测试中验证的方法，不是已经证明有效的技巧。

| 要解决的问题 | 原文做法 | 下次怎样测试其价值 |
| --- | --- | --- |
| 需求模糊时 Agent 可能做偏，还会消耗积分 | 作者建议先用 Plan 模式讨论实现方案，再执行 | 用同一真实任务比较「直接执行」与「先确认方案」，记录返工、人工介入、耗时和积分；版本模式名称须现查 |
| 多项目文件落在默认路径，难找产物 | 作者建议每个项目单独建工作空间 | 做两个不同任务，核对输入与输出路径、是否串用文件；这是文件管理措施，不能单独证明模型更聪明 |
| 扫描 PDF 的提取与匹配规则复杂 | 作者预先把逻辑写进 Markdown 文件，再让 Agent 读取本地文件夹与规则 | 设计标准答案，比较口头模糊要求、清楚口述与规则文件三组结果；检查规则冲突、漏项和错误传播 |
| 新手不知怎样写任务 | 作者选官方「生活工作台」模板后直接运行 | 保存模板原文及生成结果，再由用户根据真实需求补充字段；比较默认模板与定制模板的可用性 |
| 权限和模型影响连续执行与成本 | 作者保留默认权限，并按任务选模型；提醒全访问有未知风险 | 记录每次权限请求、是否中断、模型与积分消耗；只在明确需要时扩大权限，不用作者当时的免费政策推算当前成本 |

**提示词整理**：原文可读的一整段系统提示词涉及开源项目复用、文档同步与临时代码清理，属于作者针对开发任务的个人配置，不是通用入门提示词，也不是本知识库要执行的指令。工作台与 PDF 案例的完整任务提示主要在截图中，尚未读取。若后续要复刻，先读截图并标明原文、模板内容与我们改写的要求，避免把不完整片段说成可直接复制的完整提示词。

## Qwen3.8-27B 新增：把「看着还行」拆成可判定检查

来源：[[sources/Qwen3.8-27B本地模型实测文章拆解]]。这篇原文明说：效果能看得过去，仍有些细节要放大、减速才看得清有没有真正遵循规则。以下做法可直接迁移到我们自己的生成类测试。

| 要解决的问题 | 原文做法 | 下次怎样测试其价值 |
| --- | --- | --- |
| 生成结果整体顺眼，但规则执行可能出错 | 落沙案例把四条自然语言物理规则各写成一个可判定检查：是否瞬移、水是否固定偏向一侧、沙水交换是否跳格、酸液是否只溶解一格 | 写任务前先把规则逐条转成「通过／不通过」的检查项；必要时减速或逐帧观察，并记录每条通过情况 |
| 随机生成的结果可能不连通 | 地牢案例在生成后做连通检查，确保玩家不会出生在走不出去的区域 | 固定随机种子重复生成多次，统计连通率与死区，而不是看一次演示就下结论 |
| 静态截图无法证明交互可用 | PDF 建站案例逐项描述筛选、详情弹窗、购物袋与总价 | 交互类任务必须实际操作并录屏；截图只能证明版式，不能证明功能 |
| 榜单分数容易被当成本篇能力依据 | 原文用 AA 榜单分数与同分说法建立期待 | 分数只作背景。正文里的判断必须来自本次任务的检查结果，并写明测试环境与量化版本 |
| 运行成本容易被忽略 | 作者自述几小时跑完三个案例、部署过程踩坑 | 记录部署耗时、运行耗时、硬件或云服务规格与费用；报「一次产出」时同时报耗时 |

## Buzz 新增：多 Agent 协作里的四道关口

来源：[[sources/Buzz多Agent协作文章拆解]]。以下方法来自作者两次翻车后的调整，未做对照实验；换平台或换任务结构时需要重新验证。

| 要解决的问题 | 原文做法 | 下次怎样测试其价值 |
| --- | --- | --- |
| 让协调 Agent 统筹会全员等待 | 作者先让 Claude 总指挥，频道停滞；后改为「主节奏由人控制，Claude 只做问询台」 | 同一任务分别用「Agent 统筹」与「人控节奏」跑一遍，记录停滞次数、人工介入次数与总耗时 |
| 全自动接力会跳过人工确认点 | 自动接力时前端还没预览，后端就开工，改动要两端同步，返工成本高 | 明确标出必须人工确认的节点并写进流程；对照「不设确认点」的结果与返工量 |
| 写代码的 Agent 自己验收不可靠 | 作者让未参与编码的 Agent 逐条对照需求文档、启动服务调接口、检查空数据与重启后数据留存 | 验收方与执行方分离；验收项来自需求文档而非实现过程，并保留检查报告作为证据 |
| 系统级约束写不清会导致静默失败 | Agent 能回答但频道看不到；作者把「唯一有效回复方式是执行指定命令，频道与事件 ID 必须从当前 Context 读取」写成最高优先级指令 | 把平台机制类要求写成明确禁令与必做动作，并声明失败时的重试与上报方式；同时记录同期平台版本变化，避免把修复全部归因于提示词 |

**一条来自原文的提醒**：作者明确写出修复「也可能是因为 Buzz 中间的更新修复了bug」。写这类排查结论时保留这种不确定性，比直接宣称提示词解决了问题更可信。

## Pixmax 新增：视频生成的提示词与成本控制

来源：[[sources/Pixmax修仙短剧文章拆解]]。原文带明显推广特征，但制作方法部分可迁移；效果与成本数字均未独立核实。

| 要解决的问题 | 原文做法 | 下次怎样测试其价值 |
| --- | --- | --- |
| 一段里出现多个状态，模型把它们混在一起 | 把 15 秒拆成四个阶段，逐段写死时间点、动作与光影变化（靠拢成核→压缩成旋涡→短暂静止声停→光波扩张→稳定成穹顶） | 先写秒级阶段表再生成；对照「只写整体效果」与「逐秒约束」两组的返工次数 |
| 多张参考图互相污染 | 标明每张图职责：前两张固定宗门地形与建筑，第三张只固定弟子外形，第四张只参考灵树特效且不使用其中建筑 | 用同一段做有／无逐图职责说明的对照，检查是否出现把不想要的元素搬过来的情况 |
| 已知易错点反复出现 | 写具体禁止项：不炸毁楼阁、不产生火球、不持续闪白、不额外长手、不变成石像 | 把每次返工的原因追加进禁止项清单，形成自己的负面约束表格，并记录新增条目是否减少同类返工 |
| 连续动作靠提示词说不清 | 改用 3D 导演台先摆动作再生成；用白模跑动作并导出参考，驱动非人形角色 | 同一镜头分别用纯提示词与动作参考各做一次，比较动作连贯性与返工次数 |
| 成本说不清 | 记录六段共 1584 积分与折算金额，并给出另一版本按分辨率的每秒单价 | 建立自己的记账表：积分数、折算金额、模型版本、分辨率、镜头时长、返工次数；报成本时同时给口径 |

## Image2.5 新增：把「像不像」拆成三件事

来源：[[sources/GPT-Image2.5草图生图文章拆解]]。以下做法用于生成类功能的验收设计。

| 要解决的问题 | 原文做法 | 下次怎样测试其价值 |
| --- | --- | --- |
| 生成结果好看，但不确定是否照做 | 画板中把龙画在正中，成片里龙确实居中；换童趣风格后太阳与小鸟仍在草图位置 | 把「位置与元素是否被遵守」和「画面好不好看」分成两个评分项，先判遵守再判审美 |
| 自动补全难以评价 | 指出模型补了草图里没有的蓝天白云、山崖城堡，品牌案例中还补了提示词未提到的交通工具与软件 UI | 每次生成后单列「我要求了什么／它自己加了什么」，判断补充是否与目标冲突 |
| 同类功能在不同端表现不一致 | 记录只有手机端会直接给出合成好的 GIF，网页端行为不同，桌面端未找到入口 | 结论必须带端、版本与入口路径；换端后重新验证，不沿用另一端的结论 |
| 两代对比在小样本下看不出差异 | 作者如实写下差距不大，给出样本量与场景的解释，再引用官方大批量样本 | 先报样本量再报结论；用「本次未观察到差异」替代强行寻找胜负，必要时补足样本 |
| 耗时被忽略 | 提醒不要直接让模型生成动图，否则会出现一次生成十几张图、速度极慢 | 先明确交付物形态（静态图还是动图），把模型可能选择的耗时路径写进限制条件 |

## DeepSeek Harness 新增：对比设计与故障处置

来源：[[sources/DeepSeek原生Harness文章拆解]]。以下方法可直接迁移到我们自己的工具对比测试。

| 要解决的问题 | 原文做法 | 下次怎样测试其价值 |
| --- | --- | --- |
| 想比较工具对结果的影响，变量太多 | 固定同一个模型，只替换三种 Harness 做同一任务 | 明确写出固定了哪些变量（模型、提示词、起点）与未固定的条件（机器、网络、推理强度）；每个组合重复至少两次 |
| 模型陷入重复动作的循环 | 出现反复执行同一占位动作，思考里提示应换动作却回到原处；作者终止任务并追问原因，随后模型改用文件系统路径完成 | 发现连续几次相同操作就先终止；追问原因后给出替代路径。把这条写成自己的处置流程，而不是等它自恢复 |
| 工具安装容易卡在环境上 | 给出一条完整指令：核对包信息、检查运行时环境、安装最新版、启动界面、用 HTTP 请求验证可访问、回报版本与启动命令 | 把「装好并自证可用」写成一条可复用指令；验证步骤必须是外部可观测的（如 HTTP 检查），不是模型自称完成 |
| 判断自定义 Agent 值不值得配 | 对照标准模式，指出自定义的优势只在重复使用时显现 | 用同一任务跑标准模式与自定义模式各一次以上，比较首次配置成本与后续每次节省的时间 |
| 权限设置被忽略 | 作者把工作区权限改成完全放开，只留一句自嘲 | 记录权限档位、放开后允许的操作范围与恢复方式；能完成任务的前提下优先用更小权限，并在文中说明 |

## 天才机甲师新增：长篇视频的一致性控制

## DSH 插件新增：一段防越界的执行约束

来源：[[sources/DSH插件市场文章拆解]]。作者因模型自行推进而返工，随后写出下面这段约束并附加到每条指令末尾，过程明显顺畅。这是本库最有复用价值的提示词之一，原文如下（保持原样，便于直接取用）：

```
【执行约束 - 必读】1. 边界：只做我明确要求的事，禁止主动扩展范围、添加"顺手就能做"的改进、实现我未提及的功能。任何超出指令字面意思的动作都算越界。2. 确认：遇到歧义、多个可选方向、或任何需要拍板的决策时，先停下来用简洁的选项问我，禁止用"推荐选项"或你自己的判断替我做决定。我说"先别急/先讲方案"时，必须停手，只输出方案和影响，等我批准才动手。3. 节奏：分步推进，每完成一步先汇报结果和下一步计划，等我确认再继续。禁止一口气做完整条流水线。4. 验证：引用任何模式/方案前，先验证当前环境是否支持（服务清单、依赖机制、运行行为）。测试必须贴近真实运行，mock 与真实行为不一致时不得当作通过。5. 提问优于猜测：不确定就问，不猜。你的每一个假设都要说出来让我确认，而不是闷头执行。6. 如果你认为指令有更好的做法，用一句话提出建议并说明理由，然后等待我的决定——不得直接采用。
```

| 要解决的问题 | 原文做法 | 下次怎样测试其价值 |
| --- | --- | --- |
| 该停没停，一口气做完整条流水线 | 约束第 2、3 条要求遇歧义先问、分步推进并等确认；作者的问题正是「只问了一句却被做完了第一版」 | 用同一个多步任务跑对照：不加约束／加约束各一次，统计越界与跳步次数 |
| 主动加「顺手就能做」的改进 | 约束第 1 条把超出字面意思的动作直接定义为越界 | 记录未经要求的新增文件、功能与依赖数量，看是否下降 |
| 假设没说出来就执行 | 约束第 5 条要求不确定就问、假设要讲出来 | 检查回复里是否出现「我假设……」；没有则补充询问 |
| 引用不存在的环境能力 | 约束第 4 条要求先验证当前环境是否支持，并禁止用与真实不一致的模拟当通过 | 记录因环境不支持导致的失败次数；测试结论必须来自真实运行 |
| 有更好做法却直接采用 | 约束第 6 条要求先说明并等待决定 | 检查是否出现「未经同意就换方案」；这类改动最容易打乱原有节奏 |

| 不会写提示词 | 建议先与目标工具或别的模型沟通清楚，或找一支优秀视频让模型反向拆解成提示词 | 试一次反向拆解：把拆解结果作为初稿，再按自己的需求改 |

## Astra 演示汇总新增：第三方素材的引用纪律

来源：[[sources/GPT-6-Astra演示汇总文章拆解]]。这一篇自己没有实测，价值在于把「不能实测时怎么写」示范清楚了。

| 要解决的问题 | 原文做法 | 下次怎样测试其价值 |
| --- | --- | --- |
| 素材是别人的演示，容易被读成亲测 | 开场即写「我们现在还用不上」与「这篇文章暂时做不了实测，我先把公开的功能和流出的演示逐个看一遍」 | 无法实测时在开头写明性质与素材来源；定稿前再检查一次有没有段落读起来像亲测 |
| 演示结论互相矛盾 | 作者发现两模型对比帖结论完全相反，遂不发布对比 | 引用比较结论前先核对提示词、工具、运行环境与人工修改四项条件；缺项就只描述并存的说法 |
| 高冲击力说法缺出处 | 文中转述「内部版本推进了十个数学问题」「成本约两千美元」等信息 | 这类说法注明「官方公布」或「有说法称」并补时间；自己写时优先找一手材料 |
| 演示耗时被当普遍速度 | 十五分钟、不到一小时等来自演示者 | 转述时加「演示者称」；自己复测后另附条件与耗时 |
| 情绪标题与克制判断的张力 | 标题写「真实效果太夸张」，正文承认下结论太早 | 标题可保留情绪，但正文必须有对应的收敛判断，两者要在同一篇里对齐 |

## 出海转绘新增：多层验收与关键节点

来源：[[sources/Seko出海转绘文章拆解]]。这一篇给出了「哪一步不能错、哪些必须保留、哪些必须人来决定」的完整划分。

| 要解决的问题 | 原文做法 | 下次怎样测试其价值 |
| --- | --- | --- |
| 结构错了后面全歪 | 逐镜拉片后先不确认，在分镜表上人工调整；作者强调所有后续都建立在这份拉片上 | 把结构确认设为强制节点：镜头编号、时长、机位、切点逐项核对后再进入生成 |
| 一致性无法量化 | 用「空间拓扑锁定」解释：换材质与文化符号，但空间结构不动 | 改版前后逐项核对物体位置与朝向；用空间清单代替「看起来差不多」 |
| 只验证了一层就下结论 | 作者只确认了三版镜头顺序、时长、机位、切点一致，未评画面细节与语言自然度 | 把验收拆成三层：镜头结构、画面细节、语言与表演，分别给结论 |
| 设定改动缺少理由 | 北美版把无限回档改成有能量上限、冷却与损耗的机制，并给出受众心理上的解释（不接受无代价超能力） | 记录每处设定改动的理由；没有理由的改动要单独标出复查 |
| 后续阶段静默偏移 | 裂变方案自带禁止改动清单，锁定主角身份原型、机制定位与高潮选择权 | 长流程项目开工前先写不可变项清单；每次阶段性交付后回查是否被改动 |
| 工具决定不了投放 | 作者明确「它能给你两套方案，但哪套更适合你的内容、你要投哪个平台、那边的观众吃不吃这一套，这些它决定不了」 | 把市场选择列为人工决策项，不写进工具的验收标准 |
