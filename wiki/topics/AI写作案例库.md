# AI写作案例库

> 收录约定：路人甲TM 的条目不再重复标注作者；其他作者的条目以「作者名：」开头。跨作者的统计结论要等样本量足够后单独成页。

本页收集的是**怎样设计和讲述可检验的任务**。原作者声称的产品表现不能直接用于我们的文章。用于新稿前，必须确定自己有相应材料、工具权限、时间和可展示的产物；没有亲自做过的任务只能写成「计划测试」，不能写成实测。单篇细节见 [[sources/百度搭子三道题文章拆解]]、[[sources/GPT-6-Astra连测文章拆解]]。

案例要和明确的测评问题配对。针对性测试、失败后的调整和可读到的提示词片段见 [[topics/测评问题与实战技巧库]]。

## 案例卡片的筛选字段

每个候选案例至少回答：**要解决谁的什么问题、起点材料是什么、让工具做什么、怎样判断成败、能留下什么证据、需要多少时间与成本、哪些条件会让它不适用**。缺少关键材料时，不把它推荐为可立即写的案例。

## 可直接借用的测试卡：可拖拽布丁／果冻

**来源中的具体创意**：作者想要「外形像布丁，质地很通透」，拖动时变形，松手后弹回，再晃几下逐渐停住，呈现「duang duang」的感觉。作者对产物的描述包括圆润饱满、拉扯时有软弹性、整块一起晃，以及参数可调。以上是原文文字描述，视频画面未在本库核看；也不知道作者给模型的完整指令。

**我们下次实测可采用的任务**：让待测模型制作一个能在浏览器运行的单物体交互原型。页面中心放一个半透明、圆润的布丁状物体；鼠标或触摸拖动时形体随拖拽方向变形；松手后回弹，出现逐渐衰减的整体晃动，最后稳定。提供至少两个可见的调节项，例如弹性强度与晃动衰减，并让调整即时生效。这是根据原文创意整理的*新测试要求*，不是原作者的完整提示词。

**验收点**：①能打开并操作；②外形圆润、呈现一定通透感；③拖拽会造成连续变形，而不是整个物体平移；④释放后回弹，有可见的衰减过程，最终停止；⑤主体整体运动，不出现明显撕裂或失控旋转；⑥调节项确实改变运动表现。录下同一套动作，并保存代码、运行环境、模型、提示词、迭代次数、用时和额度消耗。

**比较方式与边界**：比较多个模型时，使用同一初始要求、相同运行环境和相同的首次交付机会；若允许迭代，另记迭代后的结果。视觉「想不想上手玩」属于主观评价，可让读者看录屏，但不能替代可操作性和回弹行为的检查。只凭这一例也不能概括模型整体编程能力。

**用于写作的切入点**：一个看似简单的「duang」效果，实际同时考验视觉表达、交互逻辑和动态手感。文章可按「我想要什么感觉 → 怎样把感觉写成可检查的要求 → 首次结果哪里不对 → 调整后怎样 → 哪个模型更接近目标」推进。只有真正完成测试并保存结果后，才能写成第一人称实测。

## 其余七个案例的具体测试卡

以下各卡先保留原文里的**具体做法**，再给出我们下次可采用的**改编任务**。改编任务只是建议，不能写成已经发生的测试。

### 1. 跟完整场活动，交付一套内容成果

- **原文做法**：作者让百度搭子自行找到发布会直播间，持续记录和整理，最后交出回顾视频、产品升级长图、嘉宾金句海报、新闻稿等内容。文中称任务约跑四小时、交付七项；其中产品长图末尾有字体重叠。来源：[[sources/百度搭子三道题文章拆解]]。
- **可改编任务**：选择自己确有观看或使用权的一场公开活动，先列出交付清单，例如一页要点、一条短视频脚本、一张时间线和一篇简报。让工具长时跟踪，并记录人工接手的每一次操作。
- **验收与适用条件**：核对关键事实、时间线、素材引用、内容完整性和排版；保留原直播、任务记录和全部产物。适合有真实活动与明确交付需求的题材，不适合只想测短问答的文章。类似案例可换成公开课程、产品演示或一场线上讲座，但每种素材的可用权限都要确认。

### 2. 一个选题走完自媒体内容链路

- **原文做法**：作者以「大一新生如何选择 AI 产品」为题，让工具调研，再生成公众号、小红书、视频脚本和封面等素材；自己在选题与产出后继续选择、修改、核验。来源：[[sources/百度搭子三道题文章拆解]]。
- **可改编任务**：拿本账号近期真的要写的一个选题，要求工具先给资料来源和角度，再交文章大纲、各平台版本、封面文案与短视频脚本；人工记录每一步要修改什么。
- **验收与适用条件**：比较各版本是否针对平台重写、事实是否有出处、作者实际修改耗时，以及最终能否发布。必须有真实选题与目标读者。类似案例可改为「一篇长文变成邮件、短帖和口播稿」，但不能只按产物数量判断好坏。

### 3. 从长财报整理带出处的分析报告

- **原文做法**：作者上传腾讯控股 2026 年中期报告，要求提取营收、净利润、毛利率、现金流等，分析业务、同比变化和风险，并给关键数字标出原文页码或章节。文中只称「大部分核心数字」能找到，未展示完整核验表。来源：[[sources/百度搭子三道题文章拆解]]。
- **可改编任务**：用一份公开且可获取的长报告，先人工列出待查字段；让工具生成带出处的摘要，再随机抽查与高风险字段全查。写稿时展示「正确、错误、找不到出处」三类结果。
- **验收与适用条件**：核对数值、单位、年份、同比口径和页码，保留原 PDF、提示词与核验表。适合读者真有查长文档需求时使用。类似案例可用招股书、政策文件或产品技术报告；文件领域不同，核验字段也应改变。

### 4. 从城市概念图扩展为能探索的原型

- **原文做法**：作者先给模型一张城市概念图，得到 3D 城市后继续加需求，形成可切换视角、步行、开车、乘船和与 NPC 互动的游戏雏形，并描述了高 token 消耗。来源：[[sources/GPT-6-Astra连测文章拆解]]。
- **可改编任务**：用自己制作或获准使用的一张概念图，分两轮测试：首轮只求可移动视角与基本场景；第二轮新增一种交互，例如驾驶或与对象对话。保存每轮项目和额度。
- **验收与适用条件**：检查能否运行、场景是否保留原图主要元素、视角和交互是否稳定，记录实现时间与成本。适合测代码生成和迭代能力；若没有开发环境或素材，先缩成一个房间而不是直接造开放世界。类似案例可换成展厅、校园或产品陈列空间。

### 5. 让电脑操作工具完成一关游戏

- **原文做法**：作者让模型通过电脑操控手机游戏《开心消消乐》第 9874 关，称六分钟通关；对照叙述是此前另一模型十几分钟只走一步。来源：[[sources/GPT-6-Astra连测文章拆解]]。
- **可改编任务**：挑一个可重复、状态可重置的界面任务，预先规定成功条件和时间上限，录屏记录观察、点击、错误与重试。办公题材可改为「在测试环境里整理一张表并导出」，但这属于新设计，不能拿游戏结果推断办公表现。
- **验收与适用条件**：记录设备、关卡或任务初始状态、指令、时间、点击次数和是否求助。模型对照需要同一环境与起点；若不一致，只能写成两次体验，不能称公平胜负。

### 6. 把真实撕碎的图片重新拼合

- **原文做法**：作者打印图片，手撕为几十块，旋转打乱并拍照交给模型。一张雷诺阿画作的主要人物和构图大体恢复；换成风景照后，拼出的图与原图差异很大。来源：[[sources/GPT-6-Astra连测文章拆解]]。
- **可改编任务**：使用自己拍摄的图片，固定碎片数量与拍摄条件，先用主体清楚的图，再用重复纹理较多的图；要求模型只根据碎片位置复原，不补画未知内容。
- **验收与适用条件**：保留原图、碎片照片、重拼结果，比较主要区域位置、拼接错误和是否凭常识「脑补」缺失。适合测视觉空间推理，若读者关心文档修复，也可推导出「打乱图表或版面重新排序」的新案例，但要另设评分标准。

### 7. 参照荒漠概念图在 Blender 建模

- **原文做法**：作者给模型一张美西荒漠概念图，要求在 Blender 里制作；文章描述模型搭场景、补物体、加材质、调灯光，并截图检查、继续修改。来源：[[sources/GPT-6-Astra连测文章拆解]]。
- **可改编任务**：给模型一张有权使用的场景图和一份元素清单，要求输出可打开的 Blender 工程；录下首次结果与自检修改过程，而不只看最终视频。
- **验收与适用条件**：核对主要物体、空间布局、材质与灯光是否接近参照；检查工程可编辑、镜头转动后是否仍合理，并记录耗时与额度。适合 AI 视频或 3D 制作文章。类似案例可换成房间布景、产品展示台或动画分镜场景，难度应按作者现有素材和技能调整。

## 第四篇新增：Agent 入门教程里的两个任务

来源：[[sources/WorkBuddy入门教程文章拆解]]。它们是作者文中的任务演示，不等于我们验证过 WorkBuddy 的功能或结果。

### 生活工作台：先本地，后多设备

- **原文做法**：作者想记录开销、运动、阅读和观影，保留默认权限，选 Hy3 模型与「工作台搭建师」专家，再使用官方「生活工作台」模板。文中称未改模板、不到一刻钟得到本地工作台；之后口头要求用资料库功能升级到可多设备查看。
- **供自己测试的任务**：用真实需要追踪的 2—4 类数据，先做最小工作台：新增记录、查看列表、按日期查找或汇总。确认本地功能后，再测电脑和手机修改同一条记录能否同步。保存模板原文、补充要求、产物及两端操作录屏。
- **验收与限制**：逐项检查保存、重开后数据是否仍在、跨设备是否同步、是否需要人工配置和权限。没有第二台设备或真实同步需求时，只做本地版；不要因页面截图好看就宣称数据持久化或多设备可用。类似任务可换成选题池或文章进度看板，但先看作者是否真有长期记录需求。

### 扫描 PDF 抽取字段，并与另一文件匹配

- **原文做法**：作者把本地文件先归类，在 Markdown 文件中预写处理逻辑，再让 Agent 对 PDF 做 OCR、定位所需信息、理解字段含义并和另一个文件匹配。文中称约半小时完成，人工做类似任务曾花一周；未公开完整文件、规则和逐项结果。
- **供自己测试的任务**：准备一小批有使用权的扫描 PDF、一份待匹配表和一份明确的 Markdown 规则：字段名称、同义词、匹配键、缺失值处理及输出格式。先人工标注一小份标准答案，再让 Agent 执行，最后逐行比较。
- **验收与限制**：分别统计 OCR 漏字、字段提取错误、匹配错误和无法判断项，记录重试、耗时与人工核验时间。适合确有重复文件处理工作的作者；没有标准答案时先做小样本，不声称「质量完全没问题」。相近题材可用票据与台账、活动报名表与名单，但应使用自己可合法处理的数据并处理隐私。

## 第六篇新增：多 Agent 协作的两个用法

来源：[[sources/Buzz多Agent协作文章拆解]]。原文平台为 Buzz，且属于早期版本；角色指令依赖该平台的命令与事件字段，迁移到其他工具时需要重写，不能照抄。

### 多 Agent 分工开发（可拆分的开发任务）

- **原文做法**：把项目经理兼产品经理、前端工程师、数据与后端工程师、经验沉淀员四个角色拉进同一频道，做一个真实的小红书数据复盘工具：自动抓取账号后台数据，生成数据总览与视频复盘页面。
- **供自己测试的任务**：选一个能前后端分开、且你能判断结果对错的真实小项目。开工前先测每个 Agent 能否收消息并在频道回复；交代背景后让每个 Agent 自我介绍职责；按环节一次只 @ 当前需要的 Agent；编码完成后由**未参与该项目**的一方按需求文档逐条验收。
- **验收与限制**：需求文档先行且验收时逐条对照；由人工复核关键数据（原文作者亲自到后台核对页面数字）。注意原文教训：让协调 Agent 统筹会导致全员等待，全自动接力会让人失去确认节点。适合任务可拆、你能定清楚需求并承担协调的情况。

### 用多 Agent 做头脑风暴

- **原文做法**：把多个模型拉进同一频道讨论没有标准答案的话题，例如写选题找不到切入点，靠不同模型的视角互相补充。
- **供自己测试的任务**：用一个你真在纠结的问题开场，让每个 Agent 先独立给出方案，再互相评论；最后由你自己收敛。
- **验收与限制**：这类任务没有正确答案，验收标准应是「是否出现了你自己没想到且可执行的选项」，而不是多数票。注意成本：模型越多、讨论越长，费用和协调时间越高。

### 可直接改造的两份资产

- **经验沉淀员指令**：任务验收完成后通读频道全过程，输出「哪里卡住及原因／哪些方法有效可复用／下次开工前注意什么」，每条写成可执行的一句话，不评价成员优劣。可迁移到自己的多 Agent 或单 Agent 长任务复盘。
- **交付约束写法**：角色指令里写清职责边界与交付形式，例如「只做页面与交互，按契约的数据格式开发，有疑问在频道确认，交付文件加接口说明，不粘贴大段代码」。这是把「别越界」转成可执行条款的样本。

## 第七篇新增：AI 短剧的制作与成本控制

来源：[[sources/Pixmax修仙短剧文章拆解]]。该篇带明显推广特征，产品功能与价格部分属于介绍而非验证结论；以下只抽取制作方法。

### 复刻一段带天地异象的短剧场面

- **原文做法**：自写剧本并更换人物、宗门、洞府设定；为灵树、四色灵球、聚合核心、扩散光波、宗门穹顶、巨型法相各做参考图；剧本先转成六个镜头（天地异动、四色凌空、灵压爆发、法相显形、法相临空、归于一身）；每个镜头写逐秒阶段提示，标注参考图分工并附负面约束；最后剪成 75 秒。六段共 1584 积分。
- **供自己测试的任务**：选一段自己有权使用的题材，先做 15—30 秒的单镜头或双镜头。先写镜头与秒级阶段表，再准备参考图并逐张写用途与排除项，最后加一份禁止项清单。
- **验收与限制**：按镜头检查时间点、动作、光影是否与阶段表一致，记录返工次数与积分或费用。适合已有素材与剪辑能力的作者；素材或剪辑能力不足时先做单镜头。原文的「基本一次就出」没有抽卡次数记录，不要据此预期低返工率。

### 用动作参考驱动非人形角色

- **原文做法**：提示词说不清连续动作（要角色从左跑到右并含起跑、加速、收步，模型往往给原地摆姿势），改用 3D 导演台先摆动作再让模型照着做；用白模跑一段打斗动作并导出参考，再驱动一只四肢比例与人形差别很大的猫。
- **供自己测试的任务**：挑一个需要完整动作过程而非单一姿势的短镜头，分别用纯提示词与动作参考各做一次，比较动作连贯性与返工次数。
- **验收与限制**：检查起手与收招是否连贯、有无硬接姿势、非人形角色的比例是否合理；记录两种做法的耗时与消耗。动作库的免费与授权条款属于限时活动，使用前需重新核对。

## 第八篇新增：草图生图与两代对比

来源：[[sources/GPT-Image2.5草图生图文章拆解]]。以下任务可直接改用自己有权处理的素材，效果需自己实测。

### 用草图控制构图

- **原文做法**：在画板正中画一条龙并加骑士，配一句简短提示，成片里龙居中、骑士伏在背上呈冲锋姿态，模型另补蓝天白云与山崖城堡；再选童趣绘本风格重画一次，验证太阳仍在右上角、小鸟仍在天上，同时自动补了表情与腮红。
- **供自己测试的任务**：先用简单草图验证**位置与元素是否被遵守**，再用同一草图换风格，观察哪些是照做、哪些是自动补全。
- **验收与限制**：把「指令遵循」与「自主补全」分开打分。补得好看不等于符合要求，要看补的内容是否与目标冲突。复杂构图的稳定性原文未做系统测试。

### 品牌物料成套生成

- **原文做法**：用内置品牌模版做 logo 到门店全套。给出三段提示词：复古 logo、餐饮连锁「老乡鸭」的门头菜单杯子桌子、快递品牌「逆风快递」的 logo 广告包装；作者指出模型还生成了提示词里没提到的交通工具与软件 UI。
- **供自己测试的任务**：为虚构品牌（必须明确标注虚构，避免与真实品牌混淆）生成 logo、包装与门店物料，检查跨物料一致性。
- **验收与限制**：逐件核对名称、配色、字体与标识是否一致；模型自行添加的元素要判断是否合适。仿造真实品牌的设计只能作为内部测试，不要用于对外投放。

### 两代模型的同任务编辑对比

- **原文做法**：用同一张图做两轮编辑，第一轮把最左者的上衣改绿、裤子改成休闲沙滩短裤，第二轮给第四个人加金链并把自行车座改红；作者自述小样本下两代差距不明显，并以官方大批量连续生成（150 张图）作为参照。
- **供自己测试的任务**：固定底图与提示词，两代模型各跑同一组编辑，至少多轮多次；记录每次改了哪里、有没有破坏其他细节。
- **验收与限制**：明确样本量，报告差异时要说明是「本次小样本未观察到」还是「多轮稳定差异」；生活场景很少出现上百张的连续生成，不要把极端样本结论直接套到日常使用。

## 第九篇新增：Harness 对比与自定义 Agent

来源：[[sources/DeepSeek原生Harness文章拆解]]。原文每组对比只跑一次，环境条件未交代；以下设计可用于自己复测，结论需重新建立。

### 固定模型只换 Harness 的横向对比

- **原文做法**：同一个模型分别接入三种 Harness 做同一个 3D 黑洞引力模拟器任务，记录耗时并评价视觉与交互（25／40／42 分钟）。
- **供自己测试的任务**：选一个 15—30 分钟能跑完、结果可肉眼判断的前端或算法小项目，固定模型、提示词、起点与环境，只换 Harness，每个至少跑两次。
- **验收与限制**：记录机器、网络、推理强度、耗时与返工；结果分「是否实现需求」「视觉与交互质量」「耗时」三项评价。单次结果不足以给 Harness 排名，只能描述本次差异。

### 用创造模式配置可复用的自定义 Agent

- **原文做法**：先配置一个面向不懂代码的小店老板的门店宣传助手，把提问方式、适配与交付检查写进预设；发布后用一句信息不完整的需求测试，它主动补问且控制在三项以内，3 分钟完成网页并检查运行。
- **供自己测试的任务**：挑一类你经常重复的任务（例如周报整理、门店或产品页面、数据清洗），先把固定要求写进预设，再用不完整需求测试它是否会补问而不是乱猜。
- **验收与限制**：对照标准模式跑同一任务，比较耗时与返工；判断是否真的会因为重复使用而省时间。偶尔做一次的任务用标准模式更省事，这一点原文也说清了。

### 复杂数据处理的双平台对比

- **原文做法**：同一模型分别接入 WorkBuddy 与官方 Harness，处理同类数据任务。前者 33 分钟完成并指出已有流程问题；后者 20 分钟报错停下，继续后近 50 分钟完成，产出质量没问题但更慢。
- **供自己测试的任务**：用自己的真实数据任务（注意隐私与授权），准备标准答案，分别跑两个平台并记录报错次数与恢复方式。
- **验收与限制**：分开记录完成质量、报错与中断、人工介入和总耗时；报错后需要人工「让它继续」的时间也要计入总耗时。

## 第十篇新增：从创意到成片的完整链路

来源：[[sources/天才机甲师拆解文章拆解]]。该篇带推广特征，第二节效果为厂商内测素材；以下抽取的是流程方法，作者自己跑的是分镜、资产、机位与生成环节。

### 手搓一支 3D 短片（世界观先行）

- **原文做法**：创意是「一台被遗弃多年的机甲在废墟城市中重新苏醒」。先把剧本交给分镜工作流，系统理解主体、环境与动作后拆成不同景别（约 15 分钟）；再确认四类视觉资产——主角恒定灰白风衣、红围巾与右眼下短疤；机甲固定黑灰重型装甲、左肩白色编号与胸口红色能源核心；敌方侦察机统一银白外壳与红独眼；城市保持黄昏、冷灰废墟与暖橙天空；把资产图关联到对应分镜；最后在 3D 导演台摆机位、试生成一条、批量生成、审片、局部返修、组接与后期。
- **供自己测试的任务**：做一个 30—60 秒的单场景短片。先写恒定特征清单（每类角色/道具/场景各三到五条），再做分镜，最后生成。
- **验收与限制**：逐镜核对恒定特征是否保持；对每个不合格镜头记录是分镜问题还是机位问题。素材或剪辑能力不足时先做一个镜头。全套流程对素材量与耐心要求较高，原文用的是厂商工作流，换工具后能力需重新验证。

### 用机位预演替代反复抽卡

- **原文做法**：同一场景试两个机位——低角度英雄镜头贴近地面向上拍并压低背景高楼，机甲体积感与压迫感增强；俯拍大场景抬高镜头，把机甲、人物与废墟放进同一画面，展示战场规模并为动作调度提供空间。
- **供自己测试的任务**：同一场景先用纯提示词写「低角度仰拍」，再用机位预演方式摆好角度生成，比较两次结果与预期机位的接近程度。
- **验收与限制**：把「是否符合想要的机位」与「画面是否好看」分开评。注意原文已说明这类预演不是为了把 AI 视频变成传统 3D 动画，也不是所有内容都需要复杂建模。

### 局部返修清单

- **原文做法**：审片后回到对应分镜或机位只改单条，已确认镜头保留；并给出三条具体修法（双方距离不够清楚→调整机甲站位；低角度缺压迫感→降低机位并增加前景遮挡；俯拍过于空旷→重新安排敌机群位置与阵形）。
- **供自己测试的任务**：给自己的项目积累一份「问题现象→可调参数」对照表，每次返工后追加一条。
- **验收与限制**：记录每条镜头改了几轮、是否影响其他已确认镜头；目标是把整段重做变成单条重做。

## 第十一篇新增：体验类产品的观察框架与一个推导案例

来源：[[sources/豆包爱学诗词山河文章拆解]]。该篇作者**没有做效果测试**，只评价内容组织与呈现；下面的第一项是它给出的观察框架，第二项是本库推导的补充测试，标为推导案例，不能算原作者做过的事。

### 用「缺失的一层信息」观察产品设计

- **原文做法**：背诗常记得作者与名句，却想不起地点、登楼原因与心境，作者把这一层概括为「坐标」；随后用图文与视频展示产品如何把诗、地点与历史空间连起来，并用「打开先看到地图而不是课程目录」「从城市看同地多诗、从诗人看迁徙轨迹」两组对照说明设计意图。
- **供自己测试的任务**：选一个你熟悉的学习或工具产品，先问「传统方式里缺的是哪一层信息」，再用「原来是什么／它改成了什么」两组对照去体验。
- **验收与限制**：这类观察只能支持「设计有想法」与「内容组织不同」的判断；不能推断学习或工作效率提升。产品覆盖范围与课标数量要按官方材料核对。

### 【推导案例】给学习效果补一次小测

- **来源与性质**：原文结尾提出三个无法回答的问题（看得有趣是否等于学会、AI 意境画面是否限制想象、能否转化为记忆与表达），但没有测试。本案例由这些缺口推导，**不是原作者做过的事**。
- **可执行设计**：选同一个学段的 10—20 首诗词，先做一次前测（默写、词义、作者与背景）；让学生用产品探索一段时间后做等难度后测；同时留一组不用产品的人作为对照。记录使用时长与完成练习情况。
- **验收与限制**：分开报告「兴趣与使用意愿」和「记忆与表达成绩」，不能把喜欢用当成学会。样本小就明确写样本量，不宣称普遍效果；涉及未成年人需取得同意，不公开展示可识别的个人信息。

## 第十二篇新增：三组难度递进的预演对照

来源：[[sources/updream预演台文章拆解]]。这一篇的对照设计可以直接照做，是案例库里最完整的一组。

### 静态白模对照（最简单的起点）

- **原文做法**：做病房醒来一场，摆三个机位：全景交代环境、大特写给惊醒瞬间、近景带出人物与床的位置关系。同时用纯提示词做两版对照，提示词已限定主角坐在床上，切镜后仍出现有时坐床上、有时坐床边的割裂。
- **供自己测试的任务**：选一个单场景、无运镜的镜头，先摆好人与物的位置再换机位看三段；再用纯提示词写同一意图。
- **验收与限制**：检查人、物与空间关系在三次生成之间是否稳定；预期白模明显更稳，纯提示词会有位置漂移。这是起步难度，器材与素材要求低。

### 简单运镜对照（判断旧方法是否够用）

- **原文做法**：做过肩推镜，起点、终点与速度都在预演台里拖出；作者明确说这种简单运镜「提示词也能控得差不多」。
- **供自己测试的任务**：同一组运镜分别用提示词与预演各做一次，比较是否值得增加上手成本。
- **验收与限制**：如果差异不明显，本组结论应写成「此难度下旧方法够用」，不要为了夸新方法而强行找差距。

### 复杂运镜对照（方法真正成立的地方）

- **原文做法**：做十秒追逐戏、三次机位变化（俯拍推近到面部特写、过肩平移带出身后的人、侧后方跟随且距离缩短）。纯提示词跑了四条，相对满意的那条里追的人基本看不见；预演版三段镜头与设定一致，身后人物清楚且距离缩短。
- **供自己测试的任务**：设计一个含两次以上机位变化、且需要前后空间关系连续的镜头；固定镜头要求后各跑一次以上。
- **验收与限制**：逐段核对机位、落点、人物位置与距离变化；记录抽卡次数与失败表现。复杂度高、耗时长，第一次不要太长，建议 5—10 秒。

## 第十四篇新增：三种输入做三种产物

来源：[[sources/全新Qoder实测文章拆解]]。三个案例都是作者亲自跑的，难度按输入的不确定程度递进；提示词可直接改造使用。

### 真实照片 → 可交互的布局规划器

- **原文做法**：给一张出租房照片与一句简短提示，要求保留单人床、增加居家办公区与收纳、预算不超 5000 元，产出可拖拽旋转家具的俯视布局网页，包含预算统计、改造前后切换与通道碰撞提醒；并在提示词末尾要求完成后用浏览器实际操作验证。
- **供自己测试的任务**：换成自己的房间、工位或书架照片，做同样的交互规划器。
- **验收与限制**：检查家具是否真能拖动旋转、预算是否随增减变化、重叠与间距冲突是否给出提示、改造前后切换是否可用。适合有真实布置需求时使用；照片模糊或空间关系复杂时应降低要求。

### 手绘草图 → 可运行的移动端 Web App

- **原文做法**：草图只给页面结构（首页、打卡、分享），跳转与交互细节未画；提示词要求先识别页面结构与交互关系、生成实施计划，指定治愈系植物视觉风格，完成情绪打卡、植物成长、历史日历、数据洞察与分享卡片，并要求在浏览器中逐页操作测试。第一版已能跳转，作者实测发现「浇水后根部变化但叶片没同步生长」与若干文字错误，用语音描述现象让其修复，再改一轮后首屏改善。
- **供自己测试的任务**：用手绘或低保真草图描述三到四个页面，让模型补全交互并实现。
- **验收与限制**：逐页点一遍并交叉检查数据是否同步（例如同一操作影响的两个元素是否都变化）；文字错误单独列清单。适合自己说不清技术实现、但能判断成品好坏的情况。

### 音频 → 声音驱动的动态画面

- **原文做法**：提示词列出四种视觉风格及其适配音乐类型与声控映射（雨夜：声音控制雨量、雾、涟漪与闪电；海浪沙滩：低频推动海浪、高频生成泡沫与水光；赛博朋克城市：节拍控制霓虹与光轨；烟气梦境：声音控制烟雾与流体），要求不同歌曲呈现明显不同、暂停后缓慢进入余韵、保留单文件 HTML、音频本地读取不上传服务器。初版炫但踩不上鼓点，作者自己改几轮无果且占用大量上下文，最后用侧边任务先只做诊断后再修改。
- **供自己测试的任务**：拿自己常听的一首歌，先定义两到三种视觉映射，再验证画面与音频的对应关系。
- **验收与限制**：用固定片段反复对照鼓点与画面变化是否同步；主观审美与同步性分开评。音频驱动类任务的判断依赖主观听觉，最好保留录屏供读者自己判断。

### 把诊断与修改分开

- **原文做法**：在不熟悉的音频处理领域，作者改用侧边任务并明确「先别改代码，只检查画面为什么跟不上节拍」，拿到问题与建议后再让主任务调整；侧边任务与主任务共用工作环境、可并行、关闭不留存。
- **供自己测试的任务**：遇到自己不熟悉的领域，先开一个只做诊断的任务，让它输出问题清单与建议，再决定改什么。
- **验收与限制**：诊断结论要能对应到具体代码位置或现象；如果诊断本身说不清原因，先缩小问题范围，不要直接开始改。

## 第十五篇新增：三类能力各一个案例

来源：[[sources/豆包Seed-Evolving实测文章拆解]]。三组案例覆盖长程结构化、前端加推理、检索与交叉验证，规模差异较大，可按自己的时间选择最小的一个。

### 把一整本资料结构化成可查的知识库（长程）

- **原文做法**：把已有项目仓库与一整本《三国志》一起交给模型，要求先读懂原项目再复用到新史料，独立完成文本解析、实体识别、关系抽取与知识图谱构建。原文给出 65 卷、2149 段正文全部结构化，1944 个标准化事件、2151 条跨传记载、2265 个人物实体、2727 条人物关系与 4312 个 Wiki 页面，且全文逐字保留、抽取内容可回原文核验；并行子任务需按最初标准判断合规才入库。
- **供自己测试的任务**：选一本可公开使用的文本（如方志、公开年报、技术文档），先做小样本：抽 20 段，要求输出实体、关系与出处定位。
- **验收与限制**：随机抽 20—30 条结果回原文核对，统计错标、漏标与无法判断项；检查是否逐字保留原文。原案例规模很大（近八小时、近 3 亿 token），不要一上来做整本书。

### 做一款跨页面线索的网页推理游戏（前端加推理）

- **原文做法**：先一句话生成方案，再让模型铺开博物馆、论坛、终端等多个网页；第一版「一眼就是很 AI」，于是给真实网站作参照重做，随后导入参考素材生成完整游戏——入口是报纸头条，玩家从失联者手机短信与相册日期得到线索，再登录内网，页面间线索复用并影响状态。
- **供自己测试的任务**：做三个页面的最小闭环：一个入口页、一个线索页、一个使用线索解锁的页面。
- **验收与限制**：逐项走通线索链，检查同一线索在不同页面是否一致、上一页的状态能否影响下一页；外观要单独评，给真实参照物比继续写形容词有效。发现界面问题时直接截图反馈，比只用文字描述准确。

### 核查一个「行业首创」式说法（检索与交叉验证）

- **原文做法**：核查某公司宣称的行业首创是否成立，并额外提供多篇标题党倾向的媒体文章与官方材料，让它自行搜索与交叉验证。原文肯定它没有掉进「谁早一天谁就赢」的框架，而是指出两者解决的是不同问题；同时也发现它写错了两处日期，且在自认未查遍全局的情况下仍断言第一。
- **供自己测试的任务**：挑一个你怀疑的「首创／第一／唯一」说法，先自己写出成立条件（同一功能、同一时间范围、同一对象类别），再让模型核查。
- **验收与限制**：逐条回原始来源核对；把结论分成「已证实」「未找到反例」「信息不足」三档，不能把「没找到反例」写成「已证明」。这个任务耗时不长（原案例半个多小时），适合作为入门案例。

## 第十六篇新增：远程接续与延迟验证

来源：[[sources/UU远程Vibecoding文章拆解]]。该篇带明显推广特征；以下抽取的是可复用的测试设计，不是对产品的验证结论。

### 双设备接续做一个真实小项目

- **原文做法**：在电脑端开始做选题工作台，外出时用手机终端看到第一版跑出，切到远程桌面查看网页效果，发现需要增加已读／未读／待核验三个筛选标签，就在手机终端补一句需求，回到电脑后继续。另一案例先在被控端建好会话，手机端自动出现同一会话，中途在终端与桌面之间来回验收。
- **供自己测试的任务**：用自己真要做的网页或小工具，分三段执行：电脑端启动、外出时用手机查看并补一条需求、回电脑继续验收。
- **验收与限制**：记录接续是否需要手动同步、退出移动端后任务是否仍在跑、手机上输入长需求是否可接受。适合确实有移动场景的人；只在家办公则不必折腾。

### 用敏感场景验证不敏感的指标

- **原文做法**：作者认为办公操作很难直观看出远程控制的延迟，于是改用平板玩对延迟敏感的小游戏来验证，并记录帧率与画面档位设置。
- **供自己测试的任务**：想验证延迟、同步或稳定性这类指标时，先找一个会把它放大的场景（游戏、实时视频、语音同步），再回到日常工作场景看是否够用。
- **验收与限制**：明确写出档位设置与网络条件，因为能开到哪一档取决于控制端、被控端与网络；单款游戏的经验不能推广到所有场景。

### 用一次真实迁移测文件传输

- **原文做法**：把旧 Windows 电脑的文件迁到新 Mac，给出约 5MB/s 的实测速度，并注明速度受两台设备与网络环境影响。
- **供自己测试的任务**：拿自己真实需要迁移的文件夹（注意隐私与授权）跑一次，记录总量、耗时与平均速度，并记录失败与断点续传情况。
- **验收与限制**：报速度必须附设备与网络条件；小文件多与大文件少的结果差别很大，最好说明文件构成。

## 第十七篇新增：长视频连续性工作流

来源：[[sources/长视频导演Skill文章拆解]]。作者自己做出了 Skill 并做了对照，但只做了一组对照、无量化数据；以下做法可改造使用。

### 生成前先出「导演执行包」

- **原文做法**：给一段自然语言故事，不马上开拍，先把人物、事件与空间整理成执行包，等作者确认后再生成；随后把故事拆成前后相连的视频节点，每段推进剧情并给下一段留入口，人物、道具、场景与摄影机都要接住上一段状态。
- **供自己测试的任务**：写一段 30—60 秒的多镜头故事，先让它输出执行包（人物、场景、事件衔接、每段起止状态），人工确认后再生成。
- **验收与限制**：逐节点核对上一段的结束状态是否等于下一段的开始状态；执行包明显不合理时先改它，不要直接生成。

### 用锚点图固定人物与场景

- **原文做法**：生成前先做人物、道具与场景参考图固定视觉信息，后续每个节点都看同一套参考，「不用拿到一段文字以后重新猜一遍」。
- **供自己测试的任务**：先统一主角服装特征、关键道具与场景色调，各出一张参考图，之后所有节点共用。
- **验收与限制**：逐节点核对服装、道具位置与色调；与已有的资产清单做法配合使用（参见 [[topics/AI写作案例库]] 中第七篇与第十篇的资产方法）。

### 节点化返修

- **原文做法**：五个节点中，尾声被模型做成了 2D 平面动画，作者只改这一段要求并重新生成该节点，其余四段不重抽，最后合成完整视频。
- **供自己测试的任务**：把长内容拆成 3—5 段，每段单独验收；出问题的段单独重生成，记录重抽次数。
- **验收与限制**：统计节点数与总重抽次数，用来判断节点化是否真的省成本；只有定性感受时不要写「省了很多」。

### 转场靠画面里的动作线索

- **原文做法**：不用「镜头切过去」这类指令，而是从当前画面找动作与视觉线索，把注意力带到下一个场景。例：猫接过客厅的注意力后往厨房走，摄影机跟着转过去；乐队指挥段落用推进、环绕与拉远串成一次不间断运动。
- **供自己测试的任务**：在两段之间设计一个「画面里已经发生的动作」作为转场动力，而不是加一句切镜说明。
- **验收与限制**：检查转场是否由前一动作自然带出；做不到时退回到明确切镜，不要为了连续而牺牲叙事清楚。

### 关于控制粒度的取舍

- **原文做法**：起初把人物动作写得很细，结果「规则越多，视频越僵」；后来只定住影响前后连续性的部分，动作细节交给模型发挥。
- **供自己测试的任务**：同一段分别用「细规则」与「只定连续性」两版生成，比较动作自然度与返工判断难度。
- **验收与限制**：记录哪一版更容易定位问题节点；不要因为放宽后画面更好看就取消所有约束。

## 第十八篇新增：生态教程与自建插件

来源：[[sources/DSH插件市场文章拆解]]。这一篇提供的是「教程＋实录」结构，以及三处可直接复制的指令。

### 先把方向看准，再动手实现

- **原文做法**：做插件前先让模型做需求理解（对齐双方说的是同一件事），再做难度判断（给三档难度框架：纯界面插件／涉及文件与事件的进阶档／加整个应用壳的宿主级），随后**先出几个效果图方案**供选择，作者选定一款后才开始实现。原文明确说直接开跑很可能不符合预期，token 也会白花。
- **供自己测试的任务**：拿一个自己的小需求，走完「描述 → 需求理解 → 难度判断 → 方案预览 → 选定 → 实现」六步，记录每步耗时。
- **验收与限制**：对照「跳过方案预览直接开工」的一组，比较返工次数与消耗。适合界面或插件类小工具；需求本身说不清时先花时间说清。

### 给爱自作主张的 Agent 加约束

- **原文做法**：作者只问了一个澄清问题，模型却在同一条回答里花了二十一分钟把第一版做完，结果不满意。他随后在每条指令末尾追加六条约束（见 [[topics/测评问题与实战技巧库]] 中的完整文本）。
- **供自己测试的任务**：把同一段约束贴到自己的常用工具上，用同一个需要多步确认的任务跑两次，比较越界次数与返工量。
- **验收与限制**：记录「未经确认擅自扩展」「该停没停」「跳步」三类行为各自出现几次；约束过长可能压缩模型的主动性，需要按任务调整。

### 装插件前的安全动作

- **原文做法**：作者提醒产品仍是预览版，插件会出现不兼容、冲突崩溃与安全性问题，建议优先选择持续维护、经筛选的插件，并把一句话交给任一 Agent 做自查：「帮我确认这个插件「地址」，检查它是不是真的 DSH 插件、源码有没有问题。」
- **供自己测试的任务**：安装任何第三方插件前先跑一次源码与来源检查，记录检查结论与后续是否发现问题。
- **验收与限制**：这类自查不能替代人工审阅；涉及账号与凭证的插件尽量避开，或先用隔离环境试。

## 第十九篇新增：从概念图到 3D 模型

来源：[[sources/iPhoneDuo配件设计文章拆解]]。本篇交付的是概念方案，不是实物；适合作为脑洞类作品的制作流程参考。

### 用参照资料做配件概念设计

- **原文做法**：先吐槽官方配件的配色与价格，再说「有点不服」，随后做三个方向的手机壳方案（机械风、简约素净、彩色编织），每款单独展开并补材质特写与各角度细节，形成类似商品详情页的效果；做笔时先从「折叠屏展开像小 iPad、官方笔长度不变」论证必要性，再给两款不同取向的方案。
- **供自己测试的任务**：挑一个自己真的想买但不满意的现有产品，先列三条不满，再做两到三个方向的概念方案，每款注明针对什么需求、适合谁。
- **验收与限制**：概念阶段就要写明未验证项（材料、耐脏、耐用、成本）；不要把概念稿说成已经做出来的东西。

### Blender 建模的提示词要点

- **原文做法**：把设计图交给模型时明确要求——准确理解整体轮廓、比例、曲面、按键布局、材质与配色；**图片中看不到的背面与侧面依据合理的工业设计自行补全**；模型适合近距离产品展示，结构干净、曲面平滑、材质真实，并完成基础灯光与展示渲染；**直接开始建模，不用先写方案**；完成后保存源文件并导出可用于网页三维展示的格式。
- **供自己测试的任务**：拿一个自己的设计稿或现成产品照片，用同一段要求生成模型，检查看不到的背面是否被合理补全。
- **验收与限制**：检查轮廓比例、曲面是否平滑、材质是否真实、灯光是否可用；导出文件要能在浏览器三维场景中打开。适合已有设计稿或清晰产品图的人。

### 借现成 3D 模型做展示

- **原文做法**：为展示支架效果，让模型去找该机型的现成 3D 模型，放到支架上做展示。
- **供自己测试的任务**：做产品概念展示时，先找目标设备的现成模型作为参照，再叠加自己的设计件。
- **验收与限制**：确认现成模型的使用许可；比例与接口位置要与真实尺寸核对，不要只看画面好看。

## 第二十篇新增：一套品牌全案的分步提示词

来源：[[sources/Miora火锅店品牌全案文章拆解]]。全部产物为设计稿与生成素材（原文已标注含 AI 生成图片），未打样、未施工；虚构品牌名需在文中声明与真实品牌无关。

### 从一句模糊需求到品牌基础规范

- **原文做法**：用一句「做一个餐饮品牌河底捞，帮我头脑风暴一下品牌调性和 Logo 设计方案」起手；模型识别需求模糊后给出选项，引导确定调性与风格；定稿后立刻补一套基础视觉，供后续所有物料继承。
- **供自己测试的任务**：用一个自己想到的名字做同样两轮：先由模型给选项收敛风格，再让它输出一套可继承的基础视觉（主色、辅助色、字体、图形元素）。
- **验收与限制**：品牌名与真实品牌近似时必须声明无关；基础规范要能落到后续每一项物料上，只给风格形容词不算规范。

### 门店与包装（沿用规范）

- **原文做法**：提示词为「沿用已经确定的 Logo、配色和字体，继续做门店 VI 和食品包装。先设计门头和店内空间，再出外卖餐盒、手提袋和饮品杯，风格保持一致。」
- **供自己测试的任务**：拿自己定的基础规范，先做空间再做包装，逐件核对 Logo、配色与字体是否一致。
- **验收与限制**：检查继承关系是否真的成立；出现局部文字崩坏时用框选局部重生成，不要整张推倒。空间是设计效果图，不能当作施工依据。

### 十秒宣传视频的逐秒脚本

- **原文做法**：指定 16:9、电影级广告风格、色彩规范、禁止修改标识，并按秒写出六个镜头与转场，末尾列避免项（空锅、清水感、食材变形、塑料质感、浓雾、乱码、其他品牌标识）与声音设计。
- **供自己测试的任务**：为自己的一段物料写一份秒级镜头表，每段包含画面、转场与声音；另列一份避免项清单。
- **验收与限制**：逐段核对时间点与画面是否对应；第一版效果差时优先补参考图与把汤底、食材、节奏写具体——作者的结论是「描述得越细致、越丰富越好，还得在关键画面给一些预期效果的参考图」。

### 界面需求（限定单页与完成度）

- **原文做法**：要求高保真、严格延续基础视觉、**每次只生成一个页面**、列出四个板块职责、其余按成熟产品标准自行补充、使用真实完整内容而非占位素材、达到可直接评审与开发落地的完成度。
- **供自己测试的任务**：为自己的一款小工具写界面需求，一次只做一个页面，逐页核对信息层级。
- **验收与限制**：原型信息密度过高时要回到自己的描述上找原因（作者本人就是这么归因的）；真正要开发前需要自己重做信息层级与交互逻辑。

### 把定稿沉淀成可复用能力

- **原文做法**：选中画布里确认过的整套视觉规范，让工具生成品牌专属能力，「以后生成新的包装、海报和线上物料时，继续沿用现在的 Logo、配色、字体和设计风格」，之后新物料直接调用，不必重讲背景。
- **供自己测试的任务**：一个项目完成后，把定稿规范整理成一份可复用的说明或自定义配置，下一次新物料先加载它。
- **验收与限制**：比较「重新讲一遍背景」与「直接调用定稿」的产出一致性；沉淀内容要包含具体色值与字体，不只是一段风格描述。

## 第二十一篇新增：演示类素材的处理方式

来源：[[sources/GPT-6-Astra演示汇总文章拆解]]。该篇作者未实测，全部案例为第三方演示；以下抽取的是**如何处理这类素材**，不是产品能力结论。

### 把演示素材按能力层级整理

- **原文做法**：把案例分成三层——能交付完整可玩的产品（桌面应用、交互音乐应用、射击游戏）、空间理解与视觉判断（模糊房源照片重建 3D 房屋并出视频、参考图重建园区、复刻 3D 工具）、进入专业工作台（数学证明讨论、医学科普视频、电路设计与数据分析）。
- **供自己测试的任务**：收集到的演示不要按时间罗列，先按「它交付了什么层级的成果」分组，再决定写哪几层。
- **验收与限制**：每组都要标来源与演示者自述的条件；层级划分是写法工具，不构成能力结论。

### 想复现演示时该补什么

- **原文做法**：作者指出对比帖的提示词、工具、运行环境和人工修改次数都没完全公开，因此无法判断差异来自模型还是条件。
- **供自己测试的任务**：挑一个自己最想复现的演示案例，先补齐这四项条件再动手；缺哪项就在结论里说明缺哪项。
- **验收与限制**：只复现一次不要下能力结论；演示里的耗时来自演示者自述，不能当自己的预期预算。

### 不凭精选视频宣布胜负

- **原文做法**：作者发现两模型对比帖结论互相矛盾（有的显示一方领先一代，换个帖子又完全反过来），加上条件不公开与展示选择的影响，最终决定「在自己真正用上以前，我不太想凭几段精心挑选的视频宣布谁赢了」。
- **供自己测试的任务**：遇到同类对比素材时，先列三条检查：结论是否互相矛盾、四项条件是否公开、是否有选择展示的可能。
- **验收与限制**：这三条不适用于条件齐全的公开评测；条件完整时可以正常比较。

## 第二十二篇新增：存量内容的多市场版本

来源：[[sources/Seko出海转绘文章拆解]]。三版镜头层面一致，画面细节与语言自然度未逐项评估；以下做法可改造使用。

### 把一条成片拆成逐镜拉片

- **原文做法**：52 秒被拆成 17 个镜头；作者的判断是「后面所有东西都建立在这份拉片上，这里错了后面全歪」，因此这一步要先在分镜表上人工确认再往下走。
- **供自己测试的任务**：拿一条自己有权处理的短片，先只做结构拆解（镜头编号、时长、机位、切点、空间关系），人工核对后再进入后续步骤。
- **验收与限制**：核对镜头数量与切点是否与原片一致；结构不对就不要进入下一步。适合有成片可改的人。

### 用空间拓扑锁定保一致性

- **原文做法**：换的是材质与文化符号，空间结构不动——床在左、窗在右、门在中间，因此镜头能对得上。
- **供自己测试的任务**：改版前先写一份空间清单（主要物体与朝向、门与窗位置、镜头主要机位），改版后逐项核对。
- **验收与限制**：检查是否出现物体换边、门窗移位这类结构变化；结构变了镜头对不上，「换皮感」就会出现。

### 同一素材再跑一个市场

- **原文做法**：美国版做完后，用同一条源片做日本版，用于检验工具是理解不同市场，还是只换语言与人脸；结果世界观与角色身份都重新设计（金融精英对社畜程序员、修女对怨灵），并引用当地类型代表作做参照。
- **供自己测试的任务**：同一条素材做两个目标市场版本，专门比较世界观与角色身份是否各自成立。
- **验收与限制**：分开评「镜头是否保留」与「文化解释是否成立」；两个市场版本都成立才算做对，只换语言和人脸属换皮。

### 只有剧本时的另一条路

- **原文做法**：剧本裂变与成片转绘是两条不同路径——转绘把做好的片子搬到海外，裂变先把本子改成海外版再去拍。裂变方案会重设计世界观与机制（例如把无代价的无限回档改成有能量上限、冷却与损耗的机制），并自带禁止改动清单锁定主角身份原型与高潮选择权。
- **供自己测试的任务**：拿一份自己的剧本梗概做裂变，重点看它是否给出可解释的机制改动理由。
- **验收与限制**：检查改动是否保住了原有爽点；同时确认不可变项是否被写清（防止后续阶段静默偏移）。适合还没开拍的团队。

## 第五篇新增：小模型本地部署的三个任务

来源：[[sources/Qwen3.8-27B本地模型实测文章拆解]]。作者在云服务器上部署，不是笔记本；以下是我们可改用的测试设计，结果需自己实测。

### 落沙物理沙盒（规则翻译与状态更新）

- **原文做法**：用原生 HTML／CSS／JS 写单文件模拟器，材料含沙子、水、酸液、墙，支持连续拖动、暂停、换材料和调大小。作者挑四个最容易看出差别的场景逐项检查：沙子是否一次只下降一格而不瞬移、水遇墙是否随机向两侧散开而不固定偏向、沙入水是否继续下沉并顶起水且不跳格、酸液是否只溶解一个相邻目标并清除自己。
- **供自己测试的任务**：给模型一份**规则清单**（每种材料如何移动、如何互相作用），要求输出单文件、零依赖页面。逐条规则转成一个可判定检查，必要时减速或逐帧观察。
- **验收与限制**：先固定画布尺寸、初始状态与更新顺序要求；记录哪几条规则通过、哪条失败及表现。适合测算法理解与长规则遵循；不适合用它推断模型的整体编码水平。
