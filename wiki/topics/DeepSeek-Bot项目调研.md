# DeepSeek Bot 项目调研

## 它是什么

DeepSeek Bot，简称 DS Bot，是 DeepSeek Harness（DSH）的第三方插件。它不是 DeepSeek 官方产品，也不是一个可以脱离 DSH 独立运行的机器人框架。它把 DSH 的单会话 Agent 界面改造成一支长期存在的 Bot 团队：每个 Bot 有独立身份、模型、指令、记忆、工作目录和聊天窗口，还能进入群聊、互相发消息和委派任务。

最准确的理解是：**DSH 提供模型、会话、工具、权限和插件底座，DS Bot 在上面增加“长期同事＋团队管理＋群聊协作”这一层。**

这与 [[sources/DeepSeek原生Harness文章拆解]] 的 Harness 主题，以及 [[sources/Buzz多Agent协作文章拆解]] 的多 Agent 分工主题直接相关。

## 安装与基本使用

### 前置条件

1. 先安装 DeepSeek Harness，并至少配置一个模型。DS Bot 直接使用 DSH 已配置的模型和用户自己的额度，并不赠送模型调用。
2. DSH Desktop 支持 Windows、macOS；在插件页输入 `ds-bot`，安装并启用，必要时彻底退出后重启。
3. DSH Web 支持 Windows、macOS、Linux，文档要求 Node.js 22.19 以上和 pnpm。v0.1.5 README 使用 DSH `0.2.0-rc.2` 的安装命令。
4. 首次打开后会自动创建主 Bot「Chief」，作者建议直接与 Chief 对话，让它帮助创建其他 Bot 和群聊。

### 一套典型玩法

可以先让 Chief 创建研究员、作者、事实核查员和主编四个 Bot，为每个 Bot 设置固定模型、角色说明和能力，再建立一个选题群。平时把材料交给研究员，研究员通过 `@作者` 委派初稿，作者完成后再 `@事实核查员`。群管理员默认统筹回复，其他成员只有被点名或确实有新增内容时才发言。

Bot 可以绑定独立工作目录；群聊也可以为所有成员指定同一目录。插件还支持一次性、每天、每周或固定间隔的定时任务，以及按 Bot、模型和时间统计 token 用量。

## 核心能力

### 1. 长期 Bot

每个 Bot 本质上是一条 DSH Session，拥有名字、角色、指令、模型、思考等级、权限和形象。用户可以长期在同一个 Bot 窗口里工作，无须自己管理上下文分段。主 Bot 权限最高，可以创建、修改和删除其他 Bot，并管理所有群聊。

### 2. Bot 之间协作

Bot 通过 `message_bot` 给另一个 Bot 发消息，主 Bot还可以创建和配置 Bot。v0.1.4 加入异步委派：群成员可以用 `@Name` 把工作交给另一个 Bot，被委派者独立运行，群聊不必停下来等待；完成后结果回到群里，再由发起委派的 Bot继续回答。

当前未发布修复还增加了一条重要保险：自用户最后一次发言、回答问题卡或定时任务启动以后，Bot 链最多继续 40 条消息，防止多个 Bot 长时间互相转发和致谢形成失控循环。

### 3. 群聊

群成员按轮次发言，每个成员先读取最新群消息。每个群必须指定管理员，用户没有明确 `@` 时默认由管理员回答，并由管理员决定是否叫其他 Bot 加入，以降低全员轮询带来的费用。每个成员在每个群里有一条独立的隐藏 Session，群聊不会直接读取该 Bot 的私人聊天。

用户可以引用另一段聊天作为当前消息的上下文，也可以直接 `@Everyone` 或指定成员。没有新内容的成员应该返回 `[PASS]` 保持安静。

### 4. 长上下文与聊天检索

DS Bot 禁用 DSH 自带的压缩，改用自己的 context steward。对话超过模型可用窗口的一定比例后，单独进行一次小模型判断：

- 工作仍在进行：原地压缩为 checkpoint，保留任务交接摘要和用户最近消息的原文。
- 工作到达停顿点：写 handoff note，并在新的 conversation part 继续。

用户看到的仍是一条连续聊天。更早的聊天片段进入本地 `node:sqlite` FTS5 全文索引，Bot 通过 `read_own_chat` 搜索。这个机制解决的是“长期会话如何续上”，并不等于模型真正拥有无限上下文。

### 5. 两级记忆

每个 Bot 有个人记忆，团队还有一份共享记忆。记忆使用 Markdown，核心文件是 `MEMORY.md`，详细内容放在 topic 文件中，所有变更记录在 `journal.jsonl`。

每轮结束后会额外调用模型审查新增对话，自动决定保存、更新或删除哪些记忆；也可以关闭自动审查，或手动使用 `remember`、`forget`、`recall`。记忆有明确限额：单条最多 300 字符，`MEMORY.md` 最多 4,000 字符，topic 最多 16,000 字符，一个作用域最多 40 个 topic。

### 6. 能力库与工具

Settings → Capabilities 是团队共享能力库，可以保存 MCP Server、Skill 和能力包，并选择哪些 Bot 可用。Bot 新增本地 MCP 命令时仍需用户批准。插件还提供 GitHub connector、自动 Web Search、定时任务、图片转文字和秘密信息卡片。

### 7. 浏览器和搜索

DSH Desktop 中每个 Bot 有独立浏览器分区，Cookie 和登录状态互相隔离。当前浏览器工具只能读取页面 DOM，不能点击、输入、滚动或主动打开地址；无法读取跨域 iframe、canvas、关闭的 Shadow DOM 和未渲染内容。DSH Web 没有这个浏览器面板。

Web Search 会依次尝试用户指定 provider、当前模型路由自带搜索、部分搜索 API，最后回退到 Bing 和 DuckDuckGo 的公开结果页。

## 实现原理

代码分为 host、client 和 shared 三层：

- `src/host/`：Bot、群聊、Session、权限、记忆、上下文 steward、SQLite 索引、定时任务、Secrets、Usage、浏览器和能力库等后端逻辑。
- `src/client/`：侧边栏、群聊、Bot 详情、设置、用量统计、记忆面板、能力管理和浏览器面板等前端界面。
- `src/shared/`：前后端共享的 mention 等逻辑。

插件通过 DSH 的 Cordis 插件系统装载，声明 `@deepseek-ai/cordis`、`dsh-llm`、`dsh-tools` 和 `dsh-web` 为 peer dependencies。前端由 esbuild 打包成 `client.js`。

本地数据主要分两处：聊天本身仍在 `~/.dsh/sessions/`；团队状态、记忆、全文索引和统计数据在 `~/.dsh/bot/`。`state.json` 保存 Bot、群聊和 Bot 间消息，`chat-index.sqlite` 保存旧聊天全文索引，`usage.sqlite` 保存 token 统计。

## 能力边界

1. **依赖 DSH**：不能独立运行，DSH 的插件接口或版本变化可能直接导致不兼容。
2. **项目很早期**：v0.1 文档明确说功能、工具和数据格式都可能变化；仓库创建于 2026-10-07，一周内连续发布多个版本。
3. **多 Bot 不等于更聪明**：效果仍由底层模型、提示词、工具和分工决定。协调、转发和重复读取群消息还可能降低效率。
4. **群聊明显更费 token**：每个成员都有独立 Session，并按轮次读取群消息。管理员默认回复只能减少无意义调用，不能消除多模型费用。
5. **记忆不是事实数据库**：自动记忆仍由模型判断，可能漏记、错记或保留过时信息；固定长度限制意味着需要整理和淘汰。
6. **浏览器目前只读**：能理解页面，但还不能替用户完成网页操作。
7. **权限风险真实存在**：Bot 可以读写文件、运行命令和使用 MCP；主 Bot 权限很高。关键操作仍需人工检查。
8. **Secrets 不是完整保险箱**：值以本地文件保存，Windows 文件权限保护有限；只会遮盖秘密值的精确副本，编码、拆分或反转后仍可能泄露。
9. **同一团队只有一个写入者**：Desktop 和 Web 共用同一 DSH home 时，第二个实例只能只读。
10. **用量页只统计 token，不计算金额**：不同模型和服务的真实成本需要用户自己换算。

## X 上的发布与传播

作者 FeiZ（@Fei2411）在 2026-10-11 发布正式介绍帖，明确写了“非官方”，并将卖点概括为持久化 Bot、自带上下文管理和记忆、主 Bot 管理团队、群聊协作、接入用户自己的模型。该帖在 2026-10-14 检查时显示约 27.3 万浏览。

评论串进一步说明：群聊虽然适合多 Bot 协作，但费用会明显增加，所以设置管理员默认回复；作者也列出若干已做兼容性测试的 DSH 插件，并再次提醒项目仍处于早期阶段。X 未登录状态下的站内搜索被要求登录，因此本次没有形成完整的全站用户评价样本；当前能确认的是作者发布串和其中一条“被点赞、可能得到官方认证”的用户回复，不能据此推断已经获得 DeepSeek 官方认可。

## 公众号选题判断

### 值得做，但不要先写成安装教程

项目有三个传播点：发布帖热度高、产品形态直观、作者把“长期记忆＋团队分工＋群聊”整合到同一个界面。但项目刚发布，安装和兼容性变化快，直接写保姆级教程容易很快过时。更合适的是先做一次真实团队任务实测。

建议选题命题：**我给 DeepSeek 装了一支 AI 团队，它们真的会自己分工吗？**

### 推荐实测案例

用它完成一篇公众号文章，但把任务拆成四个可验收角色：

1. Chief：创建团队、分配任务、汇总进度。
2. 研究员：查项目资料和 X 动态，输出带链接的事实表。
3. 作者：只依据事实表写初稿。
4. 审稿员：检查事实、AI 味、重复表达和能力边界。

重点记录：创建角色是否真能靠对话完成；Bot 间委派是否需要人工救场；群管理员是否有效减少无效回复；中断重启后任务能否恢复；记忆是否在新会话中正确复用；单 Bot 与四 Bot 的 token 用量差多少。

### 文章必须回答的问题

- 它与普通多开几个 Agent 的区别是什么？
- Chief 是真的管理任务，还是只负责转发消息？
- 多 Bot 在什么任务上比单 Bot 更值？
- 长期记忆究竟记住了什么，是否会错记？
- 一次完整任务用了多少 token，增加的成本换来了什么？
- 关掉 DSH 再打开，未完成工作能不能续上？
