# 公众号 Skill 流水线设计

把已有的公众号 Skill 串成一条能跑、能验收、能断点续跑的流水线。
参考材料是用户提供的飞书文档 [[sources/飞书Skill进阶实操第三阶段]]，
本地落地形态是 Skill `gzh-daily-pipeline`，源码在 dream-skills 仓库，
安装副本在 `.agents/skills/gzh-daily-pipeline/`。

## 2026-10-26选题环节变更与能力边界

依据本次用户决定，移除旧 `wechat-viral-topic`，重建面向本账号的 `gzh-topic-planning`；当前设计不再调用旧技能。S1沿用AI Coding、Agent工作流、AI视频及真实动手的账号定位，从六类来源找题：同领域异常表现文章、已披露商业合作案例、官方产品变化、作者真实实践、读者真实问题、旧文后续与时间节点。具体证据要求见 [[topics/公众号每日选题决策]]。

异常表现必须有可比日常基线，商业披露不证明仍有预算，官方变化不等于作者实测成功，未发生的实践与读者需求必须标为待试或假设。默认不超过3个候选、推荐1个，交代证据、读者动机、新增任务、最小试跑及退路，不设总分与淘汰线，不强制H5。作者仍负责亲测；S5标题改由 `wechat-article-writing` 处理，不自动发布。

2026-10-26已删除工作区旧技能目录，创建并同步 `gzh-topic-planning` 源码与安装副本，S1及S5模板与交接已迁移。源码提交 `2c868c6` 已推送 dream-skills。实际运行了脚手架init/check/status及隔离选题行为演练；后者只验证无热点、缺基线和未知权限下的取舍行为，不代表六类来源已自动接通、真实选题效果获验证或整篇生产已端到端完成。完整验证见 `wiki/log.md`。

## 为什么需要总调度

现有 Skill 都是单环节的：[[topics/公众号每日选题决策]] 负责选题，
[[topics/文章写法库]] 管结构，[[topics/证据与边界库]] 管论证边界，
[[topics/文章标题库]] 管标题，[[concepts/公众号写作风格DNA]] 管语言。
单环节 Skill 有三个老问题：

1. **谁先谁后靠记性**。每个 Skill 都能单独跑，但「现在该跑哪个」没有机器可读的答案。
2. **交接只靠对话**。上一个环节的结论如果没落到文件，下一个环节就得重问一遍，
   中断后也无法接着跑。
3. **验收靠自觉**。「这篇是不是该能发了」没有统一判定，容易在没证据时把稿子推给读者。

所以流水线 Skill 不做内容，只做三件事：决定现在跑哪一步、把上一步产物接给下一步、
在每道关口检查交付物是否合格。

## 三条设计原则

1. **每个环节只干一件事，交接靠文件契约，验收靠脚本。**
   下游只读上游产物文件，不读对话历史；上游不假设下游会追问。
2. **能交给脚本的不要交给人。**
   缺文件、状态取值非法、阶段顺序倒置、占位符残留、有没有实测记录，
   都由 `scripts/pipeline.py check` 判定；判断题留给作者。
3. **作者的实测记录是硬关口。**
   助手可以策划案例、设计提示词，但不能替作者实测，也不能把预期写成结论。
   没有实测记录，正文最多只能到骨架。

## 七阶段流水线

| 阶段 | 做什么 | 调用 Skill | 交接产物 | 关口 |
| --- | --- | --- | --- | --- |
| S0 定盘 | 读账号宪法与知识库，确认赛道、受众、备胎选题 | 只读 | `00_style.md` | 自动 |
| S1 选题 | 从六类来源形成不超过3个候选，依据证据与新增任务推荐1个，附最小试跑和退路 | `gzh-topic-planning` | `01_选题卡.md` | 人工确认选题，不用打分淘汰线 |
| S2 案例与实测 | 案例决策卡 + 准备素材与提示词 | `wechat-article-writing` | `02_案例决策卡.md`、`03_证据与实测.md` | **硬关口**：作者亲测 |
| S3 写作 | 按结构写正文 | `wechat-article-writing` | `04_正文.md` | 人工审稿 |
| S4 定稿检查 | 四层 AI 味、病句、事实边界、阅读承诺 | `gzh-final-check` | `05_检查报告.md` | 必须修改项清零 |
| S5 标题封面排版 | 依据真实正文拟标题、生成封面、渲染富文本 | `wechat-article-writing`、`gzh-webchat-cover`、`md-wechat-layout` | `06_标题.md`、`07_封面.png`、`08_排版/` | 人工选定标题 |
| S6 发布与回流 | 人工粘贴发布，成稿回流入库 | 人工 + 知识库入库 | `09_发布记录.md` + wiki 页 | 人工发布与入库 |

一次生产一个目录，目录名 `YYYY-MM-DD-选题短名`，十份产物按编号排列。
脚手架一次生成全部模板，`check` 报出第一个没过的关口，`status` 打印阶段状态表，
用来判断从哪一步接上。

## 交接契约

每个阶段文件开头是同一套 frontmatter，是机器可读的凭证：

```yaml
---
stage: S1 选题
status: 已确认
topic: 一句话主问题
source_skill: gzh-topic-planning
created: 2026-10-26
updated: 2026-10-26
---
```

`status` 只取待办、待确认、已确认、已跳过、已废弃五种。
阶段顺序推进：前一阶段是已确认或已跳过，后一阶段才能是已确认。
模板里的 `{{字段名}}` 是待填占位符，阶段改成已确认前必须替换完。
确实需要作者补的内容写成 `【待补：…】`，不删占位符——脚本报出两者的方式不同，
前者是模板遗留，后者是有意保留的缺口。

## 与飞书流程逐段对照

| 飞书流程 | 我们的做法 | 取舍理由 |
| --- | --- | --- |
| Step 0 定赛道，写 `00_style.md` | S0 同名同物，内容来自知识库 | 基准一致，不重复定义 |
| Step 1 采集 → 生成 → 评审，5 维 70 分线 | S1从六类来源形成不超过3个候选，按证据、读者动机与新增任务推荐1个 | 不采用固定时效门槛、加权打分或淘汰线；附最小试跑与退路，由作者实操 |
| Step 2 三版并行、A+C 合并、40 个标题 | S2/S3 只在有多个真实角度时才出多版 | 强制三版会逼出没有证据的角度 |
| Step 3 1 张人设图 + 4 张手绘正文图 | S5 只做封面，正文图暂用真实产物图替代 | 本账号的证据是操作截图，不是手绘图；缺正文配图 Skill 是已知差距 |
| Step 4 确定性脚本排版，三主题参数 | S5 用 `md-wechat-layout` 渲染，只翻译格式不改字 | 同思路；排版不用 AI 是对的 |
| Step 5 八平台改写 + 同步 + 执行报告 | S6 人工发布 + 回流入库，多平台留人工待办 | 改写有杜撰风险，先不做；回流是本地知识库的真优势 |
| 第九节 固化成总调度 Skill | 就是 `gzh-daily-pipeline` | 流程相同，验收更严 |
| 第十节 定时任务、断点续跑、批量矩阵 | 断点续跑已做，定时与批量矩阵待做 | 断点续跑是刚需，批量矩阵等有稳定产出口再说 |

## 我们的差异化

**证据关口。** 飞书流程是「热点 → 自动成稿」，成稿质量依赖 Skill 提示词和评审打分。
我们多一道硬关口：没有作者亲测记录，正文不能确认，只能交骨架。
这条与 [[topics/证据与边界库]] 一致，也是 [[concepts/公众号写作风格DNA]] 的底线。

**知识库驱动。** S0 到 S2 都要先查知识库：[[topics/选题问题库]] 给读者问题，
[[topics/AI写作案例库]] 给任务原型，[[topics/测评问题与实战技巧库]] 给验收点，
[[topics/文章写法库]] 和 [[topics/观点与表达库]] 给结构与表达。
S6 把成稿写成 source 页回流入库，下一轮选题反哺。
这一点跟 [[topics/公众号内容生产线]] 里既定的知识库驱动设计是同一条线。

**脚本验收而不是口头确认。** 「这条稿能不能发」有确定答案：实测记录在不在、
必须修改项清零了没有、标题选定后封面在不在、排版产物齐不齐。

## 已知差距

- **缺正文配图 Skill。** 封面有 `gzh-webchat-cover`，正文插图暂时用真实产物截图，
  没有「shot list → 出图 → qa-checklist」这一环。
- **没有多平台分发。** 八平台改写涉及删改和杜撰风险，v1 留人工待办。
- **新选题契约尚无本次运行证据。** 六类来源、候选比较和最小试跑是当前设计，不能声称已自动采集、已筛出优胜题或已验证传播效果；依据 [[topics/公众号每日选题决策]] 的真实记录继续修正。
- **S0 的 `00_style.md` 还没有正式落库。** 流水线假定它存在，
  目前内容分散在 [[entities/程序员拾梦]] 和风格 DNA 页里，需要正式合并成一份基准文件。
- **飞书文档只读到约八成**，Step 5 尾部细节、第九节与第十节正文未读，
  上面表格里涉及这三处的描述只基于目录标题。

### 已替换的历史方案

2026-10-23版S1和S5曾调用 `wechat-viral-topic`，S1设为3个候选、8维打分及30分淘汰线。其维度与阈值没有经过对照验证，属于旧设计而非有效性证据；2026-10-26用户决定重建后，不再保留这套评分或旧技能的活动依赖。既有历史产物如记录旧 `source_skill`，只表示当时来源，不代表当前仍应调用该技能。

## 怎么用

一句话触发：「跑今日流水线」「公众号流水线」「从选题到排版走一遍」。
单环节需求不要走总调度，直接调用对应 Skill。
已经有实测材料或成稿时，从对应阶段接上，不必从头跑。

详细字段、状态取值与自查清单见 Skill 内的 `references/handoff-contract.md`
和 `references/stage-checklists.md`。

## 多 Agent 化改造评估

2026-10-26 评估了「本流水线是否改造成多 Agent 协作」，结论与逐阶段可拆性见
[[comparisons/公众号流水线多Agent化改造评估]]：建议只改 S1 选题（分来源并行搜集）与
S4 定稿检查（分层并行检查）两处，S0、S2 实测、S3 写作、S5 排版、S6 入库保持单代理顺序执行，
人工关口不动。本页的七阶段划分与交接契约是该评估的基准，改造方案若落地需回写本页。
