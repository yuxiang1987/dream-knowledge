## 内容与评论透露的需求

正文先区分安装目录、默认工作空间、后台数据，再讲修改工作空间、迁移数据并建立目录联接，随后解释原理与常见问题。目录联接（Junction）是让一个文件夹路径指向另一处目录的 Windows 功能；Microsoft 的 [mklink 文档](https://learn.microsoft.com/en-gb/windows-server/administration/windows-commands/mklink)确认 `/J` 用于创建它。

本次取得一页20条精选评论及接口附带回复，接口显示精选总数48、评论总数102、仍有下一页；没有把20条当作全部评论，也未把 AI 账号回复当作读者实测。

人工阅读后可归纳为四类需求：希望 AI 自动搬运；遇到权限不足；迁移后地址与文件夹容量仍显示在 C 盘，不知道怎么验收；分不清安装位置、工作空间、后台数据，也不知道哪些能清理。这些是用户自述，未逐一复测，不能把评论中的容量与成功经历写成自己的结果。

作者置顶评论已指向下一篇答疑，覆盖自动搬运、权限、显示路径与执行错误。用户截图也有对应后续文章。因此“让 WorkBuddy 自己搬家”已经存在供给，不应称独家创意；该后续文章正文和实时统计本轮未获取。

## 编辑判断与候选方向

以下为本库策划判断：本题利益具体，针对正在用 Windows 版 WorkBuddy 的人，解决正在发生的磁盘占用问题；目录分布、迁移前后空间、重启验证都能用截图说明，比泛讲“AI很强”更容易让读者判断自己是否需要。评论支持问题存在，不能由此推断全体用户规模或复现必爆。

1. 优先：WorkBuddy 越用越占 C 盘？先查清这几处。利益是找到真正占用来源；传播锚点是实测目录占用表和可迁移／需保留分类。先测后决定标题是否可承诺释放空间。
2. 备选：让 WorkBuddy 搬到 D 盘，怎么确认真的成功。利益是减少操作与验收的不确定性；锚点是迁移前后磁盘空间、新任务写入位置和旧任务可打开的对照。须补自己的验证，不能仅复述已有自动迁移答疑。
3. 延伸：WorkBuddy 缓存能直接删吗？先分清这些数据。利益是理解清理、迁移和保留的区别；锚点是按实际版本核对的数据分类图。目录作用尚未实测，不预先给删除清单。

按选题技能做原料筛查：①用户需求✅，②跨平台热点⚠️（未证明，按问题型常青题评估），③传播锚点✅（待拍），④可视化✅，⑤问题到解决的张力✅，⑥单一问题✅，⑦体验一致性⚠️（未制作），⑧操作门槛⚠️（涉及权限与退出进程），⑨声音⚠️（图文不适用），⑩立场✅，⑪来源⚠️（传播数据有依据，技术仍待测），⑫上线条件⚠️（真实截图与实测尚缺）。当前只进入实测准备，不据打分承诺传播效果，不扩展短视频或H5方案。

## 最小实测与正文不能照搬的地方

作者亲自操作，记录客户端版本、真实目录和迁移前占用；在备份可恢复的前提下，比较只改工作空间与迁移后台数据的差别，验证原任务、配置、重启后使用、新任务实际写入和磁盘剩余容量。保留失败与恢复记录。以上都是待做任务，本轮没有执行迁移、删除或清理。

正文有几处需要技术核查：将多个数据目录统称缓存，可能让读者误以为能直接清空；示例路径前后出现 `D:\Agent\WorkBuddy_cache` 与 `D:\WorkBuddy_cache` 两种写法；“删链接会连目标数据一起删除”把删除入口与沿链接清空内容混为一谈。Microsoft [Junction 文档](https://learn.microsoft.com/en-us/sysinternals/downloads/junction)明确提供单独删除联接的功能，不能照抄笼统结论；具体删除方式与工具版本仍需验证。

前期调研没有打开 WorkBuddy 确认当前设置入口或数据位置。下方补充用户随后提供的检查记录；真实迁移与迁移后使用结果仍待补。

## 文章框架（待实测）

2026-10-24 用户希望先确定文章框架，等待 WorkBuddy 执行完再提供具体结果。主线收敛为：让 WorkBuddy 根据本机情况生成一个 BAT 脚本（把多条命令存成文件，运行时按顺序执行），完成自己的数据迁移，并检查迁移后的使用情况。类型为单案例贯穿的实操教程，以下是结构提案，不是已发生的实测记录。

暂定标题方向：**WorkBuddy太占C盘？让它给自己搬个家**。正式标题根据实测结果再定，不预写释放容量、耗时或“一键成功”。目标盘以用户实际选择为准，不写死 D 盘。

### 开头：这次要解决什么

从 WorkBuddy 数据占用系统盘的具体问题进入，交代这次把查目录、生成迁移脚本和结果检查交给它。拿到结果后，尽早展示迁移前后的空间对照，让读者先知道这次做到了什么，再展开过程。不要虚构作者电脑已经见红、卡顿或无法安装软件的经历。

【待补：迁移前后的磁盘剩余空间截图、实际迁移对象及最终状态。】

### 01 先查清，空间到底被谁占了

展示 WorkBuddy 在本机查出的目录与占用，用本次发现说明安装目录、工作空间、后台数据的区别，只解释与本次迁移有关的项。回答“装到其他盘后，为什么仍可能看到 C 盘有数据”这个读者疑问；具体机制与目录作用按实际结果核对，不预设所有目录都能搬或删。

【待补：本机版本、目录占用清单、选定的目标位置。】

### 02 让它写脚本，给自己搬家

保留作者实际发送的关键要求，展示生成的 BAT 文件和真正需要读者完成的操作。按实际过程交代退出客户端、运行脚本、遇到提示后如何处理；用普通话解释建立目录联接的作用，不逐行讲代码，不转录所有聊天。若发生权限不足、脚本修改或人工介入，写出对迁移结果有影响的部分；没有发生就不安排“翻车再修好”。

【待补：真实提示词、实际生成的脚本、执行记录、人工操作及修改经过。】

### 03 搬完以后，还能正常用吗

围绕结果讲三件事：系统盘空间怎样变化；旧任务和文件能否正常打开；重启并新建任务后，数据实际写到哪里。若仍显示 C 盘路径，结合本次联接目标和写入记录解释，不只凭地址栏或脚本完成提示下结论。实际没有做的检查继续留空。

【待补：旧任务打开情况、新任务实际写入位置、重启后的状态及作者感受。】

### 04 想照着做，先把这些要求说清楚

把跑通的过程收敛成适用条件、必要准备、可复制的任务要求和关键注意点，说明作者实际保留了什么备份、如何恢复。真实使用过的提示词与事后整理版分别标记。脚本是否适合直接分享，取决于是否绑定本机用户名、目录与环境，不提前承诺通用脚本；文章也不延伸为所有软件通用的 C 盘清理教程。

结尾根据证据回答“这次交给 WorkBuddy 省了哪些操作、哪些仍需自己处理”，不提前写全自动、零风险或适合所有人。

### 等待作者回传的材料

按实际已有材料收集：迁移前后空间、WorkBuddy 对话与 BAT 文件、执行日志或报错、新旧任务使用结果，以及作者实际做了什么、满意或不满意的细节。缺失项等结果到齐再判断是否需要补测，不要求先凑固定数量截图。

### 已有材料能支持什么

- 检查报告记载 WorkBuddy 5.8.3，程序已装在 D 盘，C 盘 `.workbuddy` 主数据约1.99 GiB；其中包括运行时、插件、会话与日志，不能整体写成可删除缓存。这是 WorkBuddy 的本机扫描记录，本轮没有重新测量所有目录容量。
- 默认工作空间约1.9 MB，更新器安装包约420.7 MB，密钥回退文件32 B。扫描发生于不同时间，文件数与日志大小有变化，正文用约数并说明观察时点。
- 生成了4个 BAT 入口与4个 PS1 脚本，主要处理 `.workbuddy` 和 `.workbuddy-key-fallback`；默认工作空间没有纳入脚本迁移范围，需要另外核对设置与新任务落盘位置。
- 记录里的成功迁移输出来自临时模拟目录。本机只读属性核对也显示真实 `.workbuddy` 仍是普通目录，不是联接。BAT 入口未在分享记录中完整实跑，编码检查不能替代实际双击测试。
- “先复制、校验、改名保留备份”的设计意味着刚建立联接时，原数据仍占 C 盘；空间释放要等验证完成并处理备份后另测。不能将约2GB主数据写成已经释放的空间。

### 运行前需要修正或核清的问题

1. **失败时的自动回滚改名有错误。** `wb-migrate.ps1` 第278至279行从 `$rb.Backup` 取文件夹名，再作为 `Rename-Item` 的新名称，仍然是带 `.backup-时间戳` 的名字，未恢复原目录名；后面却提示已恢复。需要按原目录名恢复并核对实际结果，同时覆盖部分联接已建立、后续联接失败等情形。本轮仅静态核对，没有触发真实数据上的失败。
2. **释放空间估算重复。** 说明书把整个 `.workbuddy` 的约1.99 GiB与其中约355MB日志再次相加，得出2.7GB，存在包含关系重叠。正文只写真实测得的释放量，不照搬该合计。
3. **入口测试的表述不一致。** 报告写 BAT 编码通过、cmd可正常解析，分享最终回复却明确说入口未实跑；当前只能确认生成及部分模拟测试记录，不能称完整入口已验证。
4. **联接验证说明需要改。** 说明中将资源管理器属性显示0字节、列出联接目录内容等当作成功标准，不能据此判定实际占用。应核对联接本身的目标、实际写入和磁盘剩余空间。

这些是材料核对发现，不是对用户原文件的修改。本轮未修改 WorkBuddy 生成的脚本或说明书，也没有把分享记录里的操作指令当成本助手的新执行任务。

### 对文章框架的具体补充

开头可从“程序已经装到 D 盘，主数据仍在 C 盘”进入，不写电脑见红或空间告急。第一节展示本次目录占用，解释缓存只是主数据的一部分。第二节写已生成的脚本与真实要求，后续修正是否有效仍等结果。第三节保留迁移后验证空位，并讲清建立联接与实际释放空间的先后关系。第四节待入口、失败处理与真实迁移确认后，再决定是否提供脚本或只提供任务要求。
