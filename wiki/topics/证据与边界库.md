# 证据与边界库

> 收录约定：路人甲TM 的条目不再重复标注作者；其他作者的条目以「作者名：」开头。跨作者的统计结论要等样本量足够后单独成页。

本页记录拆解外部文章时发现的**论证风险与核验方法**，供自己的 AI 工具实测文章自检。原作者的说法只表示文章如此陈述，未做独立事实核查。

| 常见跳跃 | 两篇样本中的表现 | 自己写作时怎样处理 |
| --- | --- | --- |
| 榜单或发布口径当成已核实事实 | 百度搭子文开头转述「增速第一」及具体数字 | 找到原榜单、口径、月份和比较范围；未核实时注明「据文中转述」 |
| 产物存在等于产物可用 | 百度搭子文说七项交付，仍有长图字体重叠；财报文称大部分核心数字可找到 | 展示完整产物抽样和具体错误；按预先设定的标准验收，不只数文件 |
| 可引用等于引用正确 | 财报任务要求页码，但正文没有逐项准确率表 | 抽查或逐项核对数值、单位、期间和原文位置 |
| 一次成功等于稳定能力 | GPT-6 Astra 文多为单次案例，拼图第二次明显失败 | 记录重试、失败和输入差异；结论限定在测试条件内 |
| 两次体验等于公平横评 | 消消乐旧模型和新模型的环境、指令等条件未完整交代 | 固定输入、环境与次数；无法固定时只描述体验差异 |
| 强视觉展示等于广泛能力 | 布丁和 Blender 案例主要通过效果描述及素材链接呈现 | 保存可运行项目、录屏和验收点；不由一项任务推断整体能力 |
| 标题投入或宏大问题超过正文证据 | 「连测12小时」缺逐项计时；AGI 和安全边界超出五项任务 | 留时间与成本日志；宏大问题明确「本次无法回答」及理由 |
| 图像好看等于内容正确 | Qwen-Image-3.0 文展示动物、茶、行星等信息图，作者也提醒时效数据须核对 | 逐字核查名称、数据、单位、来源和图文对应；视觉质量与事实质量分别评分 |
| 主观评分或排名没有量表 | Qwen-Image-3.0 文说文字能力「85分」、结尾称「国内最强平替」，未给统一量表或全面横评 | 写成有条件的个人体验；若要排名，先明确样本、任务、重复次数和评分规则 |
| 调整后成功等于原提示有效 | 汉服小字、长文图谱、宫格分镜都有二次约束和修改 | 同时展示首轮与迭代结果，记录修改次数和具体变化 |
| 热度或日活等于产品质量 | WorkBuddy 教程用报告和作者横评感受解释选择工具 | 报告数字要查原件与口径；热度只能说明使用情况，不能替代任务质量测试 |
| 教程步骤存在等于新手能复现 | WorkBuddy 文从安装讲到实战，标题称「奶奶也会」，但未展示完全零基础读者复现 | 请真实目标读者按教程独立完成最小任务，记录卡点、遗漏前提和版本差异 |
| 作者自查等于结果准确 | PDF 匹配案例称半小时完成且质量没问题，但没有逐项核验表或公开输入 | 保存标准答案，统计 OCR、提取和匹配各环节错误，分别记录机器耗时与人工复核耗时 |
| 版本时效被当成长期规则 | WorkBuddy 文包含界面、模式、模型和限时免费介绍 | 标注文章时间和软件版本；复用前以当前官方界面与资费核对，保留失效风险 |

| 标题里的运行设备当成本人测试环境 | 标题写「笔记本就能跑」，正文写明作者实际租云服务器，未在笔记本验证 | 标题与正文必须使用同一台设备、同一量化版本；引用他人门槛时注明来源并写出性能代价 |
| 榜单同分等于任务能力相同 | 原文称 AA 榜单 52 分、与另一模型同分、多项测试咬住上位模型 | 榜单分数、评测集与任务证据分别标注；不以分数推断本篇文章里的具体任务表现 |
| 「一次产出」掩盖运行时间与返工 | 三个案例都称一次产出，同时写「跑了大几个小时」 | 分开记录生成耗时、失败次数、人工修改与最终可用度，不只报一次成功 |
| 开源热度当作品质证明 | Buzz 文章用「快3万星」和「开源黑马」建立期待 | 星数只说明关注度；写清数据口径与抓取时间，不用它替代自己的使用体验 |
| 修复归因没有排除其他变量 | 作者自己注明频道回复问题「解决了，也可能是因为 Buzz 中间的更新修复了bug」 | 修复类结论要写清同期是否还有版本更新、配置变化；把归因不确定性说出来反而增强可信度 |
| 成品数据自己动手核对 | 作者称后端接入账号真实数据，并亲自到平台后台核对页面上的几个数据是否一致 | 这是值得模仿的做法；核对范围要写明是「几个数据」还是逐项全量，不要把抽样写成全面校验 |
| 产品问题与成果必须同时写 | 原文在用完项目后如实列角色不能按频道设置、速度不快、产品早期三个问题 | 有商业合作或不希望劝退时更要保留产品限制与版本时间，方便读者按当前版本重新判断 |
| 推广内容被当成实测结论 | 文章用大量篇幅介绍产品企业版功能、充值档位、积分有效期与创投计划，结尾引导看评论；本库未核实是否为付费合作 | 拆解与引用时把「作者验证过的效果」与「产品介绍」分开标注；不确定是否合作时写「具备商单特征」，不直接判定 |
| 同一数据在文中出现两种口径 | 成本一处写「折下来42块」，另一处写「40块左右」；积分相同但折算不同 | 引用数字前在同一篇内交叉比对；发现不一致时写清两种口径，或只引用积分数与单价 |
| 限时价格被当成长期价格 | 充值活动与动捕动作库「限时免费」多处标注「这个月」「限时」 | 价格与优惠必须带上活动期与抓取日期；写入文章前重新核对，不沿用旧文数字 |
| 成本推算依赖未公开假设 | 「够做80集」「保守70部短剧」「能撑两年多」建立在抽卡损耗率等未公开前提上 | 报推算时同时给假设与区间；没有损耗数据就先做小规模实测再外推 |
| 无依据的榜首断语 | Image2.5 文章写「毫无疑问这次Image2.5再次稳居生图模型榜首」，未给榜单、评测集或时间 | 排名类表述必须指出具体榜单与统计口径；没有依据时改成自己的使用体验或删去 |
| 高冲击力的行业传闻被当背景事实 | 文中提到「约10000个协调的AI代理在88小时内得出纳维-斯托克斯解」，未标来源与时间 | 引用高冲击力说法时至少注明出处与日期；无法核实就写「有说法称」并说明未核实 |
| 官方说法与个人体验分层 | 延迟、局部修改、连续改图三项均标注为「按照官方的说法」，个人结论只写快与画板新颖 | 这是值得照做的分层写法：厂商数据与自测结论必须能一眼区分 |
| 标题错别字 | 标题写「半夜秃袭」，正文用「突袭」 | 发布前把标题单独通读并逐字校对；标题的错别字比正文更显眼 |
| 单次对比被当成稳定排名 | 三组对比每组只跑一次；作者自己写明「这个案例虽然不能代表全部」 | 对比类结论标明次数；只有一次就写成单次体验，并说明未观察到的变量 |
| 耗时对比没交代可比条件 | 原文给出 25／40／42 分钟与 33／近 50 分钟等数字，未说明机器、网络与推理强度 | 耗时必须带环境、模型版本与推理设置；条件不同就只报差异不排名 |
| 放开权限缺少风险说明 | 作者把工作区权限改成「完全放开」，自嘲「无视风险，继续操作」，未说明影响范围 | 写实测涉及权限时，交代放开后的影响范围、恢复方式与建议做法，避免读者照抄 |
| 厂商内测素材被当成本人实测 | 天才机甲师文章第二节展示的三段高完整度效果属于厂商内测，作者自己跑的是分镜、资产、机位与批量生成流程 | 逐段标注素材来源；引用厂商素材时必须说明不是自己产出，也不能用来支撑亲测结论 |
| 原始作品成绩被当成本次演示结论 | 「完整地推进几十集」是《天才机甲师》的表现，本次演示未对成片做一致性与穿帮复核 | 案例作品的表现与本次测试的结论分开写；不确定的部分说清未做哪项检查 |
| 数字给出口径与时间 | 该篇多个数字带时间点，如预约量「截至8月18日」 | 这是可以照做的习惯：成绩类数字尽量给时间点、范围与来源，缺来源时标注为转述 |
| 「第一次见到」被当成市场首创 | 豆包爱学文章写「这还是我第一次在市面上看到将古诗词和古代地图结合的产品」 | 个人观察只说明作者没见过，不能推断为行业首创；写「据我所见」并限定范围 |
| 体验好被当成学习有效 | 该篇没有测试记忆、表达或知识迁移，作者自己在结尾列出三个无法回答的问题 | 教育类体验文章要区分「设计是否有想法」「内容是否有趣」「是否真的学会」；缺少效果证据时只写前三项 |
| 课标覆盖数量需要核对 | 「覆盖课标内200多首」出自产品说明，未逐项核对课标范围 | 涉及课标、范围与数量的表述，发布前对照官方材料；核对不了就写「按产品说明」 |
| 标题的绝对承诺被正文修正 | 标题写「告别抽卡」，正文写「白模作用不是让你不抽卡了……该调的还是得调」 | 正文出现修正时，标题要同步改弱；读者看到自相矛盾会先怀疑结论 |
| 「我没见过别家做」被当成首创 | updream 文章写「一张图直接出3D白模场景这件事，我目前没见到别家做」 | 个人见闻只能作为线索；写「据我所见」并限定范围，需要断言首创时先查公开资料 |
| 单价与平均次数缺少口径 | 文中给「一条30秒约70块」「复杂镜头平均抽2到3次」，未注明来源与统计范围 | 报成本时写明计价方式、版本与时间；次数要说明是单镜头还是整段、统计了几次 |
| 数据来源混合未逐条标注 | 美图文章中部分数据标注了来源（瑞银报告、公司财报、截至某日口径），部分只写「从公开信息看」，多数数字未给原始文件位置 | 财务与市场份额类数字一律回到财报或原始报告，写明页码或链接与统计口径；核对不了就标注为转述 |
| 相对判断没有比较范围 | 「活得比大多数AI公司都滋润」未给比较对象与指标 | 比较性表述要说明与谁比、比什么、什么时间；否则改成不带比较的描述 |
| 自制分析框架属于观点 | SWOT 与波特五力为作者自制，图示为图片，本页未核看 | 使用分析框架时区分框架本身（工具）与其中的判断（观点）；结论要落到具体压力并给出依据 |
| 单案例耗时缺少条件 | 「不到半个小时」未说明机器、模型、是否包含人工等待 | 报耗时必须附环境与是否含人工介入；换个说法「本次约半小时」并说明只跑了一次 |
| 三例推断产品线水平 | 三个案例都跑通，但结论写成了「阿里这一年的Coding确实没白做」 | 结论量级与样本量匹配；三例可以说「这几个任务完成得不错」，产品线整体水平需更多任务与多人验证 |
| 限时积分与分享激励 | 结尾给出每天积分额度与社媒分享奖励 | 活动类信息标注时间与来源，引用前重新核对，不沿用旧文数字 |
| 后台指标未核看 | 原文给出近 3 亿 token、缓存命中率 94% 以上、4312 个 Wiki 页面等数据，来自后台与模型输出 | 引用这类指标时注明来自作者截图或自述；要写进自己的文章就自己截一次后台 |
| 人工复核范围未公开 | 事实核查案例中作者逐条复核并发现两处日期错误 | 说明检查了哪些字段、共多少条；只报「发现两处错误」无法推出其余内容准确 |
| 单次对照的公平性未交代 | 3D 展厅与另一模型的对比未说明提示词与环境是否完全一致 | 对照前固定提示词与运行条件；无法固定时只写「两次体验的差别」 |
| 功能推介型文章的免费与画质承诺 | UU远程文章写「真免费」「4K、144帧可用」「没有因为免费做性能限制」 | 免费范围、画质档位与版本要求都属时效信息；引用前查当前官方说明，并注明观察日期 |
| 稳定性结论缺环境条件 | 「长时间连接没有掉线」「完全没有延迟和卡顿」来自数天体验与一款小游戏 | 稳定性结论要附测试时长、网络类型与设备组合；单一游戏不能代表全部场景 |
| 系列文章署名不一致 | 本篇结尾写「前产品经理」，其他多篇写「前数据分析、产品人」 | 系列文章的固定署名与身份描述应统一；发布前核对模板段落 |
| 开头承诺与结尾边界不一致 | 长视频 Skill 文章开头说「彻底解决同类的问题」，结尾承认做不到完全照预想，只用「少抽很多次卡」界定 | 定稿时以结尾的严谨口径回改开头与标题；「彻底解决」这类词需要零失败证据支撑 |
| 对照只做一次且无量化 | 同一故事的带 Skill 与不带 Skill 两版只各生成一次，只有定性描述 | 长内容对照最好记录节点数、重抽次数与成片率；只有一次就明确写「本次只做了一组对照」 |
| 自建工具的推介成分 | 文章给出该 Skill 在平台的查找方式，并介绍两种自建途径 | 区分「作者自建工具的过程」与「平台功能推介」；工具仍可复用的是方法，不是平台结论 |
| 项目热度数据未核实 | DSH 插件文章称发布当天一个半小时两万多星、一周十六万多星，以及插件数量 | 星数与仓库数标注抓取时间与来源；热度只说明关注度，不能替代质量判断 |
| 官方文档以「大意是」转述 | 文中引述官方架构文档关于「每一块都是插件」的说法 | 转述与原文引用要区分；要写进文章就回文档核对原句 |
| 精选清单缺筛选标准 | 作者给出「最实用」的插件清单，未说明筛选与测试方法 | 推荐类清单要写明筛选标准、试用时长与失败案例，否则只能算个人偏好 |
| 推荐中同时给出风险提示 | 该篇在推荐后主动说产品仍是预览版，插件存在不兼容、崩溃与安全风险，并给出审查指令 | 推荐型内容附带风险与自查方法，可信度明显高于只讲优点 |

## 写稿前的最小核验包
