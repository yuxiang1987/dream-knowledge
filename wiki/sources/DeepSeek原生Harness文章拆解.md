# DeepSeek原生Harness文章拆解

来源：`raw/article/lurenjiaTM/不睡觉连肝三小时，deepseek原生harness首批实测来了!.md`，署名时间 2026-08-14 凌晨。截图与视频未在本页核看；界面、模式、耗时与对比结论均为原文自述，未独立核实。

## 定位、标题与开头

这是**新产品首批实测＋横向对比**。读者问题是：同一个模型接到官方 Harness 上，会比接入其他 Harness 更好吗，值不值得现在就用。

标题「不睡觉连肝三小时，deepseek原生harness首批实测来了!」由**投入感＋时效标签＋对象**组成，没有预设结论，属于本批样本里较克制的一类。正文确实在发布后数小时完成三组测试，投入与时效都成立；「首批」的依据是发布时间与作者自述，平台侧未核实。

开头极短：直接报发布（「就在刚刚」），加一句行业调侃，交代动机（迫不及待想感受），宣布投入（深夜爆肝三小时先探水）。钩子类型是**即时发布＋行业调侃＋投入宣告**。时效型首发文章可以借这种短开场抢时间，但代价是缺少背景铺垫，读者若不关注该厂商会缺少上下文。

## 结构与推进

1. **发布与动机**：只交代时间、动机和测试承诺。
2. **怎么快速用上**：给出一条可复制的安装指令，让 Codex 或其他 Agent 完成装包、环境检查、启动 Web UI、HTTP 校验与回报版本。
3. **功能与界面**：接入自家 API；列功能（读写工作区文件、执行命令、搜索网页、调用工具与 Skills、管理任务计划与上下文、拆给子代理、会话权限沙箱与运行轨迹）；标出工作文件夹、模型与思考强度、三档权限；介绍四种模式（标准、批量任务、极简、创造）与「一切皆插件」理念。
4. **案例一 3D 黑洞引力模拟器**：固定同一个模型，分别接入三种 Harness 做同一任务。
5. **案例二 创造模式做自定义 Agent**：创建一个面向小店老板的门店宣传助手，中途出现循环故障并解决。
6. **案例三 复杂数据处理**：同一模型分别接入 WorkBuddy 与官方 Harness 处理同类数据任务。
7. **小结**：任务能做、质量没问题，但耗时明显更长，产品处于公测阶段。

**最值得学的是案例一的对比设计**：固定模型、只换 Harness，让「Harness 对结果影响很大」这个结论有可追溯的来源。作者也主动限定「这个案例不能代表全部」。局限是每组只跑一次，且未交代机器、网络与推理强度是否一致。

## 三组案例与结果

| 案例 | 设计 | 原文结果 |
| --- | --- | --- |
| 3D 黑洞引力模拟器 | 同一模型分别接 Claude、DeepSeek 官方、Hermes 三种 Harness | Claude 25 分钟，作者认为视觉与交互最好；官方 Harness 40 分钟，效果炫酷、参数变化丝滑但偏慢；Hermes 42 分钟，效果零散、细节少 |
| 创造模式做自定义 Agent | 先配置一个门店宣传助手（面向不懂代码的小店老板），再用一句信息不完整的需求试探 | 过程出现故障：模型反复执行 `Bash noop` 占位动作，思考里提示应调用另一动作却回到原处；作者终止任务并追问原因后，它改用文件系统操作完成预设文件与加载检查。此后用不完整需求测试，Agent 主动补问且控制在三项以内，3 分钟完成网页 |
| 复杂数据处理 | 同一模型分别接入 WorkBuddy 与官方 Harness，处理同类数据任务 | WorkBuddy 33 分钟完成，还指出已有流程的问题并给修改建议；官方 Harness 20 分钟时报错停下，继续后近 50 分钟完成，产出质量没问题但耗时更长 |

## 可复用资产与技巧

- **可复制的安装指令**：要求先核对包信息、再检查 Node 与 npm 环境、安装最新版本、启动 Web UI、用 HTTP 请求验证页面可访问，最后回报安装版本与启动命令。这是把「装好并自证可用」写清的一条完整指令，可迁移到其他工具的安装任务。
- **故障打断经验**：原文建议「看到连续几次相同操作时最好及时打断」。这是对 Agent 循环故障的通用处置方式：先终止，再追问原因，然后让它换路径继续，而不是等待它自己恢复。
- **自定义 Agent 的复用价值**：作者指出标准模式同样能做好单次网页任务，自定义 Agent 的优势在重复使用——店铺信息每次可换，而提问方式、手机适配与交付检查这些固定要求留在预设里，不必每次重说。这个判断比「自定义更高级」更具体。

## 证据与边界

三组对比每组只跑一次，耗时差异受机器性能、网络、推理强度与任务细节影响，原文没有交代这些条件，因此只能作为单次体验。作者自己写明「这个案例虽然不能代表全部」，也承认结果没达到预期，并给出合理归因：产品处于公测阶段，加上此前对模型的期望被拉高。

需要额外提示的是权限操作：作者把工作区权限改成「完全放开」并自嘲「无视风险，继续操作」，正文没有说明该设置的具体风险。写自己的实测时，权限放开应交代影响范围与恢复方式，不要让读者照抄。结尾还把 Harness 拼写为「harnsee」，正文另有若干笔误，发布前的拼写检查可以更严。

## 结尾与写作卡片

结尾没有为产品找补，而是直说耗时比接其他成熟 Harness 多、当前不够成熟、自己有些失望，同时保留对正式版的期待。这种**如实报告不达预期、并给出一个具体原因**的收尾，比强行给出「值得期待」更容易被信任。

**写作卡片**：适合新产品首批实测 → 用极短开场抢时效 → 先给一条能直接复制的上手指令 → 功能只讲能动手的部分 → 横向对比时固定模型只换变量 → 如实写出故障、报错与耗时劣势 → 结尾用具体原因解释不达预期。
