### 结构推进

第一节先建立总模型：每次请求重新组装输入，并把“当前上下文、会话历史、长期记忆”分开。第二节解释上下文管理器、工具结果限长和 token 阈值。第三节展开轮次前、轮次中及手动压缩，并区分 Token 预算、远程压缩和本地总结；本地总结又拆为交接摘要、保留部分用户原话和重新补入规则。第四节引入 JSONL Rollout、CompactedItem 与 checkpoint，用“快照加增量日志”解释恢复。第五节转向默认关闭的本地长期记忆，按单任务提炼和跨任务整理两阶段说明租约、去重、冲突与文件分层。第六节解释目录式渐进读取、文本搜索、引用、用户纠正和分批淘汰。结尾回到面试题，给出一段聚焦上下文压缩的标准答案。

### 逐例证据与人工成本

- 本地压缩流程是机制示例：输入为当前历史和专门压缩指令；操作是模型生成覆盖进度、决定、偏好、限制和剩余工作的交接摘要，并保留有限的近期用户原话；预期结果是以较小替代历史继续任务。原文没有给出某次真实压缩前后的 token、摘要全文、遗漏项或任务成功率，人工修正、耗时和成本未提供，证据身份为官方主张整理。

- 任务恢复用“数据库恢复里的快照加增量日志”作类比：目标是重开同一任务；输入为最近有效 checkpoint 与其后的消息、工具结果；操作是恢复精简历史并顺序补入增量；结果是重建继续执行所需上下文。这是作者的机制解释，不是数据库实现实测，没有失败恢复案例、文件样本或性能数据。

- 长期记忆两阶段流程的目标是跨任务复用稳定经验。第一阶段从空闲旧任务的 Rollout 提炼 raw memory 和摘要，第二阶段跨任务合并、核对冲突、删除失效内容并更新记忆文件；新任务先看 memory_summary.md，再按需查 MEMORY.md、skills 和来源 Rollout。没有提供真实记忆文件、命中案例、误记率、纠正耗时或对任务质量的前后对比。

### 解释、观点与可证范围

作者的总归因是：模型本身不会在两次推理间保存任务状态，连续性来自客户端再次组装输入；上下文窗口有限，因此需要限长和压缩；同任务恢复依赖模型外持久化；跨任务复用则依赖异步提炼、整理和按需读取。进一步解释了租约避免重复处理、文件分层减少上下文占用、引用次数和最近使用时间辅助后续筛选。以上内容虽呈现为源码级叙述，但原文未锁定“本文分析的 Codex 版本”，也没有源码链接、commit、测试或官方文档锚点，因此只能标为作者解释或官方主张整理，不能确认所有部署、模型服务和未来版本都如此实现。
