### 它讲什么

**目标读者**：准备把 Claude Code 或其他编程 Agent 引入遗留系统升级、技术栈迁移或业务重构的技术负责人、架构师、研发经理，以及需要参与验收、审批和预算评估的业务与管理人员。文章尤其针对“AI 能快速改代码，但团队无法证明改对、审得过、上得去”的组织协作问题，不适合被当作某个具体仓库的即用迁移脚本。

**主问题**：在允许 AI 批量修改遗留代码之前，团队应怎样明确改造边界、建立可自动核验的验收标准、安排分级审核、准备环境与权限、试跑工作流、逐步推广并估算成本，从而避免生成速度超过验证和上线能力？

**主分类**：发布解读

**主要证据身份（各例身份见下）**：官方主张整理

### 标题承诺与开头

标题用“祖传代码”“泼天的技术债有救了”制造强情绪和解决希望，正文开头随即把承诺收窄为对 Anthropic 官方博客《How to prepare for AI-driven code modernization projects》的中文整理，并没有展示作者亲自重构某个遗留项目。开篇通过“一个不起眼的判断可能藏着多年业务规则”和“审核人员不会批量出现”建立风险钩子，把读者关注点从 AI 会不会写代码转到谁来确认正确性。正文确实交付了目标、验收、审核、资源、工作流、推广和成本七个环节，因此方法框架得到兑现；但标题暗示的“技术债获救”没有以真实上线结果、前后指标或独立测试兑现。

### 结构推进

先以老项目不敢动和审核瓶颈提出矛盾，再用“一、旧系统到底要改成什么”区分版本升级、技术栈迁移和重新设计，并引入 assess、map、extract-rules 等插件工作流。第二部分转向可验证性，列出测试、覆盖率、性能、静态分析、安全扫描、新旧输出对比、请求回放和预发布观察。第三部分处理人工审核吞吐，提出按业务影响和证据分级。第四部分扩展到远程主机、测试数据、依赖、冻结范围、权限、脱敏和审计记录。第五部分说明如何把目标与工具交给 Agent，并强调小范围试跑后修正工作流。第六部分从试点转到完整上线演练和按依赖顺序分批迁移。第七部分讨论 token、验证、返工和模型分层成本，最后压缩成两个开工前问题并邀请读者自检。转场基本采用“前一步解决后还缺什么”的连续追问。

### 逐例证据与人工成本

- 文中的 C++11 升 C++20、COBOL 迁 Java、订单超时自动关闭、A 调用 B 且 B 调用 C 等均是说明方法的假设示例，不是完整项目案例。目标是说明改造类型、规则提取或迁移顺序；输入仅为抽象代码关系或业务规则；操作是让插件评估、制图、提取规则并由团队核对；结果仅描述预期可获得报告、关系图或规则说明。未提供真实仓库、锁定插件版本、实际输出、错误率、人工修正、耗时和成本，证据身份为官方主张整理。

- 请求回放、新旧系统并行处理同一输入、预发布环境观察以及让 Claude 操作界面，属于建议的验收手段。材料没有报告作者执行过这些测试，也没有样本量、差异结果、性能基线或上线结论；人工修正、耗时与成本未提供。

- “试跑十处地方，有五处犯了同一种错”是教学性假设，用于说明不应只逐项手修，而应修改 Agent 步骤或验收规则。它不是作者真实失败记录，不能转述为 50% 错误率或实测表现；实际成本和修正时间未提供。

### 解释、观点与可证范围

作者的核心归因是：遗留系统改造的主要约束不是代码生成速度，而是业务规则不透明、验收证据不足、人工审核稀缺、跨团队资源与上线责任未预先安排。文章进一步主张，小范围试点可以记录 token 与重试情况、暴露重复错误，并据此改造工作流和推算成本下限。关于 Code Modernization 插件能执行 assess、map、extract-rules，以及 Claude 可独立审查、操作界面和搭建多 Agent 流程的内容，均来自作者对官方材料的转述或机制解释；原文没有锁定 Claude Code、插件、模型和服务端版本，也没有独立核验，不能视为已证实的稳定能力。可确认的只是文章给出了一套治理清单和建议逻辑。

### 语言、图文与结尾

语言以口语反问和团队会议情境推进，如“谁来验、谁来审”“钱包扛得住吗”，句子短，技术术语后通常补中文解释，降低管理型内容的阅读门槛。分隔线和编号承担长文导航作用；文字提到关系图、报告和界面操作，但本次仅有正文，图片、视频、音频未观看，不能评价其图示质量或演示效果。结尾不再扩大能力承诺，而是要求团队先确认允许改变哪些业务结果、具备哪些证据才愿意合并，并以项目痛点提问促评论。

全文没有作者亲测仓库、代码 diff、测试日志、PR、上线指标或真实预算，不能称为实操测评或成功复盘。插件输出是否准确、业务规则能否完整提取、独立对话能否降低漏检、模型分级是否省钱，都需要具体版本和对照实验。文章没有证明所有遗留系统都适合 AI 改造，也未给出覆盖率、性能阈值的通用数值；监管、安全、许可证及数据合规仅被提示，没有法律或行业细则。发布日期晚于当前常见公开时间线的信息也不应据此推断产品已经发布或能力已落地。

### 可迁移的编辑动作

编辑可复用“风险场景开篇—按项目阶段拆清单—每节用质疑推动下一步—结尾压缩为两个开工问题”的结构。写类似文章时，应在标题后尽快说明是官方资料解读而非亲测；把“版本升级、换技术栈、重新设计”做成第一张决策表；将每个能力表述改写为“输入、输出、人工核对、失败处理”；把验收条件与上线责任放在生成步骤之前；成本部分明确区分写代码、验证、返工和同步成本。若要升级为实操内容，必须补仓库范围、版本、基线、试点记录、人工修改和最终上线证据。
