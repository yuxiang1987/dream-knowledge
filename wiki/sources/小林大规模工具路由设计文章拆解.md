### 它讲什么

**目标读者**：面向准备 Agent、LLM 应用工程面试，或正在处理几十到上百个工具接入、权限隔离、工具检索与线上评测的开发者。读者需要理解 Prompt、Schema、Embedding、鉴权和 Agent 编排等基础概念；本文不是零代码入门，也没有提供可直接运行的完整工程。

**主问题**：当单个 Agent 可接入大量工具时，怎样在不暴露无权限能力、不过度占用上下文的前提下，召回少量相关工具交给模型选择，并建立参数校验、失败兜底和评测闭环？

**主分类**：新手教程

**主要证据身份（各例身份见下）**：官方主张整理

### 标题承诺与开头

标题用面试官追问制造冲突：先给出“Schema 全塞进 Prompt”的直觉答案，再以“撑爆上下文”否定，引导读者寻找更工程化的 Tool Routing 方案。开头继续通过三轮问答依次排除全量 Schema、简单拆成多 Agent、Embedding 第一名直接执行，承诺讲清工具路由与多 Agent 路由的区别以及完整链路。正文确实交付了注册表、过滤、粗分类、检索、动态绑定、执行校验、指标与兜底，兑现较完整；但它是设计解释和面试答题框架，不是某个锁定版本系统的实测报告。

### 结构推进

先用面试对话暴露三个常见误区；“简要回答”给出从注册表到动态绑定的总览；“详细解析”先列全量工具带来的 Token、混淆、权限和延迟问题，再定义 Tool Routing 与 Multi-Agent Routing。主体按步骤展开：建设工具卡片、确定性过滤、粗分类、候选域检索、向 LLM 动态绑定完整 Schema；随后补充 Skill 渐进加载、工具描述质量、分层评测和失败兜底。伪代码承担从概念到流程控制点的转场，最后用“面试总结”压缩成可口述答案，并以资料清单导向站点、课程和项目。

### 逐例证据与人工成本

- 订单任务是解释性示例：输入为“查询订单 A100，确认未发货后帮我取消”；操作是 Orchestrator 先把任务交给订单 Agent，再让订单 Agent 先看到 order_get，确认状态后暴露 order_cancel；目标是区分 Multi-Agent Routing 与 Tool Routing。原文没有实际运行日志、输出结果或成功率，因此结果仅为作者设定的预期流程；人工修正、耗时、成本均未提供；证据身份为作者构造示例，不是作者亲测。

- 伪代码是方案材料交付：输入为 query、context、registry；操作包括按产品、租户、角色、环境和健康状态过滤，以分类置信度决定是否收窄业务域，再混合检索 top_k=6 并绑定完整 Schema；结果只是展示控制点。作者明确说阈值和 Top-K 不是通用最优值，未提供运行环境、评测集、执行日志、人工修正、耗时或成本；证据身份为作者解释。

### 解释、观点与可证范围

作者把问题归因于候选空间过大、工具边界重叠、权限暴露和输入膨胀，并提出“先鉴权过滤、再高召回检索、后由模型精选、执行层复验”的分层机制。可由正文确认的是方案组成、建议指标和风险意识；不能由本文确认的是该架构一定降低延迟、提高成功率或适用于所有工具库。关于 OpenAI Agents SDK、OpenAI 与 Anthropic 工具搜索、论文研究的描述均属于作者转述的官方或研究主张，正文没有锁定 SDK、文档、模型和论文版本，也无独立复现。Prompt Cache、动态加载和检索效果不能据此视为已证实能力。
