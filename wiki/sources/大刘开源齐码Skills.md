## 主问题

如何把模糊产品想法拆成可交接的需求、交互、架构、视觉、原型与实现文档，让零基础用户借助 AI 完成更规范、少走样的 Vibe Coding？

## 目标读者

适合有产品想法但缺少需求、设计或开发方法的新手，也适合已经使用 Cursor、Codex 等 Agent 做 Vibe Coding，却经常遇到需求漂移、页面状态遗漏、视觉不统一和反复返工的独立开发者。专业产品经理、设计师和工程师也可把它当作 AI 协作交付物模板参考，但不能据本文直接判断其对复杂生产系统的适用性。

## 主研究对象

核心对象是作者开源的「齐码.SKILL」工作流及其 GitHub 仓库，包含 vibe-idea、vibe-interaction、vibe-architecture、vibe-design、vibe-prototype、vibe-implement 六个相互衔接的 Skills；同时涉及 DESIGN.md、Google Stitch、Gemini 3 Pro、prototypes/manifest.json 和契约式设计等配套方法与工具。

## 证据身份与分项边界

主要证据是作者对自制工作流的设计说明，属于作者经验总结与产品主张，而不是带完整项目记录的对照测评。作者称该方案来自其“一年多做 Vibe Coding 和 AI 产品的经验”，并具体列出了六个 Skill 的输入、输出和交接关系，这是本文最实质的过程证据。关于 interaction.md，作者给出十一种交互呈现方式及 default、hover、pressed、disabled、loading、success、error 等状态要求，说明规则具体到了可执行层面。关于视觉与原型，作者提供了下载 Cursor DESIGN.md、导入 Agent 与 Google Stitch、逐页生成原型、下载到 prototypes/、再生成 manifest.json 的操作链。关于实现，作者描述了“不许多、不许少”的核销检查，但没有展示某个真实产品的代码、文档、原型对照图、测试记录或返工次数，因此“实现=设计”“不返工”“一处没走样”仍是作者主张。文中的“人的一瞬间想法95%是有价值的，但是真正产品化后75%都是辣鸡”被称为业界共识，却没有来源。关于 Claude Design、Harness Engineering、Design by Contract 的关系也仅作概念引用，没有独立论证。

## 标题承诺与开头

标题以“开源”“零基础”“兼具审美与规范”“做出你的产品”作出资源可得性和结果承诺。正文确实给出了仓库地址、六段工作流、主要文档产物和部分操作步骤，因此兑现了“开源介绍”和“教程框架”；但没有完整展示零基础用户从想法到上线产品的连续实录，也没有成品链接或前后对照，因而“做出产品”“高级审美”“不返工”的效果承诺只得到方法说明，未得到成品证据充分兑现。开头先用“做计划 -> AI写代码 -> 返工 x 10086 -> 删文件夹重来”的常见挫败建立共鸣，再把问题从模型代码能力转向人的思路、审美、架构和纪律，随后亮出六个 Skills，属于先放大痛点、再提出系统解法的钩子。另以“为什么叫齐码”制造轻悬念，最终用“对齐”收束命名。

## 结构与转场

开头先提出普通 Vibe Coding 的返工闭环，并完成核心判断：生成不是瓶颈，缺的是前置思考与环节对齐。随后用一条箭头链总览六个 Skills，并以“每一个 skill 的入口一定是上一个 skill 的产物”解释顶层结构。主体按 idea、interaction、architecture、design、prototype、implement 的生产顺序逐节展开：idea 负责验证痛点与立项；interaction 用交互类型和状态表消除歧义；architecture 从页面需求反推数据和技术栈；design 通过外部 DESIGN.md 固化视觉；prototype 借助 Stitch 生成并映射页面；implement 逐条核销文档。每节都以前一步的产物转入下一步，转场与文章所强调的“交接”理念一致。六节之后再次用两行概括各模块配合关系，再从工具层上升到“为什么做、为谁做”的产品判断，最后连接到契约式设计、宣布 GitHub 开源并号召互动。结构完整，但教程操作粒度不均：design 和 prototype 较具体，architecture 与 implement 只有原则，没有安装、调用、报错处理和验收示范。

## 案例：目标、输入、操作、结果与人工成本

案例1是作者设想的完整齐码流程：目标是把模糊想法变成可运行产品；输入依次包括初始想法、idea.md、interaction.md、视觉来源或 DESIGN.md、页面提示词与原型；操作是让六个 Skills 顺序产出文档、在 Google Stitch 中选择 Gemini 3 Pro 生成各页面原型、下载到 prototypes/，再由 Agent 建立 prototypes/manifest.json 并实现代码；作者声称结果可达到交互、视觉、原型和代码严格对齐。该案例没有给出具体产品主题、真实输入文本、最终产品地址、页面截图、测试结果、人工修正、失败次数、总耗时及工具成本，因此更接近标准流程示例而非完整亲测复盘。案例2是 Cursor 风格迁移示例：目标是让产品采用作者认可的 Cursor 视觉风格；输入是从 styles.refero.design 下载的 Cursor DESIGN.md；操作是在 Agent 中指定“@cursor-DESIGN.md”，再将规范传给 Stitch 生成页面；预期结果是形成包含色系、样式、组件、字体和布局的 design.md 与原型。作者未展示生成前后效果，也未交代是否手调、耗时或成本。案例3是 interaction 规格化方法：目标是避免按钮点击后弹窗、抽屉或跳页等歧义；输入是页面中全部可交互元素；操作是给每个元素限定十一种呈现方式之一，并补齐触发条件、步骤、七八种控件状态以及页面的加载中、空、出错、没权限状态；结果按作者说法是得到“没有第二种解读”的 interaction.md。未提供实际文档样例、AI 误读率或采用前后的返工对比。

## 解释、语言与图文作用

解释方式以产品流程拆解为主，反复使用“产出什么文档—为什么重要—下一步如何接收”的固定句法，降低了六个模块的理解难度。专业词后通常附白话解释，例如把 architecture 解释为从界面显示和可编辑内容反推数据表及前后端，把契约式设计解释为动手前说清“要做什么、谁对谁负责”。语言节奏短促、强调性强，大量使用“定死”“钉死”“从源头掐死”“一个不多、一个不少”等口语化动词塑造确定性；“非常非常非常”“高级、稳定、标准”等重复和断句增强传播感，但也让部分效果判断显得绝对。英文 Skill 名、文件名和交互术语保留原样，适合照着操作，却没有逐一翻译十一种交互类型。

## 结尾收束

结尾先从六个工具模块上升到人的责任：AI 可以核销交互，却不能替用户回答为什么做、做给谁。随后用 Design by Contract 为“对齐”补充软件工程来源，再把价值落到降低不会写代码者的实现门槛。最后公布 GitHub 仓库，邀请读者提出想法，并以点赞、在看、转发、星标和作者履历完成公众号常规收尾。情绪上从方法论转为技术普惠，强化了开源项目的使命感。

## 限制与不可照搬处

文章没有提供仓库版本号、支持哪些 Agent、安装步骤、运行环境、依赖项、许可证、默认技术栈内容、上下文消耗及兼容性边界；这些需到仓库独立核实。没有展示一个真实项目从 idea.md 到代码的全部产物，无法验证不同文档是否真的无歧义，也无法验证“实现=设计”“一处没走样”“审美不走样、不返工”。作者没有记录失败案例、AI 中途偏离、Stitch 原型质量不稳定、超长 interaction.md 占用上下文、需求变更后的同步成本等问题。视觉“高级”“完全没有 AI 味”属于主观判断，且依赖用户选择的 DESIGN.md。文中95%与75%的比例无来源；Claude Design、Harness Engineering 和契约式设计的具体继承关系未展开。Google Stitch、Gemini 3 Pro 等名称、功能、可用性、价格及版本状态均未独立核实。开源不等于相关第三方模型或服务免费，文中没有核算调用费用与时间成本。

## 可迁移的编辑动作

编辑类似开源方法文章时，可强制加入一条贯穿全文的真实样例：先给出一句原始想法，再依次截取 idea.md、interaction.md、architecture.md、design.md、原型 manifest 和最终页面的关键片段，让每节都沿同一案例推进。对每个 Skill 使用统一信息框：输入文件、核心动作、输出文件、人工审核点、常见失败、进入下一步的验收条件。把“高级”“不返工”“完全一致”等绝对词改为可检查指标，例如遗漏交互数、页面状态覆盖率、原型与实现差异清单、人工修改轮次。若面向零基础读者，还应在仓库链接前补充支持工具、安装命令、首次运行步骤和最低成本，并把十一种交互类型制成中英文表格。该写法适用于有稳定前后依赖、能保留中间产物的 AI 工作流；若需求处于高频探索期，不宜过早把所有细节“定死”，应增加变更与回滚机制。

## 自己的待测方向（待实操，非已执行）

面向已经能用 Cursor 或 Codex 生成简单网页、但经常返工的新手独立开发者，我会用一个具体输入“为自由职业者制作可录入客户、项目、回款状态的本地优先看板”测试齐码流程。第一步是从仓库安装六个 Skills，只运行 vibe-idea，并保存原始一句话需求和生成的 idea.md。随后按顺序生成全部文档和原型，再实现一个最小版本。观察点包括：每步是否能读取前一步产物、交互状态是否覆盖加载/空/错误/无权限、技术栈是否未经允许漂移、最终页面与原型差异、人工修改轮次、总耗时和模型调用成本。所需证据包括完整会话日志、每阶段 Git 提交、文档版本差异、原型与成品逐页截图、可点击功能测试表、失败与人工修正记录；再用“不采用齐码、直接给同一需求生成”的基线复做一次，才可评价返工和对齐改善。

## 商业线索与披露

文章的明确品牌任务是推广作者自制并开源的「齐码.SKILL」，主要卖点为六段式全链路、视觉规范、交互无歧义、原型与实现对齐以及零基础可用；入口是 GitHub 仓库 github.com/idiotLeoLYJ/Daliu-Awesome-Skills。文中还为 styles.refero.design、Google Stitch、Gemini 3 Pro 等第三方资源提供使用路径，但未给优惠、邀请码或付费购买入口。作者未明确披露广告、赞助或品牌合作，合作关系未知；不能据此推导开发预算、服务收入或第三方付费关系。
