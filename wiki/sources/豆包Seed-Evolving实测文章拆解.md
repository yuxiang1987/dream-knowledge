# 豆包Seed-Evolving实测文章拆解

来源：`raw/article/lurenjiaTM/实测豆包Seed-Evolving，写代码比我预期能打太多了.md`，署名时间 2026-09-02。视频、截图与后台数据未在本页核看；结构化数量、token 消耗、缓存命中率与耗时均为原文自述，未独立核实。

## 定位、标题与开头

这是**模型多案例实测**，三个案例分别覆盖长程结构化处理、前端加推理，以及事实核查，是本批样本里测试维度跨度最大的一篇。

标题「实测豆包Seed-Evolving，写代码比我预期能打太多了」由**产品名＋实测标签＋预期反差＋口语化判断**组成。「能打」是作者判断，正文用三个案例与具体数据支撑，并同时列出短板，属于兑现较好的判断型标题。

开头用「读者请求」作为起点：评论区不断有人提这个模型、同事也推荐，「起初我也没咋在意」，测完发现「还真能打」。随后交代一个产品特性——只有一个持续更新的版本，接入时用同一个 API key，升级自动生效；再看更新记录（支持 1M 超长上下文、长程任务能力提升、视觉检索增强），最后预告重点案例。钩子类型是**读者请求＋半信半疑＋实测反转＋产品特性交代＋预告案例**。用「大家让我测」开场，比直接说「今天测个模型」多了一层理由。

## 结构与推进

1. **案例一 史书知识图谱与 Wiki（长程结构化）**：复刻一个把史书做成可交互知识图谱的项目，把原项目仓库与一整本《三国志》一起交给模型，观察它能否先读懂原项目、再把经验复用到新史料，独立完成从文本解析、实体识别、关系抽取到知识图谱构建的全流程。作者先讲清难点：识别人名、政权、地点与事件，理清关系与时间，还要处理同一称谓在不同上下文指向不同人的情况，且面对的是整本书而非片段。任务近八小时完成。
2. **案例二 网页推理游戏（前端与推理）**：让模型做一款需要模糊现实与虚拟边界的替代现实游戏，先一句话生成方案，再铺开博物馆、论坛、终端等多个相互关联的网页。
3. **案例三 行业首创的事实核查（搜索与交叉验证）**：核查「苹果称卫星紧急求救为智能手机行业首创」与华为更早发布相关能力之间的冲突，并额外提供 12 篇标题党倾向的媒体文章与两家公司的官方材料，测试它能否自行搜索、判断与交叉验证。
4. **结尾**：给出结论与适用范围，同时列出短板。

## 三组案例的具体发现

| 案例 | 原文做法与数据 | 值得记录的判断 |
| --- | --- | --- |
| 史书知识图谱 | 输入里甚至没有附文件，让它自己扫描电脑找到素材，并结合本地仓库判断可复用的 Skill、代码与流程；模型还按实际需要修改了原有 Skill，把跨传事件关联、史料冲突判断等认知任务交给 Skill 处理。原文给出全书 65 卷、2149 段正文全部结构化，合并去重后 1944 个标准化事件、2151 条跨传记载，88 个事件在两篇以上互相印证、39 个在三篇以上、17 个在五篇以上；2265 个人物实体、2727 条人物关系、4312 个 Wiki 页面；全文逐字保留，抽取内容可回原文核验。子 Agent 并行但每个任务都要按最初标准判断合规才入库。后台显示近 3 亿 token、缓存命中率 94% 以上 | 分工并行加统一校验，是长程任务保持一致的可行做法；把认知规则沉淀成 Skill 也算一次真实的自建工具过程 |
| 网页推理游戏 | 一句话生成方案后，不到十分钟铺开多个网页。第一版能用但「一眼就是很 AI」，于是把国家博物馆官网给它照着重做，明显更真实；再导入一批参考素材生成完整游戏，故事包含报纸头条、失联者手机短信、相册日期与博物馆内网等跨页面线索，页面发现的信息要能在其他页面继续使用并影响状态 | 想摆脱「一眼 AI」的外观，给真实参照物比继续写形容词有效；跨页面线索依赖是这类游戏的核心难点 |
| 事实核查 | 前后半个多小时、调用五十多次工具，从官网查到卫星服务商提交给监管机构的文件。最值得肯定的是它没有掉进「谁早一天谁就赢」的框架，而是指出两者解决的是不同问题（一个解决出事如何求助，一个解决没信号如何给熟人报平安）；还反过来发现作者提供的一篇文章与官方资料矛盾 | 核查的价值不只在比时间，而在分清两个对象到底是不是同一件事 |

## 失败、边界与可复用技巧

- **长上下文不等于自动全局检查**：监控回放只有黑屏没有视频，作者直接截图给模型才修好。作者的总结是，只看代码时模型可能坚称视频已存在，看过截图才意识到「位置存在但没有显示」。由此建议把日期、金额这类数字单独整理成表，每次改完再走一遍表格核对，不要指望模型在长对话里自己记住。
- **日期一致性是薄弱环节**：模型曾把当天日期写错，也把案发日与当前日期的前后关系弄反，作者连续提醒两三次才统一。
- **中断次数是可用的长程指标**：近八小时的连续任务只中断三次，其中一次是询问是否继续处理第三批；一次是电脑休眠导致，「这锅确实不该模型背」，且联网后能接续；一次是十个 Agent 并行造成的堵塞。作者据此判断异常中断只有一次。
- **多 Agent 并行是瓶颈**：并行时任务可能中断、速度也会变慢。
- **3D 是明显短板**：展厅由简单几何体组成、灯光偏暗、缺少真实材质；用另一模型按同一句话重做后整体布局更合理。作者结论是能把 3D 场景搭起来，但做不到仅靠几轮自然语言就打磨成有说服力的展厅。
- **事实核查的两个问题**：作者逐条复核发现模型把开机日期与众测开放时间写错；此外，模型一边承认没有查遍所有小众设备，一边又肯定地说「苹果是全球第一个」。作者据此写下一句可复用的判断——「没找到反例，和已经证明全球第一，中间还是隔着一条河的」。他还明确表示不喜欢「先使用错误信息、再到文末标注」的做法，理由是「要是我没看到最后呢」。

## 证据与边界

结构化数量、实体与关系条数、token 消耗与缓存命中率均来自模型输出与后台截图，本页未核看，也未独立验证。事实核查案例中作者做了逐条人工复核并发现了错误，这是值得照做的做法；但复核范围与检查清单未公开，因此只能说明「作者发现了两处日期错误」，不能说明其余内容准确。3D 对比是与另一模型的单次对照，环境与提示词是否完全一致未交代。作者对模型把不确定事项标注在文末的态度前后略有张力：先说「既然标注出来那也可以原谅」，后面又强调不喜欢先给错误信息再标注，写稿时更适合采用后一种更严格的口径。

## 结尾与写作卡片

结尾先给结论（能打而且挺好用），再说明印象最深的是长程任务能力——处理整本书、维护相互关联的多个页面、用截图修 Bug，以及单一持续更新的版本省去迁移麻烦；随后列短板（多 Agent 并行中断与变慢、3D 的材质光影不足）；最后收在适用建议上：文件多、流程长、需要不断迭代的复杂项目值得一试。

**写作卡片**：适合模型多维度实测 → 用读者请求与半信半疑开场 → 先交代一个产品特性 → 三个案例覆盖长程、前端加推理与事实核查 → 每个案例给可核对的数字与一处失败 → 把不该模型背锅的中断单独剔除 → 结尾分别说明优点、短板与适用项目类型。
