## 读者主问题与标题兑现
标题的入口是“PDD 员工认为 AI 一天能做过去一周的活”，但正文没有提供任务类型、代码规模、验收标准或时间记录。开头写道：“刷到一位 PDD 老哥发的帖子，问现在还有没有古法编程，说感觉在需求明确的情况下，AI 一天就能完成他过去一周的工作量。”这是第三方主观转述，不是作者对 PDD 员工效率的核验。作者随后以自己使用 Claude Code、Codex 和 Opus 5.5 的感受附和，但也未给出同任务对照实验。主体则是 Skill、Agent 定义、超时、库存和分布式事务面试题，因此标题中的职场话题与主体存在断裂。“PDD 业务已嵌入大模型”和招聘信息部分分别属于作者概括、公开招聘信息推断；不能由此证明文中的 PaiCLI、库存或事务方案就是 PDD 的真实内部实现。

## 结构与转场
结构由效率话题切到 PDD 场景，再转向五道 Agent 面试题。前两题讲通用 Agent 运行时，后三题聚焦超时、电商库存和分布式事务，技术递进合理：先定义能力，再进入可靠性和交易一致性。但转场中的“PDD 正在建设支撑大模型业务的基础设施”只由招聘信息推断，和后续具体架构没有证据连接。部分小标题直接粘在问答之间，如“长任务自检、停滞收尾与独立快照恢复”，编辑层级不够统一，影响阅读节奏。

## 案例证据与人力成本
作者亲测叙述只到“现在打开 Claude Code、Codex，只要把需求讲清楚，的确很快就搞定了”，没有公开输入、操作录像、产出代码、验收结果和返工时间。Agent 技术部分以 PaiCLI 的团队叙述为主。库存案例的输入是用户多轮选 SKU、数量和优惠券后确认购买；操作包含实时复核、HITL 授权、Redis Lua 原子预扣、MQ 异步落库、MySQL 条件扣减、延迟释放；预期结果是防超卖和重复扣减。人工环节明确有下单前确认，但确认耗时、异常处理人力、对账与补偿成本均未披露。分布式事务案例输入为跨工具写操作或订单提交；操作是 Saga 账本逆序补偿、TCC 冻结/确认/取消、Outbox 投递；结果仅为设计目标，未披露压测并发量、故障注入、资金损失率或线上结果，不能当作实测结论。

## 解释语言与结尾
文章最有价值的是明确划分概率模型与确定性交易代码：“大模型擅长意图理解、商品筛选和工具编排，但输出带有概率性，绝对不能让大模型去计算剩余库存，也不能直接更新库存表。”这一原则比具体中间件选型更可迁移。Intent Token 也解释了为什么工具调用 ID 只能挡网络重试，不能挡模型跨轮重复调用。不过文章没有独立结尾，停在 Outbox 消费设计，缺乏对五题共同原则的收束，也没有提示 Redis/MySQL 双写、TCC 空回滚、悬挂与运维复杂度。

## 边界与可迁移编辑动作
应在技术题前加醒目标注：“以下为通用/ PaiCLI 方案，不代表 PDD 内部架构。”把“一天干一周”改成待验证假设，并补同任务的人工作业基线。库存题应增加故障矩阵：Redis 成功而 MQ 失败、MySQL 成功而响应丢失、延迟消息重复、Confirm 超时等；同时列出人工对账入口。TCC 与 Saga 不应只讲优点，还要比较锁定时间、开发量和补偿失败率。文中未披露与 PDD、Claude Code、Codex、Opus 的商业合作，商业关系未知；“想办法搞第二个账号”也应解释合规边界。

## 我的待实操方向
读者是面试中需要回答“Agent 下单怎样不超卖”的 Java 工程师。我的输入是一套模拟 SKU 库存、用户会话、Intent Token 规则和可重复投递消息。第一步实现不含大模型的确定性下单状态机及 Redis/MySQL 双层幂等，再让 Agent 仅负责参数编排。观察点包括并发超卖数、重复扣减数、确认取消后的释放延迟、消息重复消费、补偿失败和人工对账次数。所需证据为压测脚本、数据库流水、故障注入记录、状态迁移日志、基线方案对照，以及开发与人工返工工时；没有这些数据前，不宣称“一笔都不算错”。
