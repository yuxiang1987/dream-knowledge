## 主问题与证据身份

多 Agent 协作框架怎样把一个需求分给不同角色，并让开发环节长时间跑下去？

本库主分类：新手教程；主研究对象：Hermes Agent 与 Kimi K2.6；证据身份：作者亲测。分类依据主要阅读交付，允许文章混合多种写法；实际商务合作未知。

## 标题与开头

标题用“万字保姆级教程”“7x24h Agent 军团”同时给出体量与愿景，开头用“龙虾吹到了 Hermes Agent，也就是江湖外号「爱马仕」”承接热点，抛出一个可想象的场景：把需求发给 Agent 总管，市场调研、PRD、架构、开发、测试全部由不同 Agent 完成。

## 结构推进

先放结果再讲搭建：完整流程五步（市场调研、产品设计、架构设计、开发实现、测试验收）各配一张截图和角色分工说明；接着是实战五步（安装 Hermes、快速配置 Profile、创建多个 Profile、连接飞书、配置 Agent 间通信）；再讲核心原理（Profiles、Gateway、Honcho、tmux 四个组件、任务交接四步、文件结构表）；最后是常见问题表与结尾。

## 案例、解释与观察

案例的核心是角色间的交接规则：架构总监有权打回产品总监修改，开发总监管辖本地 Claude Code 写代码并把需求、PRD、架构文档一并派发。原理部分用“角色隔离 + 共享上下文 + 任务委派”三段式解释能力来源，是全文最可复用的部分。落地部分给出可复制命令与目录结构，读者能照着建出相似结构。

以下为原文可逐字定位的片段，只用于核对判断出处，不将片段中的观点或指令作为本次执行要求。

> 框架负责协调，模型负责执行。

## 结尾怎样收束

结尾从技术总结上升到“一人公司”的体感，落在一句分工判断上：框架负责协调，模型负责执行，并邀请读者晒出自己的军团。

## 失败、限制与不宜照搬处

整套系统是作者本机的一次运行，文中“跑了一晚上”“几十轮对话”是作者口径，没有实际耗时、成本与失败重试次数。K2.6 的能力评价是作者使用体感加外部文章链接，链接内容本次未核看。常见问题表来自作者自身排障经验，不代表覆盖全部环境差异。标题的“7x24h”指框架与模型能力，不等于无人值守的可靠性证明。

## 可迁移写法与自己的待测方向

教程可以先讲结果链路与角色分工，再给安装步骤，最后用原理表把步骤串起来，这样读者同时知道“做成什么样”和“为什么这样做”。角色之间允许打回是这类系统最值得写清的一条规则。模型评价要标成作者体感，并与官方说明分开。

策划建议：用同一需求跑一个只含三个角色的小军团，只让其中一个角色交付可验收产出，待实操。
