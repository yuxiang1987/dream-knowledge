## 标题与开头

标题紧扣 B 站近期热词“FDE 落地神器”，点出“又一个 Harness 开源了”。开头 P1—P14 先用 B 站“转行 FDE 必备”百万播放热度拉近读者距离，再解释 FDE“驻场交付、每家规则都不一样”的真痛点，进而说明为什么通用 AI 工具替代不了“数据留本地 + 权限管死 + 可跨客户复用”。

标题兑现情况：正文不仅讲清了 FDE 架构，还真从源码把本地工作台跑起来，并走完了“客户 A 交付 → 抽成带配置插件 → 沙箱审阅批准 → 客户 B 套模板复用 → 插件升级版本隔离”的完整 FDE 闭环，兑现非常直接。

## 结构推进

B 站 FDE 热度与企业刚需 → 心玮医疗案例与 9 项自评背书 → 拆解核心架构（大脑/小脑/记忆/MHS/TTT/RSI） → 源码安装与配置 Agnes 3.0 Flash → 第一个客户：茶屿奶茶退款核对＋轨迹页审计 → 第二个客户：把退款核对封装成插件、沙箱批准、麦穗里烘焙店改配置复用、插件升级后验证旧会话 0.1.0 版本隔离 → 结尾归纳“白牌化、可定制、可插拔、可复用”四特性。

和同批次路人甲TM的 Agnes Harness 文章相比，路人甲TM偏重“自建小餐馆对比 Codex 速度 + 深扒 TTT/RSI 论文报告”，而小林coding 偏重**“本地源码构建 + 奶茶店/烘焙店两家客户的插件化与滚动发布隔离”**，切口形成明显互补。

## 结尾怎样收束

用八个字“白牌化、可定制、可插拔、可复用”总结 Agnes Harness 对 FDE 和企业的价值，再次强调“前端自家品牌、数据权限自己管、审计记录查得到”，最后附 GitHub 开源地址鼓励想当 FDE 的同学自己拉下来跑一遍。

## 失败、限制与不宜照搬处

- 失败记录缺失：全篇演示流程一路顺滑，未记录构建报错、插件提取失败、烘焙店规则改错或退款算错的失败案例，按规则记“未提供失败记录”。
- 模拟与真实落地落差：奶茶店与烘焙店均为作者虚构的小规模模拟表，提示词和核对结果截图未核看，也没有公布精确的核对准确率（例如有没有漏算定制蛋糕条款）与 Token 成本；此外目前仍是开发者预览版、无安装包且需 Mac/Linux + Node 24.10+，对非研发新手仍有门槛。
- 数据留存细节：虽然强调“数据留本地”，但作者实测使用的是在线调用 `platform.agnes-ai.cn` 的 `Agnes 3.0 Flash` API，敏感业务数据若走云端模型接口仍需考虑出域合规边界（非纯本地离线模型）。
- 不宜照搬处：不得把“服务过奶茶行业客户”的玩笑写进自己经历；单篇互动快照为阅读 22121、点赞 97、老赞 233、转发 1216、收藏 261、评论 33（n=1），不构成日常基线或传播因果，未测本账号读者效果。

## 可迁移写法与自己的待测方向

- 可迁移动作：测“开发者/企业交付类 Agent 框架”时，别只用单文件 Demo 测能力，而是设计**“客户 A 跑通 → 抽配置成插件 → 客户 B 换规则复用 → 升级插件验证旧会话不受影响”**的四连测试，把工程价值（复用性 + 隔离性）真正演示出来。
- **待实操**：面向想把 AI 工作流封装给多业务线复用的开发者，在隔离测试环境里输入两套自己编制的脱敏“业务核对规则 + 15 条含边界陷阱订单样本”（第一套常规规则，第二套新增例外不退条件和不同金额阈值）。第一步按 README 检查构建依赖并在本地跑通首家样本并核对逐条算账准确性，再要求框架抽成配置与插件模板套用于第二套规则并做一次版本升级测试。观察算账准确率、沙箱审阅是否确实拦截越权权限、新旧会话版本隔离是否生效以及本地构建与 API 消耗。需保留源码、两套配置 diff、逐单核对表与日志，未验证本账号读者效果。
