**主问题**：当一个 Agent 可接入上百个工具时，如何在不把所有 Schema 塞入上下文的情况下，先过滤不可用工具，再召回少量候选，让模型选择并安全执行，同时建立可测量的失败兜底？

### 标题承诺与开头

标题采用面试官追问与候选人答错的对话，围绕“Schema 全塞进 Prompt”制造上下文爆炸的冲突。正文开场继续用三轮错误答案依次排除全量暴露、简单拆 Agent、Embedding 第一名直调，随后给出“确定性过滤—分层召回—模型精选—失败兜底”的标准回答。正文完整解释了标题问题，并覆盖注册表、鉴权、检索、动态绑定、评测和兜底，信息承诺兑现；但这是一套设计方案，不是作者展示的已上线系统。

### 结构推进

先用“简要回答”给面试版结论，再进入长篇解析。详细部分依次回答为何不能全塞、Tool Routing 与 Multi-Agent Routing 的区别、工具注册表、确定性过滤、业务域粗分类、候选域检索、LLM 动态绑定、Skill 渐进加载、Schema 质量、评测与失败兜底。中段用订单查询与取消案例贯穿两层路由，用伪代码把各层连接起来；尾部“面试总结”重新压缩成可口述答案，之后导入网站、训练营、私教和项目资料。整体是“错误方案—架构分层—指标闭环—商业资源”的结构。

### 逐例证据与人工成本

- 说明性案例：用户提出“查询订单 A100，确认未发货后帮我取消”。文章设定 Orchestrator 先把任务交给订单 Agent，这是 Multi-Agent Routing；订单 Agent 先暴露 order_get，确认状态后再暴露 order_cancel，这是 Tool Routing。该案例用于说明路由对象不同，没有真实用户输入日志、工具实现、调用结果、失败记录或线上指标；人工修正、耗时和成本未提供。证据身份：作者构造的教学示例，不是实测案例。

- 说明性方案：伪代码 route_tools 先按产品、租户、角色、环境和健康状态过滤，再以分类置信度0.7决定是否收窄业务域，随后混合检索 Top-K=6 并绑定完整 Schema。作者明确说明阈值和 Top-K 只是控制点示例，并非通用最优值。代码存在排版压缩，且没有依赖、索引构建、模型、数据集或执行结果，不能视为可直接运行源码；人工修正、耗时和成本未提供。证据身份：作者方案说明。

- 材料交付：文章提供一张工具卡片应包含的字段、分层路由流程、指标清单与故障兜底策略，适合作为面试提纲或设计清单。关于 OpenAI Agents SDK、OpenAI 与 Anthropic 工具搜索、动态启停和延迟加载的内容属于官方能力转述；未给出具体文档链接、产品版本和本地验证结果。

### 解释、观点与可证范围

作者把全量 Schema 的问题归纳为 Token 占用、相似工具混淆、权限暴露与延迟，并主张让确定性系统处理授权和硬边界，让检索负责高召回，让 LLM 在小集合内做语义精选，执行层再次鉴权。这个职责拆分是架构建议，不等于在任意业务上必然更快或更准；文章也承认新增分类与检索会产生耗时。BM25、Embedding、Reranker、Prompt Cache 和动态工具加载的机制解释不能替代实际基准。工具描述质量决定路由上限也是作者的工程判断，需要通过具体误选数据验证。

### 语言、图文与结尾

语言以面试对话开场，正文转为分层说明，频繁使用“先……再……最后……”保持工程步骤感。订单、退款、支付等例子让权限风险具体化；表格在文字中承担工具卡片字段模板，伪代码承担链路示意，但没有真实截图或运行 Trace。结尾先给一段可直接背诵的面试总结，再列出网站、面试题、Agent训练营、私教和四个 AI 项目，知识内容最终导向账号资源矩阵。
