## 读者主问题与标题兑现
标题把“xiaom 员工年终奖”放在最前，并附带 Agent 面试题。正文开头只依据一张截图和车型事件做时间判断，作者没有披露截图来源、员工身份、系数、奖金数额或公司确认，因此只能视为未经核验的第三方线索与作者推断。随后很快转到 MiMo 产品期待，再进入十道 Coding Agent 面试问答。标题中的职场八卦与主体面试题存在明显断裂：年终奖只是引流入口，绝大部分篇幅服务于 Agent 求职准备。作者明确说没有拿到 mimo desktop 内测资格，因此桌面端能力来自朋友测评的第三方转述，不是作者亲测；“9月8日官方启动内测”是官方信息转述，本文未外部核验。

## 结构与转场
文章可分为四块：截图判断、MiMo 与小米 AI 展望、十道面试题、个人行动感言。由年终奖转向 AI 团队，再借 MiMo 过渡到 Agent，逻辑上有桥，但内容比例失衡；“接下来，上我们的传统艺能”直接切换题库，进一步暴露标题前半与主体不一致。面试部分按架构、模型适配、工具、失败恢复、上下文压缩、摘要、记忆纠错推进，问题之间递进较好，后半集中讨论压缩与记忆，主题连贯。

## 案例证据与人力成本
题目答案以第一人称描述一个 Java、Spring AI 的终端 Coding Agent，但正文又说题目由小伙伴要求分享，没有明确每段答案究竟是作者项目已实现、候选人示范答案，还是整理后的理想设计，证据身份模糊，不能一概当成实测。披露的输入包括用户任务、九层提示词、多模型 API、工具 Schema 和多轮历史；操作包括 tool_call 解析、HITL 审批、线程池执行、Git 快照、Map-Reduce 摘要、JavaParser 诊断与记忆校验；预期结果是继续 ReAct、减少上下文、支持恢复。实际运行成功率、缓存节省账单、压缩质量、重试命中率、并行收益和测试结果均未披露。

人工成本并不低：写操作逐次审批，用户需要发现越界后拒绝或打断；项目记忆手动维护；错误方向可能回滚后重发指令。文章对此有明确表述：“第一个是审批环节拦截。比如摘要丢了‘只改 service 层’这个约束，模型去改了 controller 的代码，写文件的时候用户会在审批环节看到改动内容，直接拒绝。”这说明系统把一部分质量保障转移给用户，而非自动消除错误。返工的具体次数与时间未披露。

## 解释语言与结尾
问答体适合面试复述，诸如统一接口—协议基类—供应商实现、短期记忆—历史压缩的分层表达清楚。对压缩损伤的判断尤其诚实：“压缩有没有丢掉关键上下文，目前主要靠两个间接信号。”说明主动校验仍是建议方案，而非已完成能力。个别表述如 token 成本“省一个数量级”缺少输入长度、供应商缓存计价和账单证据。结尾从技术题切到反拖延励志，情绪饱满但没有回收年终奖或面试知识点，第三次主题跳转削弱聚焦。

## 边界与可迁移编辑动作
不能将截图推断写成公司奖金事实，不能把朋友测评写成作者体验，也不能将面试答案默认成已部署系统。可迁移动作：标题改为“从年终奖截图聊到小米 AI：10 道 Coding Agent 面试题”，或把八卦与题库拆篇；每道答案增加“已实现/设计中/建议方案”标签；用表格记录输入、操作、输出、失败和人工介入；对上下文压缩建立约束召回率和任务连续性测试；将审批策略细分为读、普通写、危险命令与生产操作。

## 我的待实操方向
读者定位为准备 Agent 后端面试、同时有原型项目的 Java 开发者。我的输入是一套小型仓库、五个带明确边界的修复任务，以及故意加入的文件路径和“不得改 controller”约束。第一步实现最小工具注册、写操作审批和完整日志，不先上长期记忆。观察点是任务成功率、越界修改、失败恢复、压缩前后约束保留、审批次数与人工耗时。所需证据包括提交 diff、工具调用轨迹、token 账单、压缩前后实体比对、测试报告、回滚记录和多次重复结果，再决定是否加入自动摘要与长期记忆。
