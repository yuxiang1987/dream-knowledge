## 主问题

如何用一份可直接放入 CLAUDE.md 或 AGENTS.md 的常驻指令，减少 Agent 擅自脑补、过度设计、扩大改动范围和目标不可验证的问题？

## 目标读者

适合使用 Claude Code、Codex 或类似 Agent 处理代码、文档、资料和表格，且经常遭遇擅自扩展、改动过多或需求理解偏差的用户。尤其适合已经会创建项目文件或设置自定义指令、愿意逐步维护协作规范的人；对完全不了解文件路径的新手，文章提供了路径但没有终端创建命令与排错步骤。

## 主研究对象

核心对象是一份适用于 Claude Code 与 Codex 的中文 Agent 行为准则，包含“想清楚再写、简单优先、外科手术式改动、目标驱动执行”四条规则，并给出项目级与全局级文件放置方法。文章称灵感来自 Karpathy 在 GitHub 公开的 CLAUDE.md，作者对其进行了中文整理和面向非开发任务的删减。

## 证据身份与分项边界

证据由三层构成：第一层是对第三方资源的转述，作者称 Karpathy 的 GitHub 项目有 17 万以上 Star、原文件只有四条规则，但未给仓库链接、统计时点或原文对照；第二层是作者亲测体感，称已在 Claude 和 Codex 中使用一段时间，变化包括 Agent 会先询问 A/B 理解、减少复杂架构、缩小改动范围并加快审核；第三层是作者给出的推理性示例，如把“整理好”改写为按三个维度分类并附出处、把“修 bug”改成先写复现测试。没有提供使用前后同任务输出、返工次数、代码 diff、测试日志或准确率，因此“效果惊艳”主要由主观报告支撑。

## 标题承诺与开头

标题承诺“可以直接复制”的 CLAUDE.md/AGENTS.md，并宣称实测效果惊艳。正文完整给出可复制的中文准则、两种工具的文件名与放置位置，前半承诺兑现较充分；“惊艳”则缺少对照实验和量化结果，只由作者体感支撑。开头借 Karpathy、GitHub 17 万以上 Star 和“四条规矩”建立权威与流行度，再迅速说明作者已在 Claude、Codex 使用，随后预告逐条解释和完整成品，资源价值明确。

## 结构与转场

开头交代来源、用途和文章交付物；主体先按四条准则逐条采用“Agent 老毛病—规则如何约束—作者体感”的结构解释；四条结束后用“都是在管 Agent 的手”归纳统一逻辑；中段给出完整可复制文本，包括总取舍、四个分节、判据和示例；后段从原则转到部署，分别说明 Claude Code 与 Codex 的项目级、全局级路径及 Codex 桌面设置入口；最后建议先原样使用一周，再按个人协作习惯补充规则。转场自然，从为什么有效到复制什么，再到放在哪里和如何迭代，形成教程闭环。

## 案例：目标、输入、操作、结果与人工成本

示例一“活动方案”用于说明需求歧义：输入是“帮我写个活动方案”，作者假设 Agent 可能默认线下，而真实目标是线上，结果会导致推倒重来；加入规则后作者称 Agent 会先问“你是要 A 还是 B”。这属于概括性亲测体感与假设示例，没有具体工具、原始会话、耗时或返工成本。示例二“三列表格”用于说明过度复杂：真实目标是简单三列表，Agent 可能擅自增加列；操作是加入“简单优先”和“资深的人是否会觉得过度复杂”的自检；作者报告不再乱搭复杂架子，但未给实际表格、删减数量和人工修正。示例三“局部改文档”用于说明范围控制：目标只改某一段，风险是连旁边标题也被优化；规则要求每处改动都可追溯到需求；作者报告改动审核变快、心里更踏实，未给 diff、审核时长和错误率。示例四“整理资料”把模糊目标改成按“是什么、做什么、怎么做”分类且每条配出处，属于方法示例，没有实际输入资料与结果。示例五“加校验”和“修 bug”要求先写非法输入测试或复现测试再使其通过，属于代码工作流示例，不是作者展示的完整亲测案例。全文未给任何案例的订阅成本、调用量、精确耗时或失败记录。

## 解释、语言与图文作用

文章用“治哪个老毛病”组织解释，把抽象 Agent 规范拟人化为“脑补”“闷头开干”“手痒”“乱伸手”，便于非技术读者理解。语言短促口语化，先说问题再给规则，随后用一句个人体感落地，节奏清楚。准则正文则切换为命令式短句和项目符号，适合机器读取与读者复制；“两百行能用五十行写完就重来”“每一处改动都要能直接追溯到我的需求”等判据比单纯价值词更可检查。不过文章把文档、表格和代码任务放在同一套规则下，没有充分解释不同工具对指令优先级、上下文加载和冲突处理的差异。

## 结尾收束

部署说明后不鼓励一次性堆叠规则，而建议原样复制、使用一周、观察不合脾气之处后再补一两条，将静态模板转为持续维护的个人协作规范。随后以“希望对你有点用”结束实质内容，再进行点赞、在看、转发、星标召唤和作者身份介绍。

## 限制与不可照搬处

准则偏向谨慎而非速度，作者也明确指出琐碎小任务可自行取舍；这意味着澄清和计划步骤可能增加短任务交互成本。文章未提供 Claude Code、Codex 的具体版本、模型、操作系统、规则优先级、子目录覆盖机制、上下文长度影响及加载失败排查。所谓“两边都认、一个字不用改”没有在不同版本和复杂项目中系统验证；面向文档、表格的适用性也主要是作者主张。GitHub 17 万以上 Star、来源归属和四条原文均未独立核实，且“一个字没改”与后文“弄成中文版”“去掉原版里偏开发的零碎”在表述上存在口径不清。没有量化返工减少程度，也未展示失败案例、冲突规则或 Agent 仍不遵守时的处理。

## 可迁移的编辑动作

可执行的编辑动作是先从真实返工记录提炼规则，而非无限添加泛化指令：收集最近五次 Agent 擅自猜测、过度实现或越界修改的实例；为每类问题写一条可观察判据；把项目专属规则与全局习惯分开存放；对改文档或代码任务要求 Agent 先复述范围和成功标准；交付时用 diff、测试或出处逐项验收。初版只放四类基础约束，运行一周后仅针对重复出现的问题补规则，并删除不能改变行为的口号。

## 自己的待测方向（待实操，非已执行）

面向同时用 Claude Code 与 Codex 维护小型代码库的独立开发者，我会选一个含明确测试的公开示例项目，并准备三类自己的任务：含歧义的新功能、只允许修改一个文件的 bug、要求保持三列输出的数据整理。第一步是在两个项目副本中分别建立无准则基线和加入同一准则的实验组，固定模型、提示和随机条件。观察点是澄清问题次数、非目标文件改动数、增加的无关功能、测试通过率、总轮次、完成时间和人工回退行数。所需证据包括完整会话日志、Git diff、测试报告、令牌或调用成本记录，并重复多轮判断改进是否稳定，而不是只凭一次顺手体验。
