## 读者主问题与标题兑现
文章解决的是：模型升级后，如何清理 AGENTS.md、CLAUDE.md、Skills 与 Memory 中为旧模型设置的过度约束。标题“Codex 最新焚决发布，快！”制造了强时效和紧迫感，但“焚决”并非正文中正式产品或方法名，而是作者对 OpenAI 文章的戏称；正文真正提供的是两段可复制提示词与四类优化原则，基本兑现“快上手”，却没有交代所谓 GPT-6 Astra、原文链接内容及发布日期的外部核验结果。作者称“第一时间就去实践了一波，效果显著”，属于作者亲测叙述，不等于经对照实验验证。

## 结构与转场
开头以第三方 G 哥分享引入，再给“审查—修改”两步提示词，随后用四个编号章节展开：收窄 Skill、瘦身规则文件、放松决策边界、预先定义完成标准。由操作入口转到原则解释顺畅，但开头说“主要优化四个方向”，紧接着只先列出前三个，第四个到后文才出现，提纲完整性稍弱。各节均采用反例、改法、自检清单，便于执行；结尾回扣清理动作，但“原贴也 500 多万浏览”没有阅读量口径与基线，不能据此称爆文。

## 案例证据与人力成本
数据库迁移 Skill 是官方信息的转述：宽泛触发会让普通 SQL 查询加载迁移流程，操作是将描述缩到新增、修改或审查迁移发布，结果被表述为误触减少，但本文未展示作者项目中的触发次数、token 或耗时前后数据。作者自己的 browser-act 观察只说明描述覆盖范围大，未披露修改后的输入、执行日志和结果。两段提示词的输入明确：让 Codex 先审查但不改，再按审查结果修改；操作和预期产物明确，但具体改了哪些文件、多少规则、耗时多少、是否人工返工均未披露。作者反而给出稳健的人力流程：“建议先挑一条有明确依据的建议改掉，然后用一个你熟悉的日常任务跑一遍，观察模型的行为有没有变化。确认没问题了再改下一条。”这意味着仍需人工逐条验收，并非一键瘦身。

## 解释语言与结尾
语言大量使用“浪费上下文”“该放手的地方要放手”等口语化判断，把抽象的触发边界解释成可观察行为。最有效的定义是：“不是写完代码叫完成，也不是「多测几遍」叫完成。完成的定义应该具体到：跑哪些测试、通过什么条件、交付什么产物。”它把提示工程从语气要求转为验收标准。局限是多次以“新模型更强”作为删规则依据，没有给错误率、安全事件或任务成功率。结尾强调长期顺畅，但没有量化收益。

## 边界与可迁移编辑动作
不能把文章视为模型能力的严谨实测，也不能把 OpenAI 例子当作作者项目验证。可迁移动作：把每条全局规则改写为“触发条件—允许动作—禁止动作—验收条件”；将长步骤移入按需子文档；保留生产删除、密钥、远程 push 等硬边界；为低风险测试显式授权；每次只改一条，用固定任务做前后对照。编辑上应补一张变更表，列原规则、新规则、触发样例、误触次数、确认次数和人工修正。

## 我的待实操方向
读者定位为维护 Coding Agent 规则文件的开发者。我的输入是一份真实 AGENTS.md、Skills 清单，以及三个固定任务：只读检索、小范围修复、数据库迁移。第一步先只让模型标记规则冲突和过宽触发，不自动修改。观察点是 Skill 加载数、无意义确认次数、上下文 token、测试通过率及越权动作。所需证据包括修改前后完整提示词、工具调用日志、token/耗时统计、测试报告和人工驳回记录；至少重复多轮，才能判断瘦身是否真的改善表现。
