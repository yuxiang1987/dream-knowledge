## 读者主问题与标题兑现
标题前半是华为、OPPO 跳槽薪资八卦，括号才提示“Agent 面试题”；正文开头仅用一张读者截图复述“42 万—56 万—想回华子”，作者明确说读者来问真假，却没有核验当事人、薪资口径、岗位级别或回流原因。随后快速转到华为 Agent 产品线，再进入 19 道知识库与 Agent 工程问答。因此标题的职场故事与主体面试题存在明显断裂：八卦承担点击入口，主体价值其实是工程知识清单。开头这句也显示证据层级有限：“有读者发来一张包浆的截图，问我是真是假。截图里的主人公上海交大毕业进了华子，年薪 42 万，干了一年被 OPPO 挖去做芯片，开到 56 万。”这是第三方转述，不是已核验事实。

## 结构与转场
结构为八卦钩子—个人职场体感—华为 Agent 产品调研—19 组面试问答—励志结尾。真正的主体又可分为记忆与上下文、安全、检索与分块、结构化抽取、评估与引用、运维更新和文件上传。每题采用“方案—为什么—产品或文章举例”，便于面试复述，但缺少总目录与难度分级；从华为产品线切到通用 Agent/RAG 题库没有说明岗位画像，读者不清楚这些题针对 Java 后端、RAG 工程师还是 Agent 平台架构师。

## 案例证据与人力成本
多数内容是方案型回答，不是项目实测。比如上下文压缩的输入是长工具输出，操作依次为落盘、编辑旧输出、最后摘要，结果目标是保留可恢复信息；真实 token 节省、延迟和返工未披露。检索方案输入是 BM25 与向量候选，操作是 RRF 融合、rerank、阈值截断，结果只给出设计逻辑，未提供作者项目数据。上下文检索处引用 Anthropic 公布的失败率下降 49%/67%，属于第三方或官方公开信息转述，不应当作作者亲测。稳定性方案明确加入人工成本：“能做的是同一份文档抽取两次，两次结果不一致的字段，说明模型自己也拿不准，直接送人工复核。”但双抽取增加多少调用成本、人工复核比例和时长未披露。上线监控与冲突处理也要求每周抽检、管理员裁决，具体人力未披露。

## 解释语言与结尾
文章擅长用反例解释机制，如 Java 17/21 说明相似度去重会误伤冲突，用 tool_call/tool_result 说明切分边界，用文件与网络隔离解释沙箱。评估部分最具方法论价值：“评估要把检索和生成分开看。不然回答错了，分不清是没搜到，还是搜到了没用对。”结尾却重新回到华为、OPPO与时代励志，没有回收 19 题如何用于面试准备，情绪完整但编辑闭环偏弱。

## 边界与可迁移编辑动作
华为产品、奖项、年份及各厂能力均是正文陈述，未做外部核验；“我们用的是分块上传”等第一人称像项目经验，但项目背景、规模、角色与线上结果未披露，不能自动认定为完整实战。商业关系未知。可迁移动作：标题直接突出“19 道 Agent/RAG 面试题”；八卦另文处理；给每题增加适用岗位、输入规模、指标、失败案例和人工成本；用标签区分作者方案、亲测项目、厂商文档和第三方论文；将官方数字附来源与测试条件。

## 我的待实操方向
读者是准备 Agent/RAG 后端面试、已有基础工程经验的人。我的输入是一套带标准答案和证据文档的小型知识库、旧新两种分块及 BM25/向量检索配置。第一步先建立 50 道标注问题与应命中文档。观察点是 Recall@K、MRR、忠实度、无结果率、延迟、模型调用次数和人工复核率。所需证据包括可复跑配置、逐题检索日志、错误分类、人工与模型评委一致率，以及每种方案的调用费用和返工工时。
