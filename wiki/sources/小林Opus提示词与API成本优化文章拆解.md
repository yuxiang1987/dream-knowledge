## 主问题与证据身份

- **主问题**：调用Claude API时，怎样判断钱是否花在重复输入、过时提示词或不合适的思考配置上，并在不牺牲任务效果的条件下优化成本？
- **目标读者**：已有Claude API应用、账单或请求日志的开发者；不等同于只用聊天订阅的普通用户。
- **主分类**：整合型；把官方成本优化文章组织成场景化方法说明。主研究对象为Claude Platform的缓存、提示词审查及effort（模型投入的思考强度）。
- **主要证据身份**：官方主张整理，而非作者亲测。作者开头明确材料来自Anthropic文章《Reducing cost and improving performance with Claude Platform》，结尾给出参考链接；没有自己的请求、运行日志、账单和对照结果。
- **逐项身份**：客服请求前缀是教学假设；六类旧提示词是作者对官方建议的重述及例子；客服六提示词实验、编程/知识评测、训练与留出工单、四组公开评测均是官方实验转述。不能因出现完整数字或命令将这些登记为小林的实测案例，故本篇不生成作者实操案例卡。

## 标题与开头

标题先接“烧Token”的费用痛点，再把嫌疑从模型转到提示词；开头先报官方材料，再用“效果还行但费用肉疼”的开发现场组织问题。正文第二节确实列出重复验证、过度强调、强制流程、过时示例、冲突规则和旧配置六类问题，兑现“可能拖后腿”的解释；但范围明显超过提示词，还包含缓存、模型/档位组合和批处理。题目不是“删提示词必定省钱”的证据，也没有作者对Opus 5.5的亲测结论。

## 结构推进

四节依次问：相同输入为何反复付费→旧规则为何引出多余工作→思考强度是否值得拉满→能否让工具定位费用来源。每节先给任务冲突，再讲机制和操作入口，随后配官方实验及适用限制；结尾按读者已有条件分流到三种命令，而非要求全套执行。

缓存节把读者常混淆的“内容意思相同”和“前缀逐字节一致”分开；提示词节把“长短”改成“规则多做了什么”；effort节把单价改成每任务总费用；工具节把有实际usage的判断和仅看代码的估算分开。图注为解释顺序提供文字索引，但未看图，不能评价图的准确性或可读性。

## 原文定位锚点

- “要检查的是，那条规则让模型多做了什么，有没有把任务带偏。”——第二节末，P48；支撑按实际行为审查规则，而不只按长短删词。
- “别只比每百万 token 的单价，还要看把同一个任务做完，总共花多少钱。”——第三节中，P66；支撑将验收单位改为同一任务总费用。
- “前两种有实际用量作依据，最后一种只是估算，读结果时得分清楚。”——第四节，P87；支撑实际usage与代码估算分层。
- “不必一次全跑完。先找一处改好，再拿同一组任务跑一遍。”——结尾，P107；支撑最小改动后复核，而非直接照搬降费数字。

## 结尾怎样收束

结尾回到重复输入与重复检查，按“刚换模型／已有API应用／已有评测集”三种状态分别给出入口；最后用“费用降了，事情也照样做对了”定义有效省钱。它交付的是待验证路径，不是作者已经跑通的教程。末尾列官方参考资料和站内Opus使用手册推荐，无购买或优惠引导。

## 可迁移写法与自己的待测方向

**可迁移动作**：把同一个成本痛点拆成“输入是否重复／规则是否冗余／配置是否匹配／证据能否验收”；每条建议跟一个可定位例子和适用条件；将引用实验明确标官方报告，再把实际用量和估算分开。避免借用官方百分比给自己的文章制造亲测感。

**待实操／待验证**：面向维护AI Coding或Agent应用、关心真实成本的开发者；使用自己的脱敏任务集、现有提示词与可授权查阅的usage记录。第一步先固定版本和任务验收口径，找出一处可能重复的输入或规则，尚不执行任何付费调用。观察任务正确性、实际请求数、工具调用、缓存命中和每个完成任务的费用是否变化；所需证据为完整输入、配置差异、逐请求usage、独立验收结果、人工修正及账单。具体测试角度与步骤由作者实操时填写，本文不代测、不承诺降费。
