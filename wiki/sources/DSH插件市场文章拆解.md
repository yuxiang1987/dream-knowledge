# DSH插件市场文章拆解

来源：`raw/article/lurenjiaTM/我给DeepSeek Harness搭了个插件市场，这篇教你装，也教你做.md`，署名时间 2026-08-20。截图与视频未在本页核看；项目星数、插件数量、官方文档原话与插件质量均为原文转述或自述，未独立核实。文中三处可复制指令（安装插件、执行约束、安全审查）属可迁移资产。

## 定位、标题与开头

这是**生态观察＋插件教程＋自建插件实录**，三者在一篇里衔接得比较自然：先用数据说明生态已成规模，再给精选清单与安装方法，最后完整记录自己做插件的过程与踩坑。

标题「我给DeepSeek Harness搭了个插件市场，这篇教你装，也教你做」由**第一人称成果＋双承诺**组成。「教你装，也教你做」是明确的交付承诺，正文两件事都做到了，兑现度高。

开头用数字冲击：发布当天一个半小时两万多星、一周十六万多星，称是 GitHub 史上增速最快的项目；不到一周，可安装到该平台的插件就有一千三百多个，带相关标签的接近八千个。接着引出核心设计理念「一切皆插件」，并引用官方架构文档的说法（模型适配器、工具注册表、会话日志，连智能体循环本身都是插件，不存在需要单独打补丁的特权核心），随后**翻译成大白话**——从里到外没有一块零件是焊死的。再**主动回应质疑**（有人说这是技术人自嗨炫技，因为普通人不懂代码托管与包管理器），给出自己的角度：对普通用户是锦上添花，也给开发者更多空间，并举出两个具体需求（只想要深色主题、想实时看 token 消耗），最后收在「每个人的工具都是个性化的」。

钩子类型是**数字冲击＋核心理念引述＋翻译成大白话＋主动回应质疑＋具体例子＋预告**。其中「把技术理念翻译成生活化说法」与「先说出读者可能的质疑再回答」是两个很值得照做的动作。

## 结构与推进

1. **数字、理念与质疑回应**。
2. **自建插件集合页**：作者做了收录各类插件的网页，免去读者逐个逛代码托管站点；每个插件有说明、原地址与可复制的安装命令。
3. **精选插件清单**：桌面端（本身也是插件，给出可发给任意 Agent 的安装指令）、任务完成通知、桌面 UI 全家桶（主题皮肤、任务看板、图像理解、宠物、文件预览）、浏览器助手。
4. **自建插件实录**：先让模型评估自制难度，拿到三档难度框架，再按需求理解、难度判断、方案预览三步推进，最后踩坑并给出约束方案。
5. **结尾的冷水**：列出插件生态的现实风险与一条可复制的安全审查指令，再把话题抬到生态秩序与产品理念。

值得学的结构手法是**教程与实录并存**：前半段是「你可以装什么」，后半段是「我怎么做的、遇到什么问题」。读者既能马上动手，也能看到完整过程与失败。

## 可复用的指令与做法

| 内容 | 原文做法 | 可复用的价值 |
| --- | --- | --- |
| 安装类指令 | 让 Agent 安装指定仓库的插件，例如「帮我安装GitHub上的DSH插件 <地址>」 | 把安装交给已有 Agent，读者不必自己处理环境；适合作为教程里的最小动作 |
| 分档评估难度 | 先让模型给出难度框架：纯界面插件只做客户端一半；涉及文件、命令或事件需客户端与宿主两半；再加整个应用壳是宿主级 | 动手前先判断任务处于哪一档，避免用几小时做一件其实很小的插件 |
| 三步前置流程 | 大白话描述需求 → 让模型做需求理解以对齐理解 → 难度判断与可行性 → **先出几个效果图方案再动手** | 原文明确说「直接跑出来了很可能不符合预期，token也都白花了」；先看方向再实现，是省钱的关键 |
| 浏览器操控的技术机制 | 插件把网页转成带编号的结构化文字（标题、正文、可点击控件），模型按编号操作，不依赖视觉能力；好处是不需要把账号密码交给一个模拟浏览器，直接在已登录的页面里干活 | 解释机制而不只讲效果；「不用交出账号密码」是安全层面的实质优势，比「更方便」更有说服力 |
| 约束急躁型 Agent 的提示词 | 因模型自行推进导致返工，作者写了一段六条约束：只做明确要求的事、遇歧义先问、分步推进并等确认、引用方案前先验证环境、不确定就问、有更好做法先说明并等待决定 | 这是本库目前最完整的「防越界」模板，可复用到任何爱自作主张的 Agent |
| 插件安全审查指令 | 「帮我确认这个插件「地址」，检查它是不是真的DSH插件、源码有没有问题。」 | 给普通读者的最小安全动作；与其讲一堆风险，不如给一句能直接用的指令 |

## 失败过程与根因

作者明确写出：过程不顺利，碰到**需求确认不足、环境查证不足、测试与真实脱节**等问题。他把根因归结为一句很具体的判断——模型「太急躁、太积极，急着推进，脱离了原本的指令」。

最典型的例子：作者只问了一句「图里的今日 token 是显示的 DSH 消耗还是账户总消耗」，模型回答完疑问后**并没有停下来等下一步指令**，而是在同一条回答里花了二十一分钟把第一版插件跑了出来，结果自然不尽如人意。此后作者改为在每条指令末尾追加约束（核心两条：不准自己扩展范围、遇到选择先问），过程才顺畅，插件最终完成并上传。

这段记录的价值在于**把「模型太积极」从抱怨变成可操作的约束条款**，而不是停在「这个模型不好用」。

## 证据与边界

星数与插件数量为公开发布后的流行数据，本页未核实，引用时需标注时间与来源。官方架构文档的说法是转述（原文用「大意是」），要引用原话需回文档核对。插件清单是作者个人的筛选结果，未说明筛选标准与测试方法，因此「最实用」应理解为个人推荐而非评测结论。结尾提到的公司长期目标与创始人说法属外部信息，未给出处。

结尾的风险提示是本文可信度的重要来源：作者明确说该产品仍是预览版，插件多了问题也多，会出现不兼容、冲突崩溃、质量参差与安全性存疑，并建议优先选择社区持续维护、已筛选的插件，装前再审查一遍。把自己做的插件市场也放在这套风险框架里讲，比只推荐更负责任。

## 结尾与观点

结尾分三层：先泼冷水（预览版、插件风险、安全审查建议），再抬到理念——「一切皆插件」意味着一切想法都可能进入这个产品，AI 长什么样不再只是开发者的事，用插件的人都在参与决定；最后用历史对照收束：敢把「核心可换」当作理念的产品不多，上一个这么做的是 Emacs，活了四十年，而该产品能否走到那一天，要看插件生态能不能在热闹之外长出秩序。末尾以「子弹已经出膛，接下来就让子弹飞一会儿」作结。

**写作卡片**：适合生态类选题 → 用数字说明规模 → 引一个核心理念并翻译成大白话 → 主动回应质疑 → 给可直接复制的安装与使用指令 → 用精选清单满足「装什么」→ 用自建实录满足「怎么做」→ 把踩坑归因到可操作的约束条款 → 结尾先讲风险再讲理念。
