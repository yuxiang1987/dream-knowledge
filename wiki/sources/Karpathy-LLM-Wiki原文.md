# Karpathy LLM Wiki 原文

来源：`raw/karpathy-llm-wiki.md`（Karpathy 发布的 gist，文件名 `llm-wiki.md`，页面显示创建于 2026-04-04。原文自述：这是一份理念文件，设计目的是直接粘贴给自己的 AI Agent，具体实现由 Agent 和用户共同确定）。

## 它想解决的问题

常见 RAG 做法是上传一批文件，提问时检索相关片段，临时综合出答案。这能工作，但模型每次都在重新发现知识：一个问题需要综合五份文档时，每次都要重新找、重新拼，知识本身不累积。

LLM Wiki 的做法：模型读取资料后，增量维护一个持久、互相链接的 markdown 结构。新资料进来时不只建索引等以后检索，而是直接整合进已有内容：更新实体页、修改主题综述、标记矛盾、强化或修正既有结论。

核心区别一句话：知识提前编译一次并持续保持最新，而不是每次提问重新推导。

## 三层架构

- **raw 原始资料**：人工筛选的文章、论文、图片、数据文件。不可变，模型只读。是事实来源。
- **wiki**：模型生成的 markdown 页面集合，包含摘要、实体页、概念页、对比、综述。这一层完全由模型拥有和维护。
- **schema**：一份规范文档（Claude Code 用 `CLAUDE.md`，Codex 用 `AGENTS.md`）。定义结构、约定，以及入库、回答、维护时该走什么流程。原文称这是"把模型变成有纪律的维基维护者，而不是通用聊天机器人"的关键配置，应该由人和模型共同演进。

## 三个操作

- **Ingest 入库**：读原始资料 → 写摘要页 → 更新索引 → 更新相关实体页和概念页 → 追加日志。原文提到单篇资料可能牵动 10 到 15 个页面。作者本人偏好一次一篇，并全程参与。
- **Query 查询**：针对 wiki 提问，模型找相关页面、读取、带引用综合作答。原文特别强调：好答案应该回流成新页面，否则探索成果会消失在聊天记录里。
- **Lint 体检**：定期健康检查，查页面矛盾、被新资料取代的过时断言、没有入链的孤页、被提到却没有独立页面的重要概念、缺失的交叉引用、可以用搜索补上的数据缺口。

## 索引与日志

- `index.md` 内容导向，按类别列出所有页面，每条带链接和一句话摘要。回答问题时先读索引定位，再深入具体页面。原文说这套做法在约 100 篇资料、数百个页面的规模下"好得出人意料"，不需要向量检索基础设施。
- `log.md` 时间导向，追加式记录发生了什么。建议每条用固定前缀，例如 `## [2026-04-02] ingest | Article Title`，这样普通文本工具就能筛出最近几条记录。

## 原文提到的其他要点

- 人负责策展资料、指引分析、提出好问题；模型负责其余记账工作：更新交叉引用、保持摘要最新、发现矛盾。
- 这套做法能成立的关键是维护成本接近零。人放弃自建 wiki 通常不是因为不会读或不会想，而是记账工作的增长速度超过价值增长速度。
- 可选工具：Obsidian Web Clipper 采集网页；把图片下载到本地固定附件目录；Obsidian 图谱视图看结构；Marp 出幻灯片；Dataview 用 frontmatter 生成动态表格；wiki 本身是 git 仓库，天然有版本历史。
- 原文明确说这份文档是"有意抽象"的，目录结构、页面格式、工具链都应该按自己的领域实例化，所有提到的东西都是可选的、模块化的。
- 思想源头是 Vannevar Bush 1945 年提出的 Memex：私人的、主动策展的信息库，文档之间的关联和文档本身同样有价值。Bush 没解决"谁来做维护"，LLM 接住了这一环。

## 评论区提出的风险（重要）

gist 评论区里有实践者提出一条值得记下的反对意见：**编译出来的知识库会"自信地出错"**。一旦没有依据的答案被写回知识库，之后的 agent 会把它当成来源继续引用，错误因此获得可信度。

他们给出的应对是把模型输出当作不可信输入，对引用做确定性校验，并区分几种状态：已纠正、已被取代、有歧义、证据缺失。

这条意见对本知识库的含义：结构检查只能验证格式和链接，验证不了结论。体检时必须抽查"结论能否在来源里找到对应证据"。该评论提到的项目本身效果尚未核实，此处仅作为风险记录。
